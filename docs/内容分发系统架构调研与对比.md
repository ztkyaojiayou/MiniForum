# 内容分发系统架构调研与对比（发帖 → 展示）

> 创建：2026-08-26
> 主题：从"发帖"到"浏览/推荐/搜索"的完整 C 端内容分发管道——写路径统一进事件总线、多路下游消费者、Outbox 必达；并与 MiniForum 现状逐项对比。
> 配套：与《feed流架构调研与对比》《推荐系统深度调研报告-抖音版》《微博推荐调研》《推荐系统微服务拆分方案》并列。本文聚焦"内容分发主干"，feed 文档聚焦"关注流时间线"。

---

## 0. 一句话核心洞察

**内容分发系统 = 发帖（写）→ 事件总线（一份事件，多路消费）→ 各下游（关注流 / 推荐 / 搜索 / 统计 / 通知）→ 展示（读）。**
写路径**统一进 Kafka**（事件分发总线），读路径各走各的存储（inbox / 索引 / 缓存）。"发帖后先统一进 Kafka" 是生产级内容分发系统的**标准主干**，不是可选项。

---

## 1. 什么是内容分发系统

从**内容生产**（发帖）到**内容消费**（时间线浏览 / 推荐流 / 搜索 / 热点 / 通知）的完整管道。微博、抖音、小红书都是典型 C 端内容分发系统。

**核心矛盾**：一份内容，要被多种消费场景复用——关注者要看到、搜索要命中、推荐要召回、热搜要聚合、@的人要收到通知。若每个场景都"读时全表扫"，读放大爆炸；所以主流做法是**写时把内容广播给各下游（写扩散），各下游建好自己的索引/缓存**。

```
一条帖子
  ├─▶ 关注者时间线（inbox）
  ├─▶ 搜索索引（倒排）
  ├─▶ 推荐召回池（冷启/热度）
  ├─▶ 热搜/话题聚合
  ├─▶ @提及 通知
  └─▶ 审核/内容理解（标签、embedding）
```

---

## 2. 写路径：发帖后统一进 Kafka（事件总线）

### 2.1 主干链路

```
发帖请求
  → 帖子服务：① 写主存储（MySQL）  ② 发"帖子创建事件"到 Kafka（事件总线）
  → Kafka topic "post-created"（一份事件，多个独立消费组）
      ├─▶ Fanout 消费者      → 写关注流 inbox（推模式）
      ├─▶ 搜索索引消费者     → 更新倒排索引
      ├─▶ 推荐冷启消费者     → 新帖进冷启池/流量池
      ├─▶ 内容理解消费者     → 标签/embedding/审核
      ├─▶ 统计/热搜消费者    → 热度聚合
      └─▶ 通知消费者         → @提及 / 粉丝广播
```

**关键点**：
- **一份事件、多路消费**：各消费者用独立消费组，互不干扰、可独立扩缩容、可独立失败重试。
- **发帖请求立即返回**：写库 + 发事件后即可响应，下游异步处理（扇出/索引/审核都不阻塞发帖）。
- **事件是"最小事实"**：只带 postId/authorId/content 等必要字段，下游按需回源详情（inbox 只存 postId，内容按 id 回源）。

### 2.2 为什么"先统一进 Kafka"，而不是各下游直接查库

| 直接查库（拉） | 统一进 Kafka（推/事件驱动） |
|---|---|
| 每个下游都要轮询/查询全表 | 事件主动推送，下游被动消费 |
| 各下游耦合帖子服务、重复扫描 | 帖子服务只发一次事件，解耦 |
| 新下游要改帖子服务 | 新下游只需订阅 topic |
| 无法削峰（发帖洪峰打爆下游） | Kafka 削峰缓冲 |

## 3. 事务性 Outbox：发帖必达的保证

**问题**：发帖写 DB 与发 Kafka 事件是**两个系统**（MySQL 与 Kafka），做不到原子提交。若先发事件再写库，事件可能带出未落库的数据；若先写库再发事件，进程崩溃可能丢事件。

**标准方案（Transactional Outbox）**：
```
同一本地事务：INSERT posts + INSERT outbox(post_id, status=PENDING)
  → Outbox Relayer（轮询 或 CDC/Debezium/Canal 监听 binlog）
  → 发 Kafka "post-created" → 成功更新 outbox status=DONE
```

- **必达**：事件先落库（outbox 表），Relayer 保证最终都发出去。
- **幂等**：下游以 `(post_id, consumer)` 为幂等键，或利用 Redis ZADD / 索引 upsert 天然幂等。
- **演进**：小项目可用"定时轮询 outbox"；大项目用 CDC（Debezium/Canal）监听 binlog，避免轮询延迟。

> 本项目现状：**未实现 Outbox**（发帖落库后直接调 notifier 发事件，非同一事务）。生产若上线，建议按此模式补强。

## 4. Kafka 的定位：事件总线，不是 feed 存储

（与《feed流架构调研与对比》§8.2 一致，此处从内容分发角度重述）

- **Kafka = 邮局**：负责把"新帖事件"送到各消费者门口，消费即移走游标（队列语义）。
- **inbox / 索引 = 收件箱**：保存每个场景最终要读的数据结构（可随机定位的集合）。
- **误区**：用 Kafka 当 feed 存储（每用户一个 topic）❌——feed 需要可随机定位的集合，不是消费即移走的队列。

## 5. 下游消费者明细

| 消费者 | 作用 | 输出存储 | 读路径 |
|---|---|---|---|
| **Fanout** | 关注流推模式扇出 | 粉丝 inbox（Redis ZSet / 内存） | 关注流读 inbox O(1) |
| **搜索索引** | 全文检索 | 倒排索引（ES / 内存） | 搜索 |
| **推荐召回/冷启** | 新帖进冷启池/流量池/召回候选 | 内存 / Redis | 推荐流 |
| **内容理解** | 标签 / 话题 / embedding / 审核 | 内容元数据 | 分类 / 话题 / 过滤 |
| **统计 / 热搜** | 热度 / 话题聚合 | 计数存储 | 热搜榜 / 看板 |
| **通知** | @提及 / 转发 / 粉丝广播 | 通知表 | 通知中心 |

**通用设计**：各消费者**独立消费组 + 独立存储 + 可独立失败重试**；事件负载最小化，详情回源。

---

## 6. 读路径（展示）

| 场景 | 读法 | 存储 |
|---|---|---|
| 最新流 | 时间序（DB / 索引） | 帖子主存储 |
| 关注流 | 读自己 inbox（推模式） | Redis ZSet / 内存 |
| 推荐流 | 召回 → 排序 → 下发 | 各召回通道索引 |
| 搜索 | 索引查询 | 倒排 |
| 详情页 | 主存储 + 缓存 | MySQL + Redis |

读路径与写路径解耦：写时广播（fanout/索引），读时各取所需。

## 7. 主流案例

| 平台 | 发帖 → 展示主干 |
|---|---|
| **微博** | 发微博 → MQ → 多路（时间线 fanout、搜索、推荐、热搜聚合）；推拉结合（大V走拉） |
| **抖音** | 发布视频 → 审核 → 多路（推荐索引增量、关注流、搜索、统计）；新视频分钟级进索引 |
| **小红书** | 发布笔记 → 审核/内容理解 → 推荐召回 + 关注流 + 搜索 |

共同点：**发帖后统一进消息总线，下游异步多路消费，写读分离**。

## 8. 对比本项目现状

### 8.1 主干对齐度

| 环节 | 主流架构 | MiniForum 生产模式（`-Pprod`） | MiniForum 内存模式（演示） |
|---|---|---|---|
| 发帖落库 | ✅ | ✅ PostRepository.save | ✅ 同 |
| **统一进 Kafka** | ✅ | ✅ `KafkaPostCreatedProducer` → topic `post-created` | ⚠️ 进程内同步 notify（模拟） |
| Fanout 消费者 | ✅ | ✅ `KafkaPostCreatedConsumer` → `followFeedStore.fanout` | ✅ `InMemoryPostCreatedNotifier` → fanout |
| 推荐冷启消费者 | ✅ | ✅ 消费者 → `trafficPool.notifyCreated`（事件驱动） | ⚠️ 懒加载（NewItemPool 扫描帖子，不走事件） |
| 搜索索引消费者 | ✅ | ❌ 无（搜索是实时全表扫） | ❌ 同 |
| 内容理解/审核 | ✅ | ❌ 无 | ❌ 同 |
| 统计/热搜消费者 | ✅ | ❌ 无（热搜实时聚合） | ❌ 同 |
| 通知消费者 | ✅ | ⚠️ 发帖时同步 notifyMentions | ⚠️ 同 |
| **事务 Outbox** | ✅ | ❌ **未实现**（落库后直接发事件） | ❌ 同 |
| 发帖请求异步返回 | ✅ | ✅（事件异步，Kafka 侧） | ⚠️ 内存同步 fanout（毫秒级可接受） |

### 8.2 差距清单（按优先级）

1. **事务 Outbox**（中）：保证发帖事件必达、不丢。当前"落库后发事件"非原子，生产可用 outbox 表 + 定时 Relayer（或 CDC）补强。
2. **搜索索引消费者**（低-中）：当前搜索实时全表扫，数据量小够用；量上来后改为"事件驱动建索引 + 索引查询"。
3. **更多下游消费者**（低）：审核/内容理解/统计/热搜的消费者化——当前都是读时实时计算，数据量小时无需拆分。
4. **内存模式冷启事件化**（低）：演示模式下 TrafficPool 懒加载而非事件驱动，与生产行为不完全一致（功能等价，口径略异）。

### 8.3 已对齐的（无需改动）

- 发帖 → 事件（PostCreatedEvent）→ Kafka（生产）/ 同步 notify（内存）的**事件驱动主干** ✅
- Fanout 扇出 + 关注流 inbox（推模式）✅
- 生产/内存两条腿（`@Profile` 切换）✅
- 事件负载最小化（PostCreatedEvent 只带必要字段，内容按 id 回源）✅

## 9. 演进路径（每阶段独立可上线）

| 阶段 | 动作 | 收益 |
|---|---|---|
| 0 现状 | 发帖 → 事件 → fanout + 冷启（生产）/ 同步模拟（演示） | 主干已通 |
| 1 事务 Outbox | 发帖事务写 outbox 表 → Relayer 轮询发 Kafka → 标 DONE | 事件必达不丢（生产加固） |
| 2 搜索索引消费者 | 订阅 post-created → 建倒排索引 → 搜索改查索引 | 搜索 O(索引) 而非 O(全表) |
| 3 更多下游 | 内容理解 / 统计 / 热搜 消费者化（量上来再拆） | 写读彻底分离、可独立扩展 |

> 与《推荐系统微服务拆分方案》§9 迁移路径联动：本文的"事件总线 + 下游消费者"正是微服务拆分后各服务（forum-recommend-server / forum-offline-job / 搜索服务）之间的协作方式——跨服务数据共享靠 Kafka 事件，而非共享内存。
