# 第2步：样本生产（1周）

> **一句话核心认知**：**样本是模型的"教材"，教材质量决定模型上限。** 模型结构再先进，喂的样本是错的、偏的、脏的，训练出来的也是错的、偏的、脏的模型。数据科学家 50% 的时间花在样本上，不是模型上。

---

## 1. 核心概念与原理

### 1.1 什么是样本

一个训练样本 = 一条"特征 + 标签"的记录：

```
[特征] user_id=u_10086, item_id=i_9527, scene=feed, position=3,
       用户历史点击序列=[...], item标签=[科技,数码], 当前时间=14:03
[标签] click=1（点击了）
```

**推荐排序本质是二分类问题**：模型学"这个用户会不会点这个物品"。

### 1.2 正样本 vs 负样本

| | 正样本 | 负样本 |
|---|---|---|
| 定义 | 曝光且点击了（行为是正反馈） | 曝光但未点击（行为是负反馈） |
| 数量 | 少（点击率通常 1%~10%） | 多（大部分曝光没人点） |
| 问题 | 稀疏 | 怎么"选"才代表真实负反馈 |

**关键认知：负样本不是"所有没点的曝光"，而是"用户看到了但选择不点"**——这是有讲究的（见 position bias）。

### 1.3 数据闭环里的位置

```
第1步的原始日志（曝光/点击/时长）
        ↓ 本步：对齐、采样、清洗
   训练样本库（正负样本对）
        ↓ 供模型训练（第4步/离线训练）
   模型 → 推荐 → 新曝光 → 新反馈 → 新样本（循环）
```

## 2. 关键技术细节

### 2.1 曝光-点击对齐（核心中的核心）

#### 目标

把"曝光事件"和"点击事件"拼成一条样本：

```
曝光表：request_id=req_7b2c, user_id=u_10086, item_id=i_9527, position=3, ts=14:03:00
点击表：request_id=req_7b2c, user_id=u_10086, item_id=i_9527, position=3, ts=14:03:05
        ↓ join on (request_id, user_id, item_id, position)
样本：user=u_10086, item=i_9527, pos=3, click=1
```

#### 实现方式

| 方式 | 做法 | 适用 |
|------|------|------|
| **离线 join（Hive/Spark）** | T+1 把两张大表 join | 离线训练样本（主流） |
| **实时 join（Flink）** | 曝光先入状态，点击到达后 join | 实时样本回流、实时特征 |
| **服务端直接落样本** | 推荐服务在点击发生时直接写样本 | 简单场景，但特征不全时受限 |

#### join 的细节

1. **时间窗口**：点击必须发生在曝光后的窗口内（如 30 秒内），超过视为无效
2. **点击归属**：一次曝光只有第一次点击算正样本，后续点击可能是"看完了再点"（或按产品定义）
3. **position 必须带上**：同一个 item 在不同位置曝光，点击概率不同（位置偏差，见 2.3）
4. **跨天处理**：晚上 23:59 曝光、00:01 点击，要按 session/时间窗口跨天 join
5. **未匹配的曝光**：曝光了但没点击 → 负样本；点击了但没曝光（如深链进入）→ 丢弃或归为其他

#### 曝光日志是"上帝视角"的数据

> **负样本只来自曝光**：只有"系统推荐过且用户看到的"才有资格当负样本。没曝光过的 item 对用户不是负样本，是"未知"。

### 2.2 负采样

#### 问题

负样本太多（99% 曝光没点击），如果全量用：
- 训练太慢（海量数据）
- 正负比严重失衡（1:100+），模型学成"全部预测负样本"

#### 采样策略

| 策略 | 做法 | 效果 |
|------|------|------|
| **随机负采样** | 按比例随机抽曝光未点击的样本 | 简单，但可能引入噪声 |
| **全局负采样 + 分桶** | 按用户活跃度/item 热度分桶，桶内随机 | 平衡不同群体 |
| **热门 item 降采样** | 热门 item 被抽中时降权（如按 popularity^α 降采样） | 缓解热门偏差（马太效应） |
| **困难负样本** | 模型认为"相关"但用户没点的样本（如粗排高分未点击） | 提升模型区分度 |
| **随机未曝光负采样** | 从全量 item 随机抽（含未曝光的） | 模拟真实推荐空间，缓解"只看曝光"的偏差 |

#### 正负比选择

- 常见比例 1:1 ~ 1:10（CTR 任务常用 1:2~1:5）
- 具体看业务：点击率极低的场景（如广告 0.1%）可以 1:20+
- **离线指标（AUC）会受采样比例影响**，评估时要校正或固定采样率

#### logQ 校正（Batch 内负采样的必配）

双塔训练常用 batch 内负采样（同 batch 其他样本的正样本当你的负样本），此时热门 item 容易被过度打压，要做校正：

```
score = u·v_pos - log(Q_pos) - (u·v_neg - log(Q_neg))
其中 Q = item 在采样分布中的出现概率（近似用 item 热度）
```

**作用**：热门 item 当负样本出现的概率高，如果直接当负样本会教模型"讨厌热门"；减去 logQ 校正后，恢复成"与真实分布一致"。

### 2.3 Position Bias（位置偏差）

#### 问题

**排在前面 = 更容易被看到 = 更容易被点击**，这不是用户真喜欢，是位置带来的偏差。

```
同一 item 在位置 1 曝光点击率 8%，在位置 20 可能只有 1%
→ 模型会学到"位置 1 的都好"，而不是"内容好"
```

#### 消偏方法

| 方法 | 思想 | 落地 |
|------|------|------|
| **position 作为特征** | 把 position 喂给模型，让模型"记住"位置影响 | 最简单，但注意推理时怎么赋值 |
| **Shuffle 实验** | 随机打乱部分流量排序，观察点击率随位置变化 | 测量真实位置偏差曲线 |
| **IPW（Inverse Propensity Weighting）** | 用"被点击的概率"倒数加权，抵消位置偏差 | 理论优美，估计倾向分较复杂 |
| **ESMM / 多任务** | 用"是否点击"和"点击后是否转化"联合建模，位置只影响前者 | 业界常用，还顺带解决样本选择偏差 |
| **训练时随机 position** | 训练样本的 position 随机化 | 简单粗暴，让模型不依赖位置 |

**工程最低要求**：position 必须进特征；有条件就做 Shuffle 实验测量偏差曲线。

### 2.4 多任务样本（多标签）

现代推荐不止优化点击，还优化时长、完播、转化、互动：

```
一条样本可以有多标签：
  click=1, dwell_time=8500ms, video_complete=1,
  like=1, comment=1, purchase=0
```

**多标签样本设计**：不同任务共享特征、各自有标签，训练时用 MMoE 等多目标模型（第6步详述）。

**注意**：不同任务的"负样本"定义不同——点击的负样本是曝光未点击；转化的负样本是"曝光点击但未购买"。逐层漏斗。

### 2.5 样本质量

| 质量维度 | 问题 | 处理 |
|---------|------|------|
| 去重 | 事件重复上报 | 按 event_id 去重 |
| 去噪 | 爬虫/机器行为/异常点击 | 行为序列异常检测、频率限制、IP 黑名单 |
| 时效 | 太久远的样本过时（兴趣变化） | 样本回放窗口（如只取最近 90 天），新样本加权 |
| 快照 | 特征随时间变化（训练时特征≠当时特征） | **特征快照**：样本落库时把当时特征一起存下来（见第3步一致性） |
| 数据泄露 | 用了未来信息（如用明天的点击预测今天的） | 严格按时间切分训练/测试集 |

## 3. 工程落地要点

1. **样本表设计**（Hive 表）：

```sql
CREATE TABLE dwd_sample_click (
  request_id   STRING,      -- 关联链
  user_id      STRING,
  item_id      STRING,
  scene_id     STRING,
  position     INT,
  ts_expose    BIGINT,      -- 曝光时间
  ts_click     BIGINT,      -- 点击时间（未点击为 null）
  label_click  INT,         -- 0/1
  dwell_time   INT,         -- 停留时长
  label_like   INT,
  ...
  feature_json STRING       -- 特征快照（序列化）
) PARTITIONED BY (dt STRING);
```

2. **样本生成流水线**（T+1 为主 + 近线补充）：

```
每日凌晨：
  原始日志(ODS) → 清洗去重 → 曝光表/点击表(DWD)
    → join 对齐 → 负采样 → 多标签 → 特征快照
    → 训练样本(ADS) → 模型训练
近线（分钟级）：
  实时曝光-点击 join → 实时样本 → 增量训练（可选）
```

3. **采样率参数化**：负采样率、正负比做成配置项，方便实验对比
4. **样本可回放**：保留原始日志，重算样本不依赖已生成的样本表
5. **样本监控**：每天样本量、正负比、点击率分布、字段缺失率——异常即告警

## 4. IoT 背景认知补全

### 你的底子能平移什么

| IoT 经验 | 平移到样本生产 |
|---------|--------------|
| 告警→处置→复现的关联分析 | 曝光→点击→转化的漏斗思维，**结构同构** |
| 时序数据对齐（多源数据按时间对齐） | 曝光-点击按时间窗口 join，思路一致 |
| 异常数据清洗（传感器脏数据） | 行为数据去噪去重，直接复用 |
| 数据质量监控 | 样本监控直接复用 |

### 你的认知缺口（重点补）

1. **"负样本"概念是全新的**：IoT 里没有"负样本"——传感器没有"该报障却没报"的标签。C 端负样本需要精心构造，**负样本的质量直接决定模型上限**，这是最需要转变的认知。
2. **数据是有偏的**：IoT 数据是客观的，C 端行为数据自带位置偏差、流行度偏差、样本选择偏差——**消偏是 C 端数据科学家的核心技能**，IoT 里没有对应概念。
3. **正样本稀疏**：IoT 故障样本也稀疏，但那是"事件稀疏"；C 端点击样本虽然绝对量大，但相对曝光是稀疏的（1%~10%），处理思路不同。
4. **特征快照**：IoT 时序数据天然带时间戳可回放；C 端样本必须做特征快照，否则训练/在线特征不一致（第3步详述）。

## 5. 常见坑与避坑

| # | 坑 | 后果 | 避坑 |
|---|-----|------|------|
| 1 | 负样本直接用"全部未点击" | 位置偏差放大，模型学偏 | 只取"曝光且未点击"，position 进特征 |
| 2 | 曝光-点击 join 窗口设太短/太长 | 漏正样本 / 引入噪声 | 按业务定窗口（如 30s），可 A/B 调 |
| 3 | 不消 position bias | 线上效果崩（离线 AUC 虚高） | position 特征 + Shuffle 实验 |
| 4 | 正负比失衡不处理 | 模型倾向全预测多数类 | 负采样控制比例 |
| 5 | 热门 item 负样本过多 | 模型打压热门，推荐变"冷" | logQ 校正 / 热门降采样 |
| 6 | 特征不存快照 | 训练在线不一致，模型线上失效 | 样本落库时存特征快照 |
| 7 | 训练测试集时间混切 | 数据泄露，离线 AUC 虚高 | 严格按时间切分 |
| 8 | 忽略多任务标签 | 只优化点击，时长/转化没优化 | 样本设计多标签 |
