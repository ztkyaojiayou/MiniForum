# 互联网 C 端推荐系统：从认知补全到数据闭环

> 整理自面向电力 IoT 背景开发者的推荐系统认知对话
> 整理时间：2026-08-28
>
> 核心观点：**推荐系统本质是一个大型系统，不是模型，不是纯算法。模型只占 20%，剩下 80% 是数据、工程、实验、监控。**
> 文档按"架构认知 → 模型体系 → 系统全景 → 数据源头 → 生命周期 → 落地路径"六章组织。

## 第一章：典型推荐系统架构与数据流

### 1.1 整体架构分层

```
┌─────────────────────────────────────────────────────┐
│                   前端 / 客户端                         │
│        （双列瀑布流 / 单列信息流 / 详情页相关推荐等）      │
└──────────────────────┬──────────────────────────────┘
                       │ 请求（user_id, context, item_id）
                       ▼
┌─────────────────────────────────────────────────────┐
│                在线服务层（毫秒级响应）                  │
│  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐  │
│  │  召回    │ → │  粗排   │ → │  精排   │ → │  重排   │  │
│  └────────┘   └────────┘   └────────┘   └────────┘  │
│   召回1000+    截断500      精排100     最终30~50     │
└──────────────────────┬──────────────────────────────┘
                       │ 特征请求（实时特征）
                       ▼
┌─────────────────────────────────────────────────────┐
│              近线层（秒~分钟级）                        │
│   实时特征计算 / 实时样本回流 / 模型增量更新 / 缓存刷新    │
└──────────────────────┬──────────────────────────────┘
                       │ 特征数据 / 样本数据
                       ▼
┌─────────────────────────────────────────────────────┐
│              离线层（小时~天级）                        │
│  日志清洗 → 样本生成 → 特征计算 → 模型训练 → 模型评估发布 │
└─────────────────────────────────────────────────────┘
```

### 1.2 多级漏斗：用成本换精度

| 层级 | 输入量 | 输出量 | 职责 | 典型手段 |
|------|--------|--------|------|----------|
| **召回** | 百万~亿级 | 数百~千条 | 快速捞出用户可能感兴趣的 | 双塔向量召回（ANN）、协同过滤、热门/新品兜底、社交关系召回 |
| **粗排** | 千条 | 数百条 | 轻量模型快速粗筛 | 双塔/小型 MLP，批量打分 |
| **精排** | 数百条 | 数十条 | 精细建模用户兴趣 | LR/GBDT/DeepFM/DIN 等多目标模型 |
| **重排** | 数十条 | 最终列表 | 业务约束与体验 | 多样性打散、去重、疲劳控制、商业插帧、MMR |

**关键思想**：越往后模型越强、特征越全，但只对越少的候选生效，保证端到端延迟在百毫秒级。

### 1.3 三层数据流水线

| 层级 | 节奏 | 职责 | 示例 |
|------|------|------|------|
| **离线** | 小时~天 | 能预计算的全预计算 | 模型训练、全量特征、向量索引、统计画像 |
| **近线** | 秒~分钟 | 需要新鲜度但容忍延迟 | 实时特征、样本回流、增量模型更新、热榜 |
| **在线** | 毫秒 | 用户请求链路 | 特征拉取、推理、检索、重排 |

**核心心法（系统设计灵魂）**：

> **把"能离线算的"全放离线，把"必须实时的"留在在线，中间塞一层近线做衔接。**
> 能离线算的放到在线做，QPS 立刻爆；必须实时的放到离线算，效果立刻过期。

这与 IoT 里"边缘计算 vs 云端计算"的分层思维同构——IoT 底子能平移。

## 第二章：双塔召回模型深度拆解

> 召回层最主流的工业级架构。核心思想：**把用户和物品分别编码成向量，用向量相似度代替匹配度。**

### 2.1 为什么需要双塔

召回面对百万~亿级候选，精排模型无法全量逐条计算。双塔的方案：

- **离线**：所有物品预先算好向量、建好索引（重活离线做）
- **在线**：用户实时编码成向量 → ANN 检索 → 毫秒级返回 top-K
- 优雅之处：**物品侧完全离线预计算，在线只做一次用户编码 + 一次向量检索**

### 2.2 网络结构

```
用户特征(uid,历史行为序列,场景...) → User Tower → L2归一化 → user向量u
                                                      ↓
                                              cos(u,v) = 匹配分
                                                      ↓
物品特征(item_id,标签,作者,热度...) → Item Tower → L2归一化 → item向量v
```

**关键点**：
- 两塔可对称可不对称（Item 塔通常更轻）
- 输出向量 L2 归一化 → 内积 = 余弦相似度 → 便于 ANN 检索
- **离线联合训练，上线两塔解耦**（物品塔离线批量出向量，用户塔在线实时出向量）

### 2.3 训练：负采样决定一切

```
loss = -log( σ(u·v_pos) - σ(u·v_neg) )
```

| 负采样方式 | 做法 | 特点 |
|-----------|------|------|
| 随机负采样 | 全量 item 随机抽 | 简单，偏离真实分布 |
| **Batch 内负采样** | 同 batch 其他样本的正样本当负样本 | 工程最常用，近乎免费 |
| 热门降采样 | 热门 item 被抽中时降权 | 缓解热门 bias（类似 word2vec） |
| 困难负样本 | 模型认为"相关但用户不点"的样本 | 提升区分度，注意别太"难" |

> 工程细节：batch 内负采样时对热门 item 做 **logQ 校正**，否则热门 item 被过度打压。

### 2.4 在线检索：ANN

亿级数据精确 KNN 不可行，必须近似最近邻：

| 算法 | 原理 | 特点 |
|------|------|------|
| IVF | 先聚类，只搜最近的几个聚类 | 简单高效，召回率有损 |
| **HNSW** | 分层小世界图逐层下探 | 召回率高、最主流 |
| PQ/OPQ | 向量分块量化 | 内存友好，精度有损 |
| IVF+PQ | 倒排+量化组合 | 亿级场景标配 |

工程要点：多副本+分片（高 QPS）、ANN vs 暴力 KNN 召回率监控、向量+标量过滤（如"只召回 7 天内发布"）。

### 2.5 多路召回与融合（重头戏）

**单路向量召回不够**——会漏掉冷启动（新作者新内容）、时效性（最新热点）、显式兴趣（用户明确想要的东西）。工业界都是多路并发：

```
双塔向量召回(主路)  协同过滤I2I  社交召回  热门召回
标签/关键词召回      新品召回    语义召回   ...
        ↓ 合并 + 去重 + 截断（各路段位配额）
        ↓
     粗排（统一排序）
```

关键点：
1. 各路打分尺度不同，**不能直接比大小** → 每路给固定配额，交粗排统一排序
2. 段位配额动态调整（新用户没行为 → 加大热门/冷启动路配额）
3. 多路曝光比例可控，保证多样性，防止某一路一家独大
4. 双塔可做"多塔"变体：长期兴趣塔/短期兴趣塔/冷启动塔，各自检索再合并

### 2.6 双塔的局限

- **表达能力受限**：交互全靠向量点积，学不到深层交叉 → 解法：双塔召回 + 交互模型精排
- **离线在线不一致**：训练用 softmax/双塔损失，在线用 ANN，打分可能漂移
- **特征时效性**：Item 塔离线计算，物品侧实时动态特征（实时热度）进不了塔，只能靠其他路或精排补偿

## 第三章：电力 IoT 背景 → 互联网 C 端，认知差在哪

> 注意：这里讨论的**不是**"给电力 IoT 做推荐系统"，而是"电力 IoT 开发者转去做互联网 C 端推荐系统"需要补什么。

### 3.1 底子能平移的 60%

- ✅ **高并发/分布式/系统架构** —— 直接迁移
- ✅ **数据管道**（Kafka/Flink/Hive，时序数据比 C 端更多）—— 直接迁移
- ✅ **向量检索**（Milvus 已在用）—— 召回层基础设施现成
- ✅ **系统设计思维**（读写分离、异步解耦、分层）—— 与微博时间线同构
- ✅ **监控告警**（服务监控、延迟监控、数据质量监控）—— 小菜一碟

### 3.2 六个核心认知差（按重要性排序）

**认知差 1：指标体系 —— 从"决策可信"换成"商业增长"**

| IoT 习惯 | C 端要换成 |
|---------|-----------|
| 准确率/误报率 | CTR、CVR、GMV、停留时长、留存 |
| 单目标 | **多目标**（点击+时长+互动+完播+商业化，MMoE） |
| 正确即正义 | 体验 vs 商业的**权衡**（广告加载多伤体验但赚钱） |
| — | 北极星：ROI/GMV/时长，模型只是手段 |

**认知差 2：数据规模与数据工程 —— 亿级不是万级**
- 完整数据管道：埋点 → Kafka → Flink 实时 → Hive/Spark 离线数仓
- 特征平台：实时+离线特征统一服务、版本管理
- 样本生产：曝光-点击如何成对、负样本怎么采、position bias 怎么消
- 高频实时更新（小时级模型/索引重建）——IoT 通常 T+1 都嫌多

**认知差 3：在线架构 —— 漏斗 + 延迟预算**
- 端到端延迟预算：**200ms 内返回**，各级分配（召回 50ms + 精排 100ms + ...）
- 高 QPS：多级缓存、降级、超时熔断、兜底策略
- 召回双塔+ANN、多路融合；重排多样性（MMR/DPP）、EE 探索

**认知差 4：模型体系 —— 从规则到深度学习的完整谱系**

```
LR(可解释) → FM(二阶交叉) → Wide&Deep(记忆+泛化)
→ DeepFM → DIN(注意力,兴趣多样) → DIEN/SIM(行为序列)
→ MMoE(多目标) → 在线学习(实时更新)
```

> 不用全精通：**精排吃透 DeepFM/DIN，召回吃透双塔，其他知道存在即可。**

**认知差 5：AB 实验 —— C 端的"命根子"**
- 离线指标（AUC/GAUC）只是参考，**线上实验才是真理**
- 实验平台：分流、分层（layer）、桶（bucket）、显著性检验
- 要懂：辛普森悖论、实验污染、置信区间、样本量计算
- **没有 AB 实验支撑，模型上线没人批**

**认知差 6：用户与供给侧生态 —— C 端特有的复杂**
- 用户侧：画像、兴趣演化、短期 vs 长期兴趣、新用户冷启动
- 供给侧：内容理解、标签体系、作者/商家生态（IoT 没有"供给激励"概念，全新维度）
- 数据偏差：流行度偏差、马太效应、位置偏差
- EE 权衡：bandit 算法、探索流量配比

### 3.3 一句话总结

> **缺的不是"算法"，是"从模型到系统的完整工程链路 + 商业指标体系 + AB 实验闭环"。算法知识最多占 30%，剩下的全是工程和数据。**

## 第四章：推荐系统的完整子系统全景

```
┌──────────────────────── 业务层 ────────────────────────┐
│ 供给管理(上架/标签/审核) │ 运营工具(人工干预/黑名单)        │
│ 商业化系统(广告/营销，与自然流量争夺)                       │
└────────────────────────┬──────────────────────────────┘
                         ▼
┌────────────────────── 在线服务层（毫秒级）────────────────┐
│ 请求接入 → 召回(多路+ANN) → 粗排 → 精排 → 重排 → 下发      │
│ 缓存 / 降级 / 熔断 / 兜底  ←—— 高QPS下的保命三件套         │
└──────┬──────────────────────────────┬──────────────────┘
       │ 特征请求                        │ 行为回流
       ▼                                ▼
┌───────────────┐              ┌─────────────────────────┐
│  特征平台(实时) │              │   数据层（埋点→管道→数仓）    │
│  KV/向量/Redis │ ◄─────────── │ 埋点 → Kafka → Flink实时 │
└──────┬────────┘              │        → Hive/Spark离线   │
       │                        └───────────┬─────────────┘
       │                        ┌───────────▼─────────────┐
       │                        │ 样本层：曝光-点击对齐       │
       │                        │ 负采样/去偏/样本回放        │
       │                        └───────────┬─────────────┘
       ▼                                    ▼
┌────────────────────── 训练层（离线/近线）─────────────────┐
│ 分布式训练 → 模型评估 → 发布 → 在线学习/增量更新            │
│ 向量索引重建(小时级) → 写向量库                            │
└──────────────────────┬─────────────────────────────────┘
                       ▼
┌────────────────────── 实验与监控层 ──────────────────────┐
│  AB实验平台(分流/分层/显著性) │ 指标监控(CTR/CVR/时长/GMV)  │
│  模型监控(AUC漂移/特征分布漂移) │ 服务监控(延迟/QPS/错误率)  │
└─────────────────────────────────────────────────────────┘
```

**注意：图中只有"召回→精排→重排"三个框是模型相关，其余全是系统。**

### 4.1 哪些能平移，哪些是新大陆

| 平移 ✅ | 新大陆 🆕 |
|--------|-----------|
| 数据管道（Kafka/Flink/Hive） | **埋点与行为日志**（IoT 没有"曝光/点击"概念，这是最大坑） |
| 高并发在线服务 | **样本生产**（曝光-点击对齐、负采样、去偏） |
| 监控告警 | **AB 实验体系**（IoT 一般不做分层实验） |
| 向量检索（Milvus） | **特征平台**（毫秒级拼特征、版本管理） |
| — | **商业化目标**（单目标 → 多目标权衡） |
| — | **供给生态**（内容、商品、作者运营） |

> **排第一的坑是埋点**。见过太多人一上来调模型，结果连像样的样本都没有。**从 IoT 过来，第一件事就该是建埋点规范。** 没有埋点就没有样本，没有样本一切都是空谈。

## 第五章：数据从哪儿来 —— 打破根本误区

### 5.1 核心认知：数据不是采集来的，是自己造的

**推荐系统自己产生自己的训练数据**——这是一个闭环：

```
系统先推荐 → 用户产生行为 → 行为回流成数据 → 训练模型 → 推荐更准 → ...
```

所以冷启动必须"先瞎推"（热门/随机/探索），才能积累数据，"才会推"。**没有曝光，就没有点击；没有点击，就没有样本；没有样本，一切免谈。**

### 5.2 四类数据源头

| 数据 | 从哪儿来 | 谁产生 | 在推荐里干什么 |
|------|---------|--------|--------------|
| **行为数据**（最核心） | 客户端埋点 + 服务端日志 | 用户每一次操作 | 训练样本、特征、画像 —— 燃料 |
| **内容数据** | 用户发帖/商家上架时产生 | 供给侧（用户/商家） | 内容理解、标签、embedding、候选池 |
| **用户数据** | 注册、画像、社交关系 | 用户 + 系统加工 | 冷启动、特征、召回路（关注关系） |
| **上下文数据** | 请求时实时获取 | 系统 | 时间/地点/设备/场景特征 |

### 5.3 行为数据的产生链路

```
用户操作(看/点/滑/停/赞)
 → 客户端埋点SDK(事件+参数)
 → 批量/实时上报
 → Kafka(消息总线)
 → 清洗 → 数仓(Hive离线) / 实时计算(Flink)
 → 特征平台(在线服务) + 样本库(训练)
```

**关键**：行为要关联成一条链——`request_id + item_id + user_id + position`，曝光和点击才能 join 成训练样本。**这是"数据从哪儿来"之后的第一个技术难点。**

## 第六章：微博帖子的完整生命周期

> 用微博这个例子，把"数据从哪儿来"到"数据回流影响推荐"的完整闭环讲透。微博系统是理解"数据从哪儿来"的最佳范本。

### 6.1 全景图

```
发布(写路径) → 自己立刻看到 → 别人通过【时间线/推荐流/搜索】看到
                                            ↓
                              行为回流(曝光/点赞/转发/评论)
                                            ↓
                              热度变化 → 影响下一次被推荐的概率
                                            ↓
                              内容过期/低质 → 衰减出池
```

### 6.2 发布瞬间（写路径）

```
用户点"发送"
 → 发帖服务
 → ① 写入主存储(MySQL/分布式KV)   ← 先落库，保证可用性
 → ② 进 Kafka → 异步消费者开始干活：
     ├─ 审核(文本/图片/视频合规)
     ├─ 内容理解：NLP打标签、CV识别、生成embedding（供向量召回）
     ├─ 建立索引(供搜索) + 写入推荐内容池
     ├─ 写扩散：推送到粉丝收件箱
     └─ 通知：@、转发提醒
```

**核心思想：发布是"写路径"，所有重活异步化**——用户点完发送，200ms 内返回"发送成功"，重活在后台跑。与 IoT"设备上报→异步处理→落库→告警"同构。

### 6.3 自己看到（写后读一致性）

- 客户端乐观更新：发送成功瞬间，本地把帖子插到时间线顶部
- 服务端：自己的帖子写入**自己的收件箱**（自己也是自己的粉丝）
- 一致性等级按用户身份分级：**自己的帖子必须立即可见，别人的可容忍几秒延迟**

### 6.4 别人看到：写扩散 vs 读扩散（微博系统的灵魂权衡）

| | 写扩散（Push/Fanout-on-write） | 读扩散（Pull/Fanout-on-read） |
|---|---|---|
| 时机 | 发帖时推送给所有粉丝收件箱 | 刷新时拉取所有关注者帖子再合并 |
| 读延迟 | 极低（直接读自己的收件箱） | 较高（要实时合并+排序） |
| 写放大 | 高（大V发帖=写爆炸） | 低（写一次就完事） |
| 典型问题 | "名人问题"（李佳琦发一条，推送千万条） | "读放大"（每个粉丝刷一次拉一次） |
| 适用 | 普通用户（粉丝少，推送便宜） | 大V（粉丝多，不能推送） |

**工业界标准答案：混合模式**

```
普通用户发帖 → 写扩散：推给粉丝收件箱
大V发帖     → 不推送，只写主存储
粉丝刷新    → 读自己收件箱(写扩散结果) + 实时拉取关注的大V新帖，合并排序
```

> 微博早期纯写扩散（明星发帖服务器会抖），后来演进成混合。**这个读写权衡思想，在 IoT 里见过：边缘设备数据是推上来还是拉下去。**

### 6.5 被推荐看到（推荐系统的完整注入点）

**时间线和推荐流是两套系统**：
- 时间线靠**社交关系**（我关注了你 → 你的帖进我时间线）
- 推荐流靠**兴趣匹配**（我不认识你 → 但模型觉得我会喜欢）

```
帖子写入推荐内容池(带时效/质量/标签)
 → 多路召回：兴趣向量/社交/热门/时效
 → 精排：CTR/互动率/完播多目标打分
 → 重排：多样性打散、去重
 → 下发到推荐流
```

### 6.6 行为回流与衰减（生命周期后半段）

```
曝光 → 点赞/转发/评论/举报
 → 行为回流 Kafka → 实时热度计算(Flink)
 → 热度特征更新 → 推荐权重上升 → 滚雪球（马太效应）
  ↓ 反面
 → 曝光高但互动差 → 模型打压 → 天然衰减
 → 时效衰减（热点帖几小时后权重暴跌）
 → 被举报/低质 → 人工/模型干预 → 下架
```

**一条帖子从出生到死亡，全程被数据驱动**：发布时靠内容数据起步，之后每一步靠行为数据修正。这就是推荐系统里供给侧的生命周期管理。

## 第七章：完整数据闭环（终极答案）

```
【供给侧】用户发帖 → 内容数据(文本/图片/标签/embedding) → 内容池
                                        │
【分发侧】推荐流: 召回→排序→下发 = 产生【曝光数据】★★★
         时间线: 写扩散/读扩散 = 也产生【曝光数据】
                                        │
【用户侧】用户看到曝光 → 点击/点赞/评论/停留 = 产生【行为数据】★★★
                                        │
【数据层】曝光+行为 join 成样本 → Kafka → 数仓/实时计算
                                        │
【回流】 特征更新 + 模型训练 + 热度重算
          → 影响下一次召回/排序/推荐
          → 又产生新的曝光 → 闭环 ♻️
```

> **数据来自"分发→反馈"的循环本身。没有分发就没有数据，没有数据就没有更好的分发。** 所以：
> - 埋点是数据源头的最前端（采集）
> - 曝光日志是推荐系统自己种的因（产生）
> - 反馈回流让系统自我进化（闭环）

## 第八章：学习路径建议（按系统模块打通，别按算法书顺序）

```
第1步：埋点 + 数据管道（地基，2周）
  事件模型(曝光/点击/时长)、日志格式、Kafka Topic 划分、Flink 实时指标
第2步：样本生产（1周）
  曝光-点击对齐、负采样、去偏 —— "数据科学家"的看家本领
第3步：特征平台（1~2周）
  离线/实时/请求时特征三分法，特征服务设计
第4步：在线链路（1~2周）
  召回(双塔+ANN) → 粗排 → 精排(DeepFM/DIN) → 重排(MMR)
  重点在延迟预算和降级策略，模型会用就行
第5步：AB实验 + 监控（1周）
  分流分层、显著性检验、指标监控、模型监控
第6步：业务闭环
  商业化目标、供给运营、冷启动 —— 回到业务看系统
```

## 附：核心结论一览

| # | 结论 |
|---|------|
| 1 | **推荐系统本质是大型系统，不是模型**。模型只占 20%，80% 是数据、工程、实验、监控 |
| 2 | 架构灵魂是**三分法**：能离线算的放离线，必须实时的留在线，中间塞近线衔接 |
| 3 | 排序链路是**多级漏斗**：召回→粗排→精排→重排，用成本换精度 |
| 4 | 双塔召回的命门是**负采样**，落地靠 **ANN（HNSW）+ 多路召回融合** |
| 5 | 数据不是采集来的，是**推荐系统自己造出来的**（闭环：分发→反馈→进化） |
| 6 | 微博生命周期示范了**写路径异步化 + 读写扩散混合 + 推荐独立成系统** |
| 7 | IoT 背景可平移 60%（架构/数据管道/监控/向量检索）；最大坑是**埋点**，其次是样本生产、AB 实验 |
| 8 | 评估体系从"决策可信"换成"商业增长"：CTR/CVR/GMV/时长 + **AB 实验才有话语权** |
