# 第3步：特征平台（1~2周）

> **一句话核心认知**：**特征平台是推荐系统的"供水系统"，承上启下**——上接样本（第2步），下接在线链路（第4步）。没有统一、一致、低延迟的特征服务，模型再强也跑不起来。

---

## 1. 核心概念与原理

### 1.1 为什么需要特征平台

特征在推荐系统里无处不在：
- **训练时**：样本需要特征（第2步的特征快照）
- **在线时**：请求来了要实时拼特征喂模型
- **召回时**：向量检索需要 item embedding（也是特征的一种）

如果每个环节各自造特征、各自存，会出现：**训练和在线特征不一致 → 模型线上失效**。特征平台就是统一管理"特征的产生、存储、服务"的中间层。

### 1.2 特征平台全景

```
特征生产（三种方式，见2.2）
   ├─ 离线批算（T+1）：用户画像、item 统计特征
   ├─ 实时流算（秒级）：近 5 分钟行为聚合
   └─ 请求时计算：实时拉取/现场算（如实时热度）
        ↓
特征存储（见2.3）
   ├─ Hive/数仓（离线特征）
   ├─ Redis/内存（在线热数据）
   └─ 向量库 Milvus（embedding，召回用）
        ↓
特征服务（见2.4）
   └─ 统一 API：get_features(user_id, item_id, context) → 特征向量
        ↓
   ├─ 在线链路消费（召回/排序特征）
   └─ 离线样本回填（训练样本特征）
```

## 2. 关键技术细节

### 2.1 特征三大类

| 类别 | 含义 | 例子 | 时效 |
|------|------|------|------|
| **用户特征** | 描述用户 | 年龄、性别、活跃度、兴趣标签、历史点击序列、近期行为统计 | 长期画像慢变，短期行为快变 |
| **物品特征** | 描述物品 | 内容标签、作者、热度、发布时间、质量分、embedding | 静态部分慢变，热度快变 |
| **上下文特征** | 描述场景 | 时间（小时/星期/节假日）、位置、设备、网络、场景 | 请求时实时 |

**按特征来源再分**：

| 特征 | 例子 |
|------|------|
| ID 类 | user_id、item_id、author_id（映射成 embedding） |
| 统计类 | 用户近 7 天点击数、item 近 24h 曝光量 |
| 序列类 | 用户最近点击的 50 个 item（喂 DIN 等序列模型） |
| 交叉类 | 用户兴趣标签 ∩ item 标签的匹配度 |
| 实时类 | 用户最近 5 分钟浏览的 item 数 |

### 2.2 三种生产方式（特征三分法）

这是特征平台的骨架，和系统架构的"离线/近线/在线"三分法一一对应：

| 生产方式 | 计算时机 | 延迟 | 适用特征 | 技术 |
|---------|---------|------|---------|------|
| **离线批算** | 每天/小时跑批 | 小时~天 | 用户画像、item 统计、长期兴趣 | Hive/Spark 定时任务 |
| **实时流算** | 事件到达即算 | 秒~分钟 | 近 5 分钟行为、实时热度、实时 CTR | Flink 窗口计算 |
| **请求时计算** | 用户请求到达 | 毫秒 | 实时上下文（当前时间/位置）、组合特征 | 在线服务直接算/查 |

**原则（系统设计灵魂）**：
> **能离线算的放离线，能近线算的放近线，只有必须实时的才在线算。**
> 在线算得越少，延迟越低、成本越低。

#### 一个特征的完整例子

```
"用户近7天点击的科技类item数"：
  离线：每天凌晨跑 Hive，算昨天为止近7天的统计 → 存 Redis（key: user_7d_click_cat_tech）
  近线：Flink 实时累加今天新增点击 → 增量更新 Redis
  请求时：在线直接读 Redis key（一次 GET，毫秒级）
```

**大多数统计特征都是"离线算基准 + 实时增量修正"的组合**，这是工程标配。

### 2.3 特征存储

| 存储 | 放什么 | 特点 | 选型考虑 |
|------|--------|------|---------|
| **Hive/数仓** | 全量离线特征、特征历史 | 容量大、可回溯 | 离线训练特征回填 |
| **Redis** | 在线特征（用户/物品/统计） | 读快（毫秒）、量大 | 在线取特征主存储，注意内存成本 |
| **向量库（Milvus/Faiss）** | item embedding、user embedding | ANN 检索 | 召回层专用（第4步详述） |
| **本地缓存** | 热门 item 特征、热点用户特征 | 最快 | 高 QPS 场景的 L1 缓存 |

**Redis 的 key 设计**（在线特征）：

```
user:<user_id>:profile          # 用户画像（哈希）
user:<user_id>:recent_click     # 近期点击序列（列表/串）
item:<item_id>:static           # 物品静态特征（哈希）
item:<item_id>:hot              # 物品实时热度
item:<item_id>:embedding        # 物品向量
ctx:time                        # 全局时间上下文
```

**注意**：在线特征全放 Redis 内存很贵，要做**分级缓存**——全量在 Hive，热数据在 Redis，更热的在本地。

### 2.4 特征服务设计

#### 统一取特征 API

```java
// 伪代码：在线排序服务取特征
FeatureVector feats = featureService.getFeatures(
    FeatureRequest.builder()
        .userId("u_10086")
        .itemIds(List.of("i_9527", "i_9528", "i_9529"))
        .context(new Context("feed", 14, 3, "wifi"))
        .build()
);
// 返回：每个 item 拼好的一行特征（与训练样本的特征顺序一致！）
```

**核心要求**：
1. **批量取**：一次请求取 N 个 item 的特征（减少 RPC）
2. **特征顺序稳定**：训练和在线必须用同一个特征列表（顺序不能变！）
3. **版本管理**：特征上线/下线要有版本号，特征版本和模型版本绑定
4. **超时与降级**：特征服务超时（如 10ms）返回默认值/缓存值，不能阻塞主链路
5. **缺失兜底**：特征缺失给默认值（如均值、0、特殊 embedding），并记录缺失率

#### 特征版本管理

```
特征版本 v3.2：
  - 新增特征：user_7d_tech_click_cnt（离线+实时增量）
  - 下线特征：user_old_interest（已被替代）
  - 训练样本的 features 用 v3.2 生成
  - 在线服务按模型绑定的特征版本取特征
```

**为什么重要**：模型在 v3.2 特征上训练，在线必须用 v3.2 取特征，否则"训练特征 ≠ 在线特征"，模型直接失效。

### 2.5 训练/在线一致性（最隐蔽也最致命）

| 不一致来源 | 说明 | 后果 | 解决 |
|-----------|------|------|------|
| **特征时点不同** | 训练用 T 时刻特征，在线取的是 T' 时刻 | 特征漂移 | 样本存**特征快照**（第2步） |
| **特征值不同** | 统计口径训练/在线不一致 | 模型拿到不同输入 | 同一份特征定义代码生成训练/在线特征 |
| **特征版本不同** | 模型绑定 v3.2，在线用 v3.3 | 输入空间变了 | 版本强绑定，发布走流程 |
| **缺失处理不同** | 训练用均值填充，在线用 0 | 分布变了 | 训练在线用同一填充逻辑 |

**黄金法则**：**训练时模型看到什么特征，在线时也必须看到一模一样的特征。** 实现手段就是"一份特征定义（配置文件/代码），训练在线共用"。

### 2.6 特征监控

| 监控项 | 指标 | 告警阈值示例 |
|--------|------|-------------|
| **分布漂移** | PSI（Population Stability Index） | PSI > 0.25 告警 |
| 缺失率 | 每个特征缺失比例 | 缺失率 > 5% 告警 |
| 延迟 | 特征服务 P99 延迟 | P99 > 20ms 告警 |
| 新鲜度 | 实时特征更新时间 | 超过 5 分钟未更新告警 |
| 覆盖率 | 用户/物品特征可查比例 | 覆盖率 < 95% 告警 |
| 命中率 | Redis 缓存命中率 | 命中率 < 90% 告警 |

**PSI 解释**：衡量特征分布相对基准的偏移程度，`PSI < 0.1` 无漂移，`0.1~0.25` 轻度，`>0.25` 显著漂移（业务变化或数据问题）。

## 3. 工程落地要点

1. **先定特征清单再建平台**：特征清单 = 特征名 + 定义 + 生产方式 + 存储位置 + 服务接口，是团队的公共契约
2. **特征生成代码训练在线共用**：一个特征定义文件，训练和在线都从它生成代码，从源头杜绝不一致
3. **分阶段实施**：
   - 阶段1：离线特征 + 简单 Redis 缓存 + 统一 API（先用起来）
   - 阶段2：加实时流特征（Flink 增量）
   - 阶段3：加特征版本管理 + 完整监控
4. **控制 Redis 内存成本**：热门 item/用户才缓存，冷数据回源 Hive
5. **特征上线流程**：新增特征 → 离线跑通 → 在线接入 → 灰度 → 全量，每一步有验证

## 4. IoT 背景认知补全

### 你的底子能平移什么

| IoT 经验 | 平移到特征平台 |
|---------|--------------|
| 设备属性/遥测数据管理 | ≈ 物品特征（设备=item，属性/遥测=物品特征） |
| 时序数据窗口统计 | 直接复用：均值/方差/趋势/突变点 → 物品实时特征 |
| Redis/缓存架构 | 直接复用 |
| Flink 实时计算 | 直接复用（实时特征生产） |

### 你的认知缺口（重点补）

1. **"用户行为特征"维度是全新的**：IoT 里你只有设备（物品侧）数据，C 端多了"用户"这个维度——用户画像、行为序列、兴趣演化，这是特征里信息量最大也最复杂的部分。
2. **"请求时上下文"是全新的**：IoT 场景固定（设备上报），C 端每个请求都有实时上下文（时间/位置/场景），这些特征只在请求时才有。
3. **训练/在线一致性**：IoT 训练和推理都是模型侧的事，没有"特征平台"概念；C 端特征跨训练和在线，一致性是必答题不是加分题。
4. **特征版本管理**：IoT 模型升级只管模型；C 端特征升级要管"特征版本 × 模型版本"的绑定关系。

## 5. 常见坑与避坑

| # | 坑 | 后果 | 避坑 |
|---|-----|------|------|
| 1 | 训练在线特征不一致 | 模型线上 AUC 崩 | 特征定义一份代码共用 + 特征快照 |
| 2 | 特征顺序变了 | 模型输入错位，静默失效 | 特征列表版本化、强校验 |
| 3 | 特征缺失处理不一致 | 分布漂移 | 训练在线统一填充逻辑 |
| 4 | 在线特征全放 Redis | 内存爆炸、成本失控 | 分级缓存（Hive→Redis→本地） |
| 5 | 特征服务超时阻塞主链路 | 推荐接口超时 | 超时/降级/默认值，绝不阻塞 |
| 6 | 实时特征不监控新鲜度 | 数据停了没人知道 | 新鲜度监控 + 告警 |
| 7 | 特征版本没和模型绑定 | 线上用错特征版本 | 版本强绑定，发布走流程 |
| 8 | 所有特征都在线算 | 延迟飙升 | 坚持"离线/近线/在线"三分法 |
