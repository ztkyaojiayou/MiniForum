# 第1步：埋点 + 数据管道（地基 · 2周）

> **一句话核心认知**：**没有曝光就没有点击，没有点击就没有样本，没有样本一切免谈。**
> 推荐系统的数据不是"采集"来的，是"自己造"出来的——系统先推荐产生曝光，用户行为产生反馈，反馈回流成数据，数据训练模型让推荐更准。埋点就是这条循环最源头的闸门。

---

## 1. 核心概念与原理

### 1.1 数据从哪儿来（回顾）

推荐系统的训练数据来自一个闭环：

```
系统先推荐 → 产生曝光 → 用户点击/点赞/停留 → 行为回流成数据
    → 训练模型 → 推荐更准 → 新的曝光 → ...
```

冷启动必须"先瞎推"（热门/随机/探索），才能积累数据，"才会推"。**埋点系统就是采集这个闭环中所有行为数据的工具。**

### 1.2 四类数据源头

| 数据 | 从哪儿来 | 在推荐里干什么 |
|------|---------|--------------|
| **行为数据**（最核心） | 客户端埋点 + 服务端日志 | 训练样本、特征、画像 —— 燃料 |
| **内容数据** | 用户发帖/商家上架 | 内容理解、标签、embedding、候选池 |
| **用户数据** | 注册、画像、社交关系 | 冷启动、特征、召回路 |
| **上下文数据** | 请求时实时获取 | 时间/地点/设备/场景特征 |

本步聚焦**行为数据**的完整链路。

## 2. 关键技术细节

### 2.1 事件模型设计

#### 事件四要素（WHO / WHAT / WHEN / WHERE）

一个行为事件必须回答四个问题：

| 要素 | 字段 | 示例 |
|------|------|------|
| WHO（谁） | user_id、device_id、session_id | `u_10086` |
| WHAT（做了什么） | event_type、target_id（item_id/uid） | `click`、`i_9527` |
| WHEN（何时） | timestamp（客户端+服务端两个时间戳） | `2026-08-28 14:03:22.123` |
| WHERE（在哪） | scene_id（场景）、page_id、position | `feed_recommend`、`p_3`、`pos_7` |

#### 场景（scene_id）是必须的

同一个行为在不同场景意义不同：
- `scene_id=feed`：信息流推荐
- `scene_id=search`：搜索
- `scene_id=detail`：详情页相关推荐
- `scene_id=hot`：热榜

**不同场景的样本要分开训练或加场景特征**，混在一起会污染。

#### 事件类型体系（建议的公共分类）

```
曝光类：item_expose（单条曝光）、feed_expose（整页曝光）
行为类：click、long_click（长按）、like（点赞）、favorite（收藏）
       comment（评论）、share（分享）、follow（关注）
消费类：video_start、video_end、video_progress（播放进度）、
       dwell_time（停留时长）、read_depth（阅读深度）
转化类：purchase（购买）、order（下单）、install（安装）
负向类：dislike（不感兴趣）、report（举报）、hide（屏蔽）、unfollow
```

**时长类事件是重点**：停留时长、完播率是比点击更深层的兴趣信号，很多产品把"有效阅读/完播"作为核心优化目标。

#### 曝光事件 vs 点击事件的关联链（本步最关键）

一个用户行为链必须有四元组关联，否则无法拼样本：

```
request_id（一次推荐请求的唯一ID）   ← 一次请求
item_id（推荐了哪条内容）            ← 推荐了什么
user_id（推荐给了谁）                ← 给谁推的
position（第几位/第几屏）             ← 在哪推的
```

**只有这四元组齐全，曝光和点击才能 join 成训练样本**（见第2步）。埋点设计时必须在事件里透传 `request_id`——很多系统第一个坑就是这里断了。

### 2.2 日志格式规范

#### 推荐：JSON 或 Protobuf + JSON 双写

- **客户端上报**：用 JSON（可读、SDK 友好）
- **服务端到 Kafka**：用 Protobuf（压缩率高、schema 强约束）
- **数仓落盘**：转 Parquet/ORC（列式存储）

#### 日志字段分层

```json
{
  "common": {                          // 公共字段（所有事件都有）
    "event_id": "evt_8f3a...",         // 全局唯一事件ID（去重用）
    "event_type": "click",             // 事件类型
    "request_id": "req_7b2c...",       // 推荐请求ID（关联链关键）
    "user_id": "u_10086",              // 用户ID
    "device_id": "d_8848",             // 设备ID
    "session_id": "s_1234",            // 会话ID
    "scene_id": "feed",                // 场景
    "page_id": "p_3",                  // 页面
    "ts_client": 1756368203123,        // 客户端时间戳(ms)
    "ts_server": 1756368203265,        // 服务端时间戳(ms)
    "app_ver": "8.2.1",                // App版本
    "os": "android_14",                // 操作系统
    "network": "wifi"                  // 网络环境
  },
  "extra": {                           // 业务字段（按事件类型扩展）
    "item_id": "i_9527",
    "position": 7,
    "source": "recommend",             // 内容来源：推荐/关注/搜索
    "duration_ms": 8500                // 停留时长（消费类事件）
  }
}
```

**设计原则**：公共字段模板化（SDK 自动填充），业务字段按事件类型定义 schema，用 Protobuf 强约束防止字段漂移。

### 2.3 埋点 SDK 设计要点

| 能力 | 说明 | 为什么重要 |
|------|------|-----------|
| **本地缓存** | 事件先写本地（内存/磁盘），定期批量上报 | 防止频繁网络请求、弱网不丢 |
| **批量上报** | 攒 N 条或 T 秒后一次性上报 | 降低服务端压力 |
| **重试机制** | 上报失败指数退避重试 | 防止数据丢失 |
| **采样** | 高流量事件按比例采样（如 10%） | 控制成本（但注意采样要可恢复） |
| **崩溃兜底** | App 崩溃时把未上报日志补传 | 防止关键数据丢失 |
| **数据校验** | SDK 侧做基础字段校验 | 垃圾进垃圾出 |

**采样要慎重**：曝光/点击这类核心事件建议全量采集（它们直接决定样本质量），只有低频高噪声事件（如页面滚动）才采样。

### 2.4 服务端日志 vs 客户端日志

| | 客户端埋点 | 服务端日志 |
|---|---|---|
| 采集点 | App SDK | 推荐/内容服务端 |
| 优点 | 能采到交互细节（滑动、长按、停留） | **数据可信（曝光=实际下发的）**、无客户端造假 |
| 缺点 | 可被篡改/丢失、上报延迟 | 只能看到"下发"看不到"真实浏览" |

**工业界做法：两者结合 + 客户端只记录"实际曝光"**：
- 推荐服务端下发内容时记一条**下发日志**（可作为"曝光基线"）
- 客户端真正渲染到屏幕上时上报**曝光事件**（用户真实看到的）
- 两者用 `request_id + item_id` 关联，可发现"下发了但没渲染"的差异

> **为什么服务端下发日志更可信**：客户端可能被作弊（刷量）、可能没渲染（划太快）、可能上报延迟。服务端日志是"系统自己说了什么"，客户端日志是"用户实际看到什么"，两者对不上就是数据质量问题。

### 2.5 Kafka Topic 划分

#### 按事件类型分 Topic（推荐）

```
# 原始层（raw）
raw_event_all            # 全量原始事件（兜底，可重放）

# 按事件类型分（方便消费方订阅）
event_item_expose        # 曝光事件
event_click              # 点击事件
event_like               # 点赞事件
event_dwell              # 停留/消费事件
event_purchase           # 转化事件

# 业务加工层（清洗后）
sample_expose_click      # 曝光-点击配对样本流（第2步产物）
feature_realtime         # 实时特征流（第3步产物）
```

#### Topic 设计原则

1. **原始层和生产层分开**：raw 层保留全量可重放，业务层是加工产物，互不污染
2. **分区键（partition key）选择**：按 `user_id` 哈希分区 → 同一用户的事件进同一分区，保证顺序、便于 join
3. **分区数规划**：按峰值 QPS 和消费并行度估算，一般为消费组消费者数的 2~3 倍
4. **保留期**：raw 层保留 7~30 天（可回溯重算），业务层保留 3~7 天（消费完即弃）

#### 事件上报链路

```
客户端 SDK ──批量上报──> 采集网关(nginx/接入服务)
                          │
                    解析/校验/格式转换
                          │
                     Kafka（原始 Topic）
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
   Flink 实时清洗       Hive 离线落盘       Flink 实时指标
   (转 Protobuf)        (ODS 层)            (DWS 层)
```

### 2.6 Flink 实时指标

#### 典型实时计算任务

| 任务 | 计算内容 | 用途 |
|------|---------|------|
| 实时 CTR/PV/UV | 滑动窗口统计曝光、点击 | 业务监控、热榜 |
| 实时热度榜 | 窗口内互动量加权排序 | 热门召回（时效性） |
| 实时特征 | 用户最近 5 分钟行为聚合 | 近线特征（第3步） |
| 实时样本回流 | 曝光-点击 join 后即时入库 | 缩短训练周期 |

#### 窗口计算示例（伪代码）

```
// 每 5 分钟统计一次每个 item 的曝光/点击/CTR
DataStream<Event> events = kafkaSource("event_click", "event_item_expose");

events
  .keyBy(e -> e.itemId)
  .window(TumblingProcessingTimeWindows.of(Time.minutes(5)))
  .aggregate(new CountAgg(), new ItemCtrWindow())
  .map(w -> new HotItem(w.itemId, w.pv, w.click, w.ctr))
  .sinkTo(redisSink);   // 写 Redis 供在线读取
```

#### 乱序处理（水位线 Watermark）

客户端时间戳可能乱序到达（网络延迟、批量上报），必须处理：

```
events.assignTimestampsAndWatermarks(
    WatermarkStrategy.<Event>forBoundedOutOfOrderness(Duration.ofSeconds(10))
        .withTimestampAssigner((e, ts) -> e.tsClient)
);
```

**不处理乱序的后果**：窗口统计不准、实时特征错位、样本 join 漏对。

### 2.7 数仓分层

```
ODS（原始数据层）   raw_event_all → 按天分区落盘 Parquet
        │ 清洗、去重、字段标准化
DWD（明细层）       dwd_event_detail（明细大宽表，含公共字段）
        │ 聚合
DWS（汇总层）       dws_item_daily（item 日粒度指标）
                   dws_user_daily（user 日粒度指标）
        │ 业务应用
ADS（应用层）       样本表、特征表、报表（直接供训练/查询）
```

**关键**：ODS 保留原始事件，DWD 做关联和标准化，DWS 做聚合，ADS 直接服务业务。分层的目的：**职责分离、可回溯、可重算**。

## 3. 工程落地要点

1. **先定事件规范再写代码**：事件字典（Event Dictionary）是团队的公共契约，用 Protobuf schema + 文档维护，变更走评审
2. **request_id 全链路透传**：客户端请求头、服务端日志、Kafka 消息、样本表，一路带到底——这是最容易断的地方
3. **双时间戳**：客户端 ts_client + 服务端 ts_server，可算网络延迟，也可识别客户端时钟异常
4. **上报链路加监控**：采集成功率、Kafka 消费积压（lag）、写入数仓行数，任何一环断了要能立刻发现
5. **先全量后采样**：核心事件先全量采集跑通，再评估成本决定是否采样
6. **数据回填能力**：raw 层保留足够久，算法迭代需要重算样本/特征时能回放

## 4. IoT 背景认知补全

### 你的底子能平移什么

| IoT 经验 | 平移到 C 端推荐 |
|---------|----------------|
| 设备上报链路（设备→网关→消息队列→落库） | 客户端埋点 → 采集网关 → Kafka → 数仓，**结构完全同构** |
| Kafka/Flink/Hive 数据管道 | 直接复用，时序数据你玩得比 C 端狠 |
| 数据质量监控（丢包、延迟、乱序） | 直接复用，水位线/乱序处理和 IoT 一致 |
| 设备 ID/会话管理 | 换成 user_id/device_id/session_id，思路一样 |

### 你的认知缺口（重点补）

1. **"事件语义"是全新的**：IoT 里数据是客观采集的（传感器读数），C 端里**"用户看到了什么"是系统自己决定并记录**的。曝光日志 = 推荐系统自己种的因，这个心智转换是第一步。
2. **request_id 关联链是全新的**：IoT 里设备数据天然带设备 ID 和时间，不需要"请求级关联"；C 端必须靠 request_id 把"一次推荐请求"和"后续所有行为"串起来。
3. **埋点 SDK 是全新的**：IoT 是服务端采集为主，C 端是客户端采集为主——客户端不可信、会丢、会被篡改，要多一套校验和兜底。
4. **数据是"有偏"的**：IoT 数据代表客观世界，C 端行为数据天然带位置偏差、流行度偏差（第2步详述），处理偏差是推荐特有的课题。

## 5. 常见坑与避坑

| # | 坑 | 后果 | 避坑 |
|---|-----|------|------|
| 1 | **request_id 没透传** | 曝光和点击对不上，样本全废 | 全链路强制透传，日志里必须有 |
| 2 | 只埋客户端不埋服务端 | 数据可造假、丢失无感知 | 客户端+服务端双采集，交叉校验 |
| 3 | 事件类型随意扩展 | schema 漂移、字段语义混乱 | Protobuf 强约束 + 事件字典评审 |
| 4 | 不处理乱序 | 窗口统计错、特征错位 | Watermark + 允许乱序窗口 |
| 5 | 核心事件也采样 | 样本量不足、小流量场景失真 | 核心事件全量，噪声事件才采样 |
| 6 | 没存 raw 层 | 想重算样本/特征时无源可用 | raw 保留 7~30 天，可回放 |
| 7 | 客户端时钟不准 | 时间戳错乱影响窗口和 join | 双时间戳 + 服务端校准 |
| 8 | 忽略场景区分 | 不同场景行为混训，模型互相污染 | scene_id 必填，样本按场景切分 |
