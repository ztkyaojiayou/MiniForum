# 容量测试方法（P3-4 全链路压测 · 先摸清单机再谈扩容）

> 创建：2026-08-28
> 主题：怎么用 `scripts/loadtest_feed.py` 给本项目做容量测试——**漏斗分层测、每层测什么、怎么算扩容**。
> 核心口诀：**先压测摸容量，再谈优化**（阿里双11 全链路压测方法论）；扩容公式 **机器数 = 峰值 QPS ÷ 单机 QPS**，前提是"先摸清单机容量"。
> 配套：`scripts/loadtest_feed.py`（压测脚本）、`docs/高并发优化落地清单-带优先级.md`（P3-4）、`docs/限流与熔断-分布式治理概念澄清.md`（漏斗分层）。

---

## 0. 一句话全貌

```
一份压测脚本 + 一个分层思考框架：
  请求 → 入口限流 → Tomcat 线程池 → RecommendService → 缓存层 → 推荐漏斗 → 仓库
  每一层都可能先到瓶颈 → 压测的目的就是找到"哪一层最先顶不住"，而不是只看整体 QPS 数字
```

---

## 1. 压的是什么：流量漏斗分层

```
客户端 → ① 入口限流（RateLimitFilter 滑动窗口，IP 粒度）
       → ② Tomcat 线程池（max-threads=200 / accept-count=200）
       → ③ RecommendService（Sentinel：QPS 限流 + 异常比例熔断）
       → ④ 缓存层（画像/物品特征/热门/热搜/单帖 本地 TtlCache）
       → ⑤ 推荐漏斗（召回 6 路 → 排序 → 重排 → 冷启动）
       → ⑥ 仓库（内存仓库 / prod: MySQL+Redis+ClickHouse）
```

每层都有自己的容量上限，瓶颈一般出现在**最贵的那层**（⑤⑥）。压测不是"整体打 10000 QPS 看挂不挂"，而是**逐层定位**。

### 测什么（每层对应指标）

| 层 | 关键指标 | 怎么观测 | 到瓶颈的迹象 |
|---|---|---|---|
| ① 入口限流 | 429 命中率 | 压测脚本 `--expect-status 429` | 达到 limit-per-window（100/60s/IP）即 429 |
| ② Tomcat 线程池 | 活跃线程 / 队列 | Spring Boot Actuator metrics / `threads.busy` | 线程占满 → 新请求排队 → RT 飙升（不是 QPS 升） |
| ③ Sentinel | 阻断数（BlockException） | 日志 WARN "推荐入口被 Sentinel 限流/熔断" | flow-qps 触发 → 全部降级热门 |
| ④ 缓存 | 命中率 / 回源 QPS | `topHotCache`/`postCache` 命中日志 | 缓存 miss 激增 → 回源打爆仓库 |
| ⑤ 漏斗 | **单机 QPS / P99** | 压测脚本输出 | P99 抬升到不可接受（>200ms）|
| ⑥ 仓库 | 连接数 / 慢查询 | prod: MySQL 慢日志 / HikariCP 池水位 | 连接耗尽 → 请求堆积（见《分布式系统四件套》§2.6） |

> **核心产出**：单机 QPS（压力下 P99 仍可接受的吞吐上限）+ 瓶颈层。这两个数决定扩容与调参方向。

---

## 2. 怎么压：脚本用法

```bash
# 1. 起演示服务（内存仓库，零中间件）——压测不需要启动任何中间件
./scripts/start.bat          # 或 start.sh；默认 8090 端口

# 2. 基础容量测试：50 会话 / 20 并发 / 2000 请求 / 100 预热
python scripts/loadtest_feed.py \
  --base-url http://localhost:8090 \
  --users 50 --concurrency 20 --total-requests 2000 --warmup 100

# 3. 结果落盘（记录模板自动生成）
python scripts/loadtest_feed.py --users 30 --total-requests 1500 --out results.json
```

**⚠️ 关键前置**：压"推荐漏斗"前先把 `app.rec.rate-limit.enabled` 设为 **false**——否则入口限流（100 请求/60s/IP）先把同一客户端 IP 打 429，你测的是限流而不是漏斗。压"限流本身"时再开回来，用 `--expect-status 429` 断言。

### 脚本输出怎么看

```
总请求 2000，耗时 12.34s，QPS ≈ 162.1
期望状态 200 命中 1980，其它状态 {'429': 20}，连接错误 0     ← 出现 429 说明入口限流挡了，压漏斗请关限流
延迟(ms): p50=68.5  p90=142.0  p95=176.3  p99=245.9  max=812.0
扩容参考: 机器数 = 峰值QPS ÷ 单机QPS（留 30~50% 冗余）
```

- **QPS ≈ 162** = 这台机器（当前配置）在 p99≈246ms 下的容量；
- 想看"能不能更高"，逐步加 `--concurrency` 到曲线平台期（吞吐不再涨、RT 开始涨 = 到容量点了）；
- **P99 比 P50 重要**：P99 是真实用户感知，P50 好看没用。

## 3. 扩容公式（压测的唯一产出目标）

```
机器数 = 峰值 QPS ÷ 单机 QPS × (1 + 冗余系数)
```

- **单机 QPS**：上面脚本测出的平台期 QPS（记得冗余系数留 30~50%）；
- **峰值 QPS**：线上真实峰值（从网关/Nginx 访问日志统计，或按业务预期估算）；
- **冗余系数**：给突发流量/单机故障/自动扩缩容时间留的安全垫。

**示例**：单机压出 160 QPS，线上峰值 1000 QPS → 机器数 = 1000 ÷ 160 × 1.4 ≈ **9 台**。

> ⚠️ 扩容前提是"**无状态 + 状态外置**"（本项目 P2 已做：Session Redis、流量池 Redis、ItemCF 模型 Redis、调度 XXL-Job 中心化）。否则堆机器只会把状态不一致放大。**先摸容量再谈机器**，别一上来就堆。

## 4. 场景表（逐场景验证治理开关）

| 场景 | 怎么配 | 期望 | 验证什么 |
|---|---|---|---|
| **基线** | rate-limit=false，Sentinel flow-qps=100（默认） | 记 QPS/P99 | 单机容量基准 |
| **关缓存** | `app.rec.profile-cache-ttl-ms=0`、`item-feature-cache-ttl-ms=0`、`post-cache-ttl-ms=0`、`hot-post-ids-ttl-ms=0` | QPS 明显下降、P99 抬升 | 证明缓存是容量大头（优化有数字） |
| **关入口限流 vs 开** | `rate-limit.enabled` true/false 对比 | 开：同 IP 超 100/60s 被 429 | 入口限流有效性 |
| **触发 Sentinel 限流降级** | `app.rec.sentinel.feed.flow-qps` 调到远低于压测 QPS（如 10） | 日志大量"被 Sentinel 限流"，返回仍是 200 热门兜底，接口不 500 | 限流降级链路（BlockException → hotFallback） |
| **触发 Sentinel 熔断** | 手动注入故障（如让召回抛异常，见 `RecommendServiceFallbackTest` 桩法）或改 degrade.ratio 为极小值 | 日志 WARN 降级、异常率超阈值后进入熔断窗口、恢复后半开自动回 CLOSED | 异常比例熔断端到端（**需真流量，生产验证项**） |
| **限流专测** | rate-limit=true，`--expect-status 429`，`--concurrency 50` | 429 命中数 ≈ 超限部分 | 限流是否按预期拒绝 |

## 6. 注意事项与坑

1. **压测前先关入口限流**（`rate-limit.enabled=false`），否则 429 污染漏斗数据——除非你就是在测限流；
2. **预热必做**（`--warmup`）：不预热的话把"画像/特征/热门首次现算"的冷启动成本算进容量，测出来偏低；
3. **单机为准，多实例另测**：分布式限流（Sentinel 集群流控）、多 pod 一致性不在本脚本范围——那是"真上多实例"时对生产环境的专项压测；
4. **P99 优先**：容量点以"P99 到可接受阈值"为界，不以"不报错"为界；
5. **记录机器配置**：容量是"这台机器的容量"，换机器/改 JVM 参数要重测。
