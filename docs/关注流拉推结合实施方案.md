## 1. 目标与设计原则

**目标**：让大 V 发帖不再扇出到每个粉丝（写放大 O(粉丝数) 爆炸、且 inbox 封顶 500 会把新帖顶掉），改为粉丝**读的时候**实时去大 V 自己的时间线（outbox）拉取合并。普通用户维持现状（推）。

**设计原则**：
1. **默认零行为变化**：阈值默认 10 万，演示数据永不触发 → 现有纯推路径原样保留，混合代码只在「读者关注的人中存在大 V」时激活；
2. **复用全局 postId 单调性**：游标统一用 postId，推/拉两路都能以同一 `maxId` 过滤，归并无歧义；
3. **大 V outbox 写一次 O(1)**：不扇出，只在作者自己的时间线/缓存写一份——写放大从 O(粉丝数) 降到 O(1)。

## 2. 总体设计：两路读 + K 路归并

读者刷流时，把「我关注的人」分成两组：

```
读者 userId 的关注流 = 
    推组（普通作者）   → 读自己的 inbox：FollowFeedStore.getInbox(userId, maxId, n)   （O(1)，已扇出）
  ∪ 拉组（大 V 作者）  → 逐个读大 V 的 outbox：FollowFeedStore.getAuthorTimeline(v, maxId, n) （O(1) each）
  → 两组都以全局 maxId 过滤 → 合并去重 → 按 postId 降序 → 取前 size 条 → resolve 回源
```

**核心洞察（为什么一个全局游标能通吃两路）**：inbox 里存的是 postId、outbox 里也是 postId，两者都天然按 postId 有序（postId 单调递增 = 时间序）。所以**同一个全局 `maxId` 对推流和每个大 V 流都成立**——各取「postId < maxId 的最近 N 条」，再归并，就得到正确的全局时间线。无需为每路维护独立游标。

**读放大**：O(1)（推） + O(关注的大V数 M × 每路 N)。普通用户关注的大 V 通常个位数，M 小 → 总成本仍近 O(1)。大 V 的 outbox 是共享热点，可缓存（见 §6）。

**写放大**：大 V 发帖只写 1 份 outbox（O(1)），不再抄送 M 份 inbox。inbox 封顶顶掉大 V 新帖的问题随之消失（大 V 的帖不再占用粉丝 inbox 名额）。

## 3. 接口与数据结构变更

### 3.1 `FollowFeedStore` 接口（forum-core/feed/FollowFeedStore.java）

新增 3 个方法 + 更名 1 个（`shouldSkipFanout → isBigV`），内存与 Redis 实现都实现：

```java
/** 大 V 判定：是否在全局大V集合（粉丝数 ≥ 阈值时的成员）。O(1) 集合查询，不逐人 count。 */
boolean isBigV(Long authorId);

/** 全局大V集合快照（供读侧求交：拉组 = bigVIds() ∩ 我的关注；Redis = SMEMBERS feed:bigvs）。接口需加 import java.util.Set。 */
Set<Long> bigVIds();

/**
 * 大 V 集合维护（事件驱动，非轮询）：关注/取关/删用户后，对受影响的那一个作者重数粉丝数，
 * 跨过阈值加入全局集合、掉出阈值移除（见 §6）。调用方只在自己改动关系边后调用，O(1)。
 */
void refreshBigV(Long authorId);

/**
 * 拉流：读某作者（大 V）自己的时间线（outbox），postId < maxId 的最新 maxCount 条。
 * 内存实现 = postRepository.findByAuthorId(authorId) 过滤可见 + 按 maxId 截断（outbox 天然在 Post 表里，无需额外结构）；
 * Redis 实现 = ZSet feed:outbox:{authorId} 的 ZREVRANGEBYSCORE（member=postId, score=postId，发帖时 ZADD，O(1)）。
 */
List<Long> getAuthorTimeline(Long authorId, Long maxId, int maxCount);
```

配套变更：
- `shouldSkipFanout(userId)` → 更名为 `isBigV(userId)`（`fanout` 内部 `if (isBigV(authorId)) return;`，读侧复用）——**语义一致，且从"每次 count 粉丝数"改为 O(1) 查全局集合**（见 §6）；
- 大 V 集合由 `FollowService.follow/unfollow/删除用户` 调用 `refreshBigV(受影响作者)` 维护——**粉丝数只在这几处变化，事件驱动即精确，无需轮询**；
- 大 V outbox 写入挂载：`FanoutPostCreatedConsumer.consume` 里，`isBigV` 分支由「直接 return」改为「写 outbox」——扇出挂载点统一，一个入口处理「普通→扇出 / 大V→写 outbox」：

```java
public void consume(PostCreatedEvent event) {
    if (followFeedStore.isBigV(event.getAuthorId())) {
        followFeedStore.writeOutbox(event.getAuthorId(), event.getPostId());  // O(1)，只写自己的时间线
    } else {
        followFeedStore.fanout(event.getAuthorId(), event.getPostId());       // 现状：扇出到粉丝 inbox
    }
}
```

（`writeOutbox` 内存实现 = no-op（读时直接查 Post）；Redis 实现 = `ZADD feed:outbox:{authorId}`。）

### 3.2 `FollowService` 改造（forum-admin-server/service/FollowService.java）

- `getFollowFeed` / `getFollowFeedSince`：加「拆推拉组 → 拉大 V → 归并」步骤（算法见 §4）；
- **首读建流回填跳过 V**：`collectRecentFromFollowees` 只收集**非大 V** 作者的近期帖——大 V 的帖读时实时拉即可，物理写进 inbox 会污染「inbox 只含普通作者」的边界，也白占名额；
- `follow()` 的关注回填同理：`recentPostIdsOf(followeeId)` 在 `followeeId` 是大 V 时**跳过**（新关注大 V → 不回填，直接靠读时拉）。

## 4. 合并与分页算法（伪代码）

```java
// FollowService.getFollowFeed 的 ID 获取阶段（maxId 为 null 表示从最新开始）
List<Long> collectMixedFeedIds(Long userId, Long maxId, int size) {
    List<Long> followingIds = getFollowingIds(userId).stream().toList();
    Set<Long> following = new HashSet<>(followingIds);
    // 拉组 = 全局大V集合 ∩ 我关注的（集合求交 O(|following|+|bigVs|)）；❌ 不是逐人 countByFolloweeId
    Set<Long> bigVs = followFeedStore.bigVIds().stream().filter(following::contains).collect(toSet());
    List<Long> normals = followingIds.stream().filter(id -> !bigVs.contains(id)).toList();

    int take = size + bigVs.size() + 1;                       // 安全余量：去重 + hasMore 判定

    // ① 推流：inbox 已聚合全部普通作者的帖子（已建流前提下 O(1)）
    List<Long> pushed = followFeedStore.getInbox(userId, maxId, take);

    // ② 拉流：每个大 V 各取 take 条
    List<List<Long>> pulled = bigVs.stream()
            .map(v -> followFeedStore.getAuthorTimeline(v, maxId, take))
            .toList();

    // ③ K 路归并：按 postId 降序，distinct 去重（防"作者跨阈值"残留导致的同帖重复）
    return Stream.concat(pushed.stream(), pulled.stream().flatMap(List::stream))
            .distinct()
            .sorted(Comparator.reverseOrder())                // 量级 = (M+1)×take，M 小，直接排序即可
            .toList();
}
// 后续沿用现状：resolveFromInbox（回源 + isVisible + 仍在关注）+ 多取1条判断 hasMore + nextMaxId = 第 size 条 postId
```

要点：
- **hasMore 判定**沿用现状「归并后条数 > size 即 hasMore」——`take` 的安全余量保证去重后仍能凑够 `size+1` 来判定；
- `getFollowFeedSince` 对称：推流 `getInboxAfter(userId, sinceId, take)` + 拉流 `getAuthorTimeline` 过滤 `postId > sinceId`，同样归并；
- **去重来源**：同一作者要么推要么拉（二选一），正常不会重复；唯一窗口是「作者从普通跨到 V」的瞬间——变 V 前扇进 inbox 的旧帖与变 V 后 outbox 的新帖 postId 不同，不会撞；真正可能重复的是「变 V 前最近一次 onFollow 回填把他的帖写进了 inbox，现在又走拉」。靠 ③ 的 `distinct()` 兜底，且 3.2 的「回填跳过 V」把重复窗口关到最小。

## 5. 边界情况

| 场景 | 处理 |
|---|---|
| 取关大 V | `resolveFromInbox` 的 `followingIds.contains(authorId)` 已过滤拉流结果，无需额外逻辑 |
| 删帖 / 不可见 | 拉流结果同样过 `isVisiblePost` 过滤，与现状一致 |
| 大 V 阈值跨越（普通→V） | 变 V 前的帖留在 inbox（残留，不清理，读取过滤兜底）；变 V 后走拉。`distinct()` 防重复 |
| 读者关注了多个大 V | 每路 O(1)，M 路并行拉取（可 `parallelStream`）；M 大时见 §6 降级 |
| 首读建流 | 回填只含普通作者；大 V 部分实时拉，无需建流 |
| inbox 封顶 | 大 V 不再占粉丝 inbox 名额；粉丝 inbox 只被普通作者占用，顶掉概率大降 |
| 未建流用户 | 推流 `getInbox` 返回空，但拉流照常工作——**未建流 + 只关注大 V 的用户也能刷到流**（读时拉不依赖建流） |

## 6. 性能与缓存

- **大 V outbox 缓存**：Redis 实现 = `feed:outbox:{authorId}` ZSet（发帖时 ZADD O(1)），是「一写多读」的共享热点，天然适合多级缓存；内存实现直接查 `postRepository.findByAuthorId`（演示量级足够）；
- **全局大V集合（核心：读侧和扇出侧都不轮询）**：
  - 数据结构：`Set<Long> bigVs`（内存 = `ConcurrentHashMap.newKeySet`；Redis = SET `feed:bigvs`），成员 = 粉丝数 ≥ 阈值的作者 id；
  - **维护**：粉丝数只在关注/取关/删用户时变化——这些事件后对受影响作者调 `refreshBigV(authorId)`（重数一次 + 跨线加/移除），事件驱动即精确，非轮询；
  - **读侧**：拉组 = `bigVIds() ∩ 我的关注`（内存 `retainAll` / Redis `SMEMBERS` 后本地求交），大V数量级小，交集几乎恒空；
  - **扇出侧**：`fanout` 的 `isBigV` 改查集合（O(1)），不再每次发帖 `countByFolloweeId` 一次；
  - 顺带收益：**「inbox 里有哪些人 / 还有哪些人没发进 inbox」都归约为「我关注的 − 拉组 = 推组」**——推组作者发了必进我 inbox（非V→扇出）、拉组作者读时拉，无第三个来源，闭环完整；
- **M（关注的大 V 数）过大降级**：读者关注的大 V 超上限（如 > 20）时，只拉最近活跃的 N 个（按最近发帖时间排序），或每路只取 top-K——当前规模不需要，预留策略说明。

## 9. 风险与取舍

- **读放大回归**：从纯 O(1) 变为 O(M×N)（M=关注的大 V 数）。本项目规模 M≈0，无感知；真出现 M 大再启用 §6 降级——这是「大 V 走拉」的固有代价，用 outbox 缓存摊薄；
- **合并分页正确性**：核心风险点是「多取的安全余量不够，去重后凑不满 size」——`take = size + M + 1` 已留余量，测试覆盖极端去重场景；
- **阈值跨越的一致性窗口**：作者变 V 瞬间，读者可能短时看到「inbox 残留 + outbox 拉取」两批不连续的帖（有 distinct 去重，无重复；最多是顺序上旧帖仍在靠前位置，随后消失）——可接受，读取过滤兜底；
- **命名重构风险**：`shouldSkipFanout → isBigV` 是接口方法更名，全仓引用点（2 个实现 + 测试）不多，机械替换 + 全量测试兜底；
- **不做**（当前规模，见调研文档 §11「不建议做的」）：多级缓存集群、分库分表、异步扇出 MQ（发帖扇出已是总线/ Kafka 消费者承载）。
