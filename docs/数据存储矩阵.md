# 数据存储矩阵（生产级数据放置决策）

> 创建：2026-08-26
> 主题：每类数据"该放 MySQL 就放 MySQL、该放 Redis 就放 Redis"的主流放置决策，作为 P1 数据中间件化与后续所有存储改造的**唯一依据**。
> 配套：与《内容生产/分发系统架构调研与对比》《生产化落地开发清单》《推荐系统微服务拆分方案》并列。

---

## 0. 一句话核心

**MySQL = 事实/主存储；Redis = 热数据/在线；Kafka = 事件流；数仓(ClickHouse) = 行为日志全量。**
每类数据按"写特征 × 读特征"定存储，**不无脑全 Redis、不无脑全 MySQL**。

```
MySQL（唯一不可丢的事实源）     帖子/用户/业务/关注关系事实/outbox
Redis（热数据，可重建）         feed inbox/实时特征/画像/幂等/热搜/冷启动池/热点详情缓存
Kafka（事件流，解耦/削峰）      行为事件/发帖事件
ClickHouse（OLAP 分析）         行为日志全量（画像/ItemCF/离线评估的事实源）
```

**可重建性层级**：Redis / Kafka / ClickHouse 均可从上游重建；**MySQL 是唯一不可丢的事实源**——任何数据要么在 MySQL 有事实，要么可被重建。

---

## 1. 决策原则

| 数据形态 | 写特征 | 读特征 | 主流存储 |
|---|---|---|---|
| 事实数据 | 低频~中频 | 按需查询/CRUD/事务 | **MySQL** |
| 热数据 | 中频写 | 高频读 | **Redis**（TTL 管理） |
| 事件流 | 高吞吐追加 | 多路消费 | **Kafka** |
| 分析数据 | 高吞吐追加 | 只读聚合/大范围扫描 | **数仓 OLAP**（ClickHouse） |

**判断方法**：问"这个数据是**事实**还是**可重建的热数据**？"
- 事实（丢了系统就坏了/是业务真相）→ MySQL。
- 热数据（丢了可以从 MySQL/上游重建，只是慢）→ Redis。
- 高吞吐追加写 + 只读聚合 → Kafka + OLAP，**不落 MySQL 行级**。

## 2. 数据存储矩阵（全量）

| 数据 | 写 | 读 | **主流存储** | 本项目现状 | 动作 |
|---|---|---|---|---|---|
| 帖子 Post | 低频写 | 高频读（热点） | **MySQL（主）+ Redis 热点缓存** | 内存 + mini_store JSON 快照 | ⚠️ P1.1 二阶段：MySQL 规范化表 |
| 用户 User | 低频写 | 中频读 | **MySQL** | 内存 + 快照 | ⚠️ 同上 |
| 评论/点赞/收藏/通知/私信/会话/搜索词 | 中频写 | 中频读 | **MySQL**（未读数可 Redis） | 内存 + 快照 | ⚠️ 同上 |
| **关注关系 Follow** | 中频写 | **高频读**（fanout 查粉丝） | **MySQL 事实 + Redis 缓存** | **Redis 纯事实源（无 MySQL）** | ⚠️ 偏差：补 MySQL 事实 + Redis 缓存 |
| **feed inbox** | 发帖扇出 | 关注流读（高频） | **Redis（ZSET）** | RedisFollowFeedStore ✅ | ✅ 主流 |
| **实时特征** | Flink 近线写 | 排序读（高频） | **Redis（TTL）** | RedisRealtimeFeatureStore ✅ | ✅ 主流 |
| **用户画像** | 行为回流算 | 推荐读（高频） | **Redis** | 无（每次现算） | ⚠️ P1.1 一阶段：Redis 画像 |
| **行为日志** | **高频写**（打点） | 只读聚合（画像/ItemCF/评估） | **Kafka + ClickHouse**（OLAP）；Redis 只做近线特征 | Kafka 事件 + 内存 + JSON 快照 + Flink→Redis 特征 | ⚠️ 生产接 ClickHouse（见 §3） |
| **热搜/话题/统计** | 行为聚合 | 热搜榜/看板（高频读） | **Redis（ZSET/计数器）** | 内存实时算 | ⚠️ 可 Redis（P1.1 可选） |
| **冷启动池**（赛马状态） | 发帖/回流写 | 排序读（高频） | **Redis**（跨实例共享） | 内存每实例一份 | ⚠️ 可 Redis（P1.1 可选） |
| **ItemCF 模型** | 离线构建 | 召回/相关读 | 内存/Redis | 内存 | ✅（够用，可后续 Redis） |
| **outbox** | 发帖事务写 | Relayer 轮询 | **MySQL** | MySqlOutboxStore ✅ | ✅ 主流 |
| **幂等 key** | 占位写 | 幂等读 | **Redis（NX/EX）** | RedisIdempotencyStore ✅ | ✅ 主流 |

## 3. 行为日志存储选型：ClickHouse vs Hive

行为日志是"高频追加写 + 只读聚合"，是典型的 OLAP 场景，**不落 MySQL 行级表**（高吞吐 append 会打爆 MySQL）。候选：ClickHouse / Hive。

### 需求特征（本项目）
- 行为已入 Kafka topic "behavior-log"（事件流已就绪）。
- 画像 / ItemCF / 离线评估是"行为数变化即算"的**近实时**形态（不是每日批量）。
- 部署轻量（学习/演示环境，单机可跑）。

### 对比

| 维度 | **ClickHouse** ✅ | Hive |
|---|---|---|
| 类型 | OLAP 列存（实时分析） | 数仓（Hadoop 生态，批） |
| **摄入** | **Kafka Engine 表直接消费 "behavior-log"**，毫秒级可见 | 批导入（MR/Spark），分钟~小时级 |
| **查询** | **亚秒聚合**（SQL），匹配画像/ItemCF 近实时聚合 | HiveQL 批查询，秒~分钟级，交互式弱 |
| **部署** | **单机 Docker 一条命令**，轻量 | 需 Hadoop/HDFS/MR 全家桶，重 |
| **实时性** | 近实时 | 批延迟 |
| 运维 | 简单 | 复杂（集群组件） |
| 与本项目匹配 | ✅ 近实时画像 + Kafka 直接摄入 + 单机可跑 | ❌ 批延迟不匹配 + 部署过重 |

### 结论：**ClickHouse**

- **摄入**：`Kafka Engine 表`（`Kafka('kafka:9092', 'behavior-log', ...)`) → `MergeTree` 落全量，毫秒级可见，无需写导入代码。
- **查询**：SQL 亚秒聚合——画像（`GROUP BY user_id`）、ItemCF 共现、离线评估直接可查。
- **部署**：`docker run clickhouse/clickhouse-server`，单机即可，契合本项目。
- Hive 的批延迟（分钟级）与"行为数变化即算画像/ItemCF"不匹配，且 Hadoop 生态部署成本高，仅适合纯离线批量场景。

### 生产架构（行为日志三路）

```
用户行为 → KafkaBehaviorLogger → Kafka "behavior-log"
   ├─▶ [ClickHouse Kafka Engine 表 → MergeTree]  行为全量（画像/ItemCF/评估的事实源）
   ├─▶ [Flink 近线作业 → Redis realtime:*]       近线实时特征（已在 flink-nearline）
   └─▶ [KafkaBehaviorConsumer → 内存 BehaviorLogRepository]  在线画像（单实例就近）
```

**本项目落地**：
- 演示（默认）：不真起 ClickHouse，保持内存 + JSON 快照（零中间件，行为等价）。
- 生产（`-Pprod` + 可选 docker-compose）：起 ClickHouse + 建 Kafka Engine 表，行为自动落库；离线评估/画像可切 ClickHouse 查询（后续阶段）。
