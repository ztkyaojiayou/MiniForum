## 1. Step 1：P3-1+P3-2 Sentinel 限流 + 熔断（推荐主链路）

### 1.1 目标
prod 用 Sentinel 对资源 `recommend-feed` 做**单机 QPS 限流** + **异常比例熔断**；限流/熔断触发（BlockException）→ 降级热门兜底。演示无规则 → 原样放行。

### 1.2 关键决策（已核实）
- **sentinel-core 必须是 forum-recommend-server 的普通依赖（非 optional）**：`RecommendService` 主代码（demo+prod 都跑）引用 `SphU/Entry/BlockException`，运行时必须有类路径；optional 不传递会让演示运行时 `NoClassDefFoundError` 直接崩。sentinel-core 无外部服务依赖、无规则时完全惰性（不连任何中间件），符合"零外部中间件"。版本 `com.alibaba.csp:sentinel-core:1.8.6`。
- **`SphU.entry` 放在 `recommend()` 内**（doRecommend 零改动）：`catch (BlockException)` → 直接 hotFallback；`catch (Exception)` → `Tracer.trace(e)` + hotFallback（给异常比例熔断供数）。`finally` 里 `entry.exit()`。**catch 顺序：BlockException 必须在 Exception 之前**（BlockException 是 Exception 子类）。
- **SentinelConfig**（@Component + @Profile("prod")）：@PostConstruct 调 `FlowRuleManager.loadRules` + `DegradeRuleManager.loadRules`（Spring 先跑完 @PostConstruct 再收请求，无"请求先到规则未加载"窗口）。规则：FlowRule(FLOW_GRADE_QPS, count=flowQps)；DegradeRule(DEGRADE_GRADE_EXCEPTION_RATIO, count=ratio, minRequestAmount, timeWindow)。

### 1.3 改动文件
| 文件 | 改动 |
|---|---|
| `forum-recommend-server/pom.xml` | + sentinel-core 1.8.6 普通依赖 |
| `.../service/RecommendService.java` | recommend() 加 SphU.entry + BlockException 分支 + Tracer；doRecommend/hotFallback 不动；+ 常量 `SENTINEL_RESOURCE_FEED` |
| `.../prod/sentinel/SentinelConfig.java`（新增） | @Profile("prod") 加载限流+熔断规则 |
| `demo-runner/src/main/resources/application-prod.yml` | + `app.rec.sentinel.*` 配置 |
| `.../service/RecommendServiceSentinelTest.java`（新增） | 无规则放行 / 规则阻断降级 / 规则清理 |

### 1.4 单测（RecommendServiceSentinelTest）
1. `recommend_passesThrough_withoutRules`：无规则 → 完整漏斗执行（verify recall 被调），结果非空。
2. `recommend_fallsBackToHotPosts_whenFlowRuleBlocks`：暖链一次（消除首建歧义）→ `FlowRuleManager.loadRules(List.of(flow count=0))` → recommend → 断言 reason="推荐服务降级·热门兜底" 且 recall 不被调用（verify times(1)，即仅暖链那次）；try/finally 清空。
3. `@AfterEach` 兜底清空两个 Manager（Sentinel 全局静态，防污染其它测试）。

### 1.5 风险
- Sentinel 规则 JVM 级全局静态 → 测试必须 try/finally + @AfterEach 双清理。
- BlockException 是 checked（漏 catch 编译不过）。
- 既有测试（fallback/topHot/集成）无规则 → 放行，保持绿。
- **本批不做集群流控（token-server）**——那是真"分布式限流"；单机 QPS 是形态 B 的每 pod 本地计数（贴合概念文档 §3 的"单机 vs 分布式"论述）。

## 2. Step 2：P3-3 热点 key（读帖子本地缓存）

### 2.1 目标
`PostService.getById` 读帖子加 `TtlCache<Long,Post>`，热门帖详情回源压力下降；短 TTL 接受轻微过期。

### 2.2 关键设计
- `PostService` 加 `TtlCache<Long,Post> postCache`（复用 forum-core，ttl≤0 禁用）+ `@Value("${app.rec.post-cache-ttl-ms:5000}")` setter。
- `getById` 读帖子处改 `postCache.get(id, () -> getPostOrThrow(id))`；其余（deleted 校验 / viewCount+1 / toVO）不变。`getPostOrThrow` 抛异常不毒化缓存。
- **写路径失效**（prod MySql 回源是快照，必须失效）：`updatePost / deletePost / restorePost` + `like / unlike` → `postCache.invalidate(id)`；`doPurgeExpiredPosts` 彻底删除同样失效。
- **缓存实体引用**：demo 内存仓库同引用自动一致；prod 靠写路径失效 + 短 TTL 兜底；注释注明"接受轻微过期"。
- 配置：`application.yml` `app.rec.post-cache-ttl-ms: 5000`。

### 2.3 改动文件
| 文件 | 改动 |
|---|---|
| `forum-admin-server/.../service/PostService.java` | postCache + getById 走缓存 + 写路径失效 |
| `forum-admin-server/src/test/.../service/PostServicePostCacheTest.java`（新增） | mock 仓储，风格对齐 PostServiceHotCacheTest |
| `demo-runner/src/main/resources/application.yml` | + `post-cache-ttl-ms: 5000` |

### 2.4 单测（PostServicePostCacheTest）
1. getById 两次 → findById 只 1 次（缓存命中）。
2. ttl=0 → findById 2 次（禁用）。
3. viewCount 每次读 +1（缓存内实体引用，save 被调 2 次）。
4. updatePost 失效后 getById → findById 2 次（缓存被踢）。
5. 不存在 → 两次均抛异常且 findById 2 次（异常不毒化）。

> 注意：getById 会调 `userRepository.findByUsername` 记 VIEW 行为 → 测试须 stub `when(userRepository.findByUsername(any())).thenReturn(Optional.empty())`。

### 2.5 风险
- 无测试碰 getById（已 grep 确认），既有测试全绿。
- 并发 viewCount 读-改-写非原子（现状如此），无回归。
