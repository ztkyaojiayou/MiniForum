## 一、严重问题（安全底线，必须修复）

### 1. 密码明文存储与传输 🔴

**涉及文件**：`entity/User.java`、`service/AuthService.java`

**现状**：
- `User` 实体中 `password` 字段直接存储明文。
- `AuthService.login()` 使用 `userOpt.get().getPassword().equals(password)` 直接比对明文密码。
- 默认管理员密码 `admin123` 也以明文写入。

**阿里规范**（【安全规约】）：
> 用户敏感信息（如密码）禁止明文存储，必须使用加密算法（如 BCrypt）进行哈希处理。

**改进建议**：
- 引入 `spring-security-crypto`，使用 `BCryptPasswordEncoder` 对密码进行哈希。
- 注册/修改时加密存储，登录时用 `matches()` 校验。
- 默认管理员密码从配置读取，避免硬编码。

---

### 2. 抛出通用异常 `IllegalArgumentException` 🔴

**涉及文件**：`service/UserService.java`（第 24、43 行）、`service/AuthService.java`（第 45 行）

**现状**：
- 用户名重复、登录失败等业务错误均抛出 `IllegalArgumentException`。
- `GlobalExceptionHandler` 也相应捕获 `IllegalArgumentException`。

**阿里规范**（【异常日志-1】）：
> 禁止抛出 `RuntimeException` / `Exception` 等通用异常，应使用语义明确的业务异常。

**改进建议**：
- 定义自定义业务异常，如 `BusinessException`、`AuthException`、`DuplicateUsernameException`。
- 在 `GlobalExceptionHandler` 中统一捕获并返回对应的 HTTP 状态码。

## 二、代码风格问题（阿里规范明确要求）

### 3. 可变静态常量暴露（`ID_GENERATOR`）⚠️

**涉及文件**：`entity/User.java`（第 16 行）

**现状**：
```java
public static final AtomicLong ID_GENERATOR = new AtomicLong(1);
```
- 该字段为 `public static final` 且是**可变对象**，暴露在实体类上。
- 由 `UserRepository.save()` 直接调用 `User.ID_GENERATOR.getAndIncrement()`。

**阿里规范**（【常量定义】）：
> 常量命名全大写、下划线分隔，且应尽量保持不可变；可变对象不应作为公开静态字段暴露。

**改进建议**：
- 将 ID 生成器私有化到 `UserRepository` 内部，由仓储负责主键生成，实体只承载数据。

---

### 4. 魔法值（Magic Number）⚠️

**涉及文件**：`service/AuthService.java`（`"admin"`、`"admin123"`、`"admin@example.com"`、`30`）

**现状**：
- 默认管理员账号信息硬编码在 `@PostConstruct` 方法中。

**阿里规范**（【常量定义-1】）：
> 不允许任何魔法值（即未经定义的常量）直接出现在代码中。

**改进建议**：
- 将默认管理员账号、密码、邮箱、年龄提取为常量或放入 `application.yml` 配置。

---

### 5. 校验注解直接放在实体上（职责混淆）⚠️

**涉及文件**：`entity/User.java`

**现状**：
- `@NotBlank`、`@Email`、`@Size`、`@NotNull` 等校验注解直接写在 `User` 实体字段上。
- `controller/UserController.java` 直接以 `@Valid @RequestBody User` 接收请求参数。

**阿里规范**（【OOP规约】）：
> 实体类只承载数据，不应承载表现层校验逻辑；请求参数校验应使用独立的 DTO 对象。

**改进建议**：
- 新增 `UserCreateDTO` / `UserUpdateDTO`，将校验注解迁移到 DTO。
- Controller 接收 DTO，Service 层完成 DTO → Entity 的转换。

---

### 6. `toString()` 输出敏感信息 ⚠️

**涉及文件**：`entity/User.java`（第 98-107 行）

**现状**：
```java
return "User{" +
        "id=" + id +
        ", username='" + username + '\'' +
        ", email='" + email + '\'' +
        ", password='" + password + '\'' +   // ← 敏感信息
        ...;
```

**阿里规范**（【安全规约】）：
> 日志与 `toString()` 中禁止输出密码等敏感信息。

**改进建议**：
- 从 `toString()` 中移除 `password` 字段。

## 三、其他改进建议

### 7. 包名使用默认占位符 🟡

**涉及文件**：全部 `com.tkzou.miniforum.*`

**现状**：已修复——包名已由 `com.example` 改为 `com.tkzou.miniforum`。

**阿里规范**（【命名规约】）：
> 包名应使用公司/组织域名的反写形式。

**改进建议**：根据实际组织域名调整，如 `com.yourcompany.miniforum`。

---

### 8. 缺少单元测试 🟡

**涉及文件**：`pom.xml` 已引入 `spring-boot-starter-test`，但 `src/test` 目录为空。

**阿里规范**（【单元测试】）：
> 单元测试必须可重复执行、代码必须覆盖；核心业务逻辑应有测试保障。

**改进建议**：为 `UserService`、`AuthService`、`UserRepository` 补充单元测试。

---

### 9. API 返回结构不统一 🟡

**涉及文件**：`controller/AuthController.java`、`controller/UserController.java`、`exception/GlobalExceptionHandler.java`

**现状**：
- 部分接口返回 `ResponseEntity<Map<String, Object>>`，部分直接返回实体。
- 成功/失败响应的字段结构不一致，无统一 `code/message/data` 包装。

**阿里规范**（【分层规约】）：
> 对外接口应使用统一的响应体结构，便于前端与调用方处理。

**改进建议**：定义统一的 `Result<T>` 包装类，统一成功与失败的返回格式。

---

### 10. 会话管理方式 🟡

**涉及文件**：`controller/AuthController.java`、`config/AuthInterceptor.java`

**现状**：使用 `HttpSession` + Cookie 维护登录态。

**阿里规范**（【安全规约】）：
> 前后端分离场景下，接口鉴权建议使用无状态 Token（如 JWT）方案。

**改进建议**：如项目为纯 REST API，可考虑迁移到 JWT 无状态认证。

---

### 11. 拦截器手动拼接 JSON 字符串 🟡

**涉及文件**：`config/AuthInterceptor.java`（第 30 行）

**现状**：
```java
response.getWriter().write("{\"message\":\"未登录或登录已过期\"}");
```

**阿里规范**（【异常日志】）：
> 统一异常处理，避免在各处手动拼接响应。

**改进建议**：
- 拦截器抛出 `UnauthorizedException`，由 `GlobalExceptionHandler` 统一处理并返回 JSON。

---

### 12. 内存存储无法持久化 🟡

**涉及文件**：`repository/UserRepository.java`

**现状**：使用 `ConcurrentHashMap` 做内存存储，应用重启后数据全部丢失。

**改进建议**：生产环境应替换为数据库（如 MySQL + MyBatis / Spring Data JPA）。
