## 1. P0 — 发帖可靠性（写路径核心）

### 1.1 幂等 Idempotency-Key（S）

**目标**：防双击 / 网络重试 / 前端超时重发 → 同一内容发两遍。

**实现要点**：
- 前端：发帖请求携带 `Idempotency-Key`（UUID，重试复用同一 key）。
- 后端：`PostController.createPost` 读取 header → 查 `key → postId` 缓存：
  - 命中 → 直接返回首次结果（幂等）；
  - 未命中 → 正常发帖 → 写 `key → postId`。
- 存储：Redis `idempotency:{key}`（TTL 数分钟）；演示版可用内存 `ConcurrentHashMap`（低风险）。
- 位置：`forum-admin-server`（PostController/PostService）+ 前端 index.html 发帖处。

**验收**：同 key 连续两次 POST → 只产生一条帖子，第二次返回首次 postId。

### 1.2 事务 Outbox → Kafka 必达（M）

**目标**：发帖落库与发事件跨系统（MySQL/Kafka），保证事件不丢。

**实现要点**：
- 发帖事务：`INSERT posts + INSERT outbox(post_id, status=PENDING)`（同一事务，原子）。
- Outbox Relayer（**仅 prod**）：定时轮询 `outbox WHERE status=PENDING` → 发 Kafka "post-created" → 更新 `status=DONE`；失败重试、幂等。
- 演示版**保持现状**：`InMemoryPostCreatedNotifier` 同步 notify（不引入 outbox 复杂度）。
- 位置：`forum-admin-server`（PostService 事务 + outbox 表）+ `demo-runner`（prod 侧 Relayer，可用 `@Scheduled` 或 `src/prod` 适配）。

**验收**：模拟"发帖后立刻崩溃"→ 重启后 Relayer 补发事件，下游（fanout）不丢帖；`data`/MySQL 中 outbox 全部 DONE。

## 2. P1 — 生产数据形态

### 2.1 数据中间件化（L）

**目标**：把"单体适配"变成"真微服务"——跨服务共享数据从内存仓库落到中间件（方案 doc §8 的"最大跳跃"）。

**实现要点**（分步）：
1. **行为日志** → 内存 `BehaviorLogRepository` → MySQL（`behavior-log` 快照表）或 Redis（近期行为）。
2. **画像/实时特征** → Redis（`realtime:*` 已有适配 `RedisRealtimeFeatureStore`，补画像 `profile:{uid}`）。
3. **feed inbox / 关注关系** → Redis（`RedisFollowFeedStore` / `RedisFollowRepository` 已就绪，激活即可）。
4. **帖子/用户主存储** → MySQL（`MySqlDataStore` 已就绪，`-Pprod` 激活）。
- 关键：各适配类已存在，本项主要是"真连中间件 + 验证一致性 + 处理跨服务读"。

**验收**：`-Pprod` + 真 Redis/MySQL 启动，多实例可共享同一份行为/画像/feed；演示（默认 profile）完全不受影响。

### 2.2 ID 生产化 Snowflake（S）

**目标**：全局单调 + 带时间戳的 ID（游标分页天然可用，跨实例不冲突）。

**实现要点**：
- `Post.nextId()` 等实体 ID 生成 → Snowflake 实现（`util/IdGenerator`，workerId 配置化）。
- 仅 prod 激活（`@Profile("prod")`）；演示保留 AtomicLong。
- 与 `resetIdGenerator`（持久化恢复）兼容。

**验收**：prod 下多实例生成 ID 全局唯一且单调递增；`max_id` 游标仍稳定。

## 3. P2 — 分发/消费增强

### 3.1 搜索索引消费者（M）

**目标**：搜索从"实时全表扫"改"索引查询"。

**实现要点**：
- 订阅 `post-created` → 更新倒排索引（标题/内容/标签/话题）。
- 内存索引（演示/低量）或 ES（生产）。
- `SearchService` 改查索引（当前 `postRepository.findAll()` 过滤）。

### 3.2 统计/热搜消费者化（M）

**目标**：事件驱动聚合，替代读时全表扫。

**实现要点**：消费行为事件（点击/曝光/互动）→ 增量维护热度/话题聚合 → 热搜/看板读聚合结果。

### 3.3 内容管道异步化（L）

**目标**：审核/embedding 等慢处理不阻塞发帖。

**实现要点**：消费 `post-created` → 审核队列 / embedding 任务 → 写回元数据（审核状态、向量）；发帖请求只做快处理（校验/提取）。

## 4. P3 — 加固与编排

### 4.1 密码 BCrypt（S）
- `PasswordEncoder` 用 BCrypt 替换 SHA-256+盐；存量 SHA-256 密码需兼容（双校验或迁移）。
- 两端都要，注意演示存量账号（admin123）可登录。

### 4.2 docker-compose 编排（M）
- 拉起：demo-runner（或各服务）+ Kafka + Redis + MySQL + Nacos（可选 Flink）。
- 配置外部化（环境变量注入 datasource/kafka/redis 地址）。

### 4.3 内存冷启事件化（S，demo 增强）
- `InMemoryPostCreatedNotifier` 同时调 `TrafficPool.notifyCreated`，与生产消费者行为对齐（当前演示 TrafficPool 懒加载）。

## 5. 暂缓

### 独立服务 main（admin/recommend/offline 启动类）
已讨论推迟：admin/recommend 是 demo 的编译依赖，加 `@SpringBootApplication` main 会被 demo 扫描器当配置类扫进（冗余嵌套扫描 / 可能 bean 冲突），需 `boot` 包 + demo `excludeFilters` 隔离，收益当前不急。待"真多进程部署"时再做。

## 6. 依赖关系与建议执行顺序

```
P0.1 幂等 ──────────── 独立，先做（半天）
P0.2 Outbox ── 依赖已有 Kafka post-created 基建，紧接（2~3天）
  ↓
P1.2 数据中间件化 ── 依赖已就绪的 prod 适配（Redis/MySQL），是后续"地基"（1~2周）
  ↓
P1.3 Snowflake ── 可与 P1.2 并行
  ↓
P2.x 搜索索引 / 统计 / 内容管道 ── 依赖事件流 + 数据中间件
P3.x BCrypt / docker-compose / 冷启事件化 ── 收尾加固
```

**建议起点**：P0（幂等 + Outbox）——"发帖必达"的核心可靠性，难度 S/M，且是生产/分发两份文档共同的最高差距。
