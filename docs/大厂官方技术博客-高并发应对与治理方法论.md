# 1　美团技术团队（tech.meituan.com）

## 1.1 缓存体系：选型框架 + 数据一致性

**《缓存那些事》**【源：tech.meituan.com/2017/03/17/cache-about.html】——方法论是"**没有一种缓存方案能解决一切**，必须按数据类型与业务场景选型"：
- 从缓存特征（命中率/最大元素/清空策略 FIFO/LFU/LRU）、介质（内存/硬盘/DB）、分类（本地 vs 分布式）逐层拆解；
- 落地：酒店商家端自定义 `@HotelCacheable/@HotelCacheEvict`，引入"作用域（domain）"解决多关联缓存联动失效，配合 MtConfig **一键关闭缓存降级**。

**《美团酒店直连产品数据一致性演进》**【源：tech.meituan.com/2016/12/26/data-consistency.html】——四阶段一致性方法论：定时全量 → 按热度分而治之 → 触发式更新+预测 → 供应商主动推送。
- 案例：**95%+ 用户订 10 天内酒店** → 每 15 分钟只拉 10 天数据，拉取量/响应时间减 **5/6**；"下单前实时校验"后退款单从每天几千降到几百。

## 1.2 分布式 KV：Squirrel / Cellar

**《美团大规模 KV 存储挑战与架构实践》**【源：tech.meituan.com/2024/03/15/KV-Squirrel-Cellar.html】
- 两条线：**Squirrel**（全内存、高吞吐低延迟，Redis Cluster 自研）vs **Cellar**（持久化、大容量高可靠，Tair 自研）；
- 关键技术：Merkle Tree 摘要降 Gossip 通信 **90%+**、forkless RDB（**8GB 节点 fork 会阻塞 500ms**，对毫秒级 KV 即大量超时）、工作多线程吞吐比社区单线程 **3 倍+**、Bulkload 导入提速 5 倍；
- 规模：**每天万亿级请求、99.995% 可用性**。

## 1.3 全链路压测：Quake + 自动化 + 数据库容量评估

**《全链路压测平台 Quake》**【源：tech.meituan.com/2018/09/27/quake-introduction.html】四大能力：
1. 流量构造：HTTP 走 Nginx 访问日志，RPC 走**线上实时流量录制**；
2. **压测隔离**：压测标识透传（线程内 ThreadLocal + 跨服务 Mtrace 分布式追踪透传）、机器级分组、写请求进**影子表**、MQ 按标识忽略；
3. 自研压测引擎（Reactor 多线程、业务与 IO 分离）；
4. 实时监控 + 双向熔断 + **压测中故障演练**。
- 规模：所有核心业务线接入，**月均压测上万次**、90% 业务迁移。

**《从0到1建设美团数据库容量评估系统》**【源：tech.meituan.com/2025/10/17/Database-Capacity-Evaluation-System.html】——方法论很有启发性：用"**线上真实 SQL 流量录制 → 沙盒隔离集群回放**"替代指标计算（线性不准）与全链路压测（拟真难）。指数加压 + 二分精确校准探测**最大承载 QPS**，健康水位区间 **30%–50%** 判冗余/不足。

## 1.4 服务治理：OCTO

**《OCTO 大规模微服务通信框架及治理体系》**【源：tech.meituan.com/2019/08/08/large-scale-microservice-communication-framework.html】
- 核心思想"**策略下沉**"：把治理策略从框架剥离下沉到代理组件；能力含注册发现、容错（实时屏蔽异常服务）、**过载保护（QoS 配额流控）**、灰度、监控、链路追踪；
- 规模：日均**千亿级调用**、成功率 **99.999%**。OCTO 2.0 走 Service Mesh（Envoy 数据面 + 自研控制面），集中式健康检查替代 N² 次 P2P。

## 1.5 并发治理：动态线程池

**《Java 线程池实现原理及其在美团业务中的实践》**【源：tech.meituan.com/2020/04/02/java-pooling-pratice-in-meituan.html】
- 痛点：**线程池参数"不好配"**（业界无通用公式）；
- 解法：**动态化线程池**——参数从代码迁到配置中心、运行时动态调参；只暴露 `corePoolSize/maximumPoolSize/workQueue` 三参数 + 队列选择（同步队列=响应优先 / 有界队列=吞吐优先）；配套活跃度预警、拒绝/积压告警；
- 案例：展示接口 corePoolSize 偏小大量 `RejectedExecutionException` 引发降级；队列设置过长导致任务堆积、最大线程数失效，引发 S2 级故障。

## 1.6 大促保障与稳定性

- **《大促活动前团购系统流量预算和容量评估》**【源：2016/09/28/stress-test-before-promotion.html】：核心公式"**扩容 = 活动峰值流量 ÷ 单机容量**"；案例**瞬时高峰为平时 33 倍**、活动页 1 PV 对基础服务产生 **7 次调用**；
- **《美团外卖订单中心的演进》**【源：2016/09/09/mt-waimai-order-evolution.html】：性能三件套**异步化 + 并行化 + 缓存预计算**；Hystrix 依赖容灾（线程池隔离）；分库分表（订单/用户/门店各冗余一份，各 100 表/4 库）；日订单突破 **600 万单**、交易 tp99=150ms、可用性 **6 个 9**；
- **《超大规模数据库集群保稳系列》**【源：2023/05/11、2023/06/09】：数据库容灾 N+1 架构、**常态 1500+ 集群并发演练**、Leader 故障 4 秒内选举；容灾目标 RPO=0；
- **《Mt-Falcon 监控》**【源：2017/02/24/mt-falcon-monitoring-system.html】：完全替换 Zabbix，监控项**超 2 亿**；
- **《美团弹性伸缩系统 Hulk》**【源：2021/04/01/Hulk-Kubernetes-Docker-OCTO.html】：弹性调度 + 混合云，节假日平均节约成本 **20.4%**，外卖午高峰释放常驻机器 365 台。

# 2　阿里技术 / 淘宝技术

## 2.1 双 11 全链路压测（方法论的开山之作）

**《详解双11终极"核武器"：全链路压测如何诞生？》**【源：《尽在双11》技术团队，developer.aliyun.com/article/106995】
- 核心思想："**让事件提前发生**"——在真实环境提前经历几次双11；
- **数据隔离方案演进**（最精华）：逻辑隔离（写线上靠标识区分）→ 放弃（破坏线上安全）→ mock 写操作 → 放弃（干扰压测）→ 最终**在所有写数据处识别压测流量、写到隔离位置（存储/缓存/搜索引擎）**，即**影子表/影子库**；
- 配套：《阿里怎么做双11全链路压测？》【源：article/723177】——**压测流量全局识别 + 透传**，层层打标；容量用 **RPS 模式**；从"200 人通宵压测"缩减到"10 人以内白天压测"。

## 2.2 限流熔断降级：Sentinel

**Sentinel 官方**【源：sentinelguard.io】：以流量为切入点，从流量路由、流量控制、流量整形、熔断降级、系统自适应过载保护、热点流量防护保障稳定性；核心抽象"**资源 + 规则**"，规则可动态调整。2012 诞生 → 阿里内部覆盖所有核心场景 → 2018 开源 → 2022 升级为"流量治理"。

**与 Hystrix 的设计取舍**【源：github.com/alibaba/Sentinel/wiki/熔断降级】——很有价值：
- Hystrix 用**线程池隔离**（隔离彻底，但有线程切换损耗、需预分配池大小）；
- Sentinel 改用**限制并发线程数 + 按响应时间降级**：资源不稳定（RT 变长）→ 线程堆积 → 达阈值拒绝新请求，**无线程切换损耗、无需预分配**；另提供**系统自适应负载保护**（类 BBR）防雪崩。

## 2.3 缓存：Tair

**《双11万亿流量下的分布式缓存》**【源：developer.aliyun.com/article/290865】
- 挑战："成本增速不超过交易峰值增速"；
- 三大解法：①**多级存储一体化**（本地内存 + 远端 Tair 合并写，安全风控大量读命中本地）；②**热点散列**（解决"数据分片=单点、大促热点打爆单分片"）；③弹性建站与水位调度；
- 规模：双11 **每秒 5 亿次峰值调用、平均延迟 <1ms**；多级存储后业务对 Tair 读取降至 27.68%、服务器成本每年降 30–40%。

## 2.4 异步削峰：RocketMQ

**阿里云官方**【源：help.aliyun.com，RocketMQ 场景】四大场景：**异步解耦**（注册后发邮件/短信）、**事务消息**（二阶段提交 + 本地事务绑定，保证最终一致）、**削峰填谷**（秒杀把洪峰平摊）、**大规模缓存同步**。
- 案例【源：article/1743005】：跨境订单把库存统计/对账/推送等**非实时逻辑全投 MQ 异步**，核心链路只保留下单+锁库存 → 接口耗时 **800ms–1.5s 降到 120ms 内**、DB QPS 降 60%。

## 2.5 异地多活 / 单元化（阿里最体系化）

**《金融级单元化分布式架构的设计原理与实践案例》**【源：蚂蚁尹博学，developer.aliyun.com/article/767241】
- 三区：**RZone**（可拆分业务分片）、**GZone**（全局唯一不可拆）、**CZone**（GZone 的城市只读副本）；数据 5 副本、三地五中心、Paxos 强一致（OceanBase）；
- 价值：容灾（**RPO=0、RTO<1min**）、弹性（租借 IDC 做临时 RZone，大促后弹回回收）、灰度（按数据分片粒度切换，可灰度可回滚）；
- 阿里云 Well-Architected 定义四种多活形态：业务流量多活 BFA / 同城多活 LRA / 异地多活 UDA（间距>300km）/ 混合云多活 HCA。

## 2.6 弹性计算：神龙架构

**《揭秘双11：阿里云弹性计算如何应对流量洪峰？》**【源：developer.aliyun.com/article/1738420】
- 洪峰不靠"堆机器"，靠"**预测扩容 + 分层过滤 + 极速弹性**"；流量经 SLB → ESS → Redis → RocketMQ 四级漏斗；
- **神龙架构**：裸金属性能 + 虚拟机弹性；预测性扩容 + 混合云兜底（自有不足调公有云 ECI）；
- 数据：**极速弹性 3 分钟拉起 50 万核**、支撑 58.3 万笔/秒订单峰值；2024 双11 阿里云 100 万核算力、弹性成本节省超 25%。

## 2.7 双11 技术保障方法论

**《阿里如何做好双11技术保障？大队长霜波分享4点经验》**【源：developer.aliyun.com/article/780951】
- **组织/备战/当天/复盘**四环节；关键动作：①全链路压测（"再做一套数据库"=影子库）；②**封网**——双11 当天从应用到基础设施逐层集中管控，保证"验证过的结果和当天一致"；③**红蓝军攻防**——把历史上所有高可用故障记录并模拟复现，集团目标"**1、5、10**"（1 分钟发现、5 分钟定位、10 分钟恢复），可模拟 800 台容器同时断、整机房断电；④**云顶指挥台**——问题自动同步、P2 以上重大故障队长直接决策。
- 数字：50+ BU 参与；为压测改造几千个应用、几十个中间件、几十万个数据库。

# 3　京东技术

## 3.1 热点治理：JD-hotkey（最体系化的热点方案）

**《京东毫秒级热 key 探测框架，已支撑 618》**【源：developer.jdcloud.com/article/2855】
- 四组件：**etcd**（配置/规则/热 key 存储）、**client jar**（key 上报 + Caffeine 本地缓存）、**worker 集群**（滑动窗口累加）、**dashboard**；
- client 每 **500ms** 批量上报待测 key，worker 按 hash 分发计算，达阈值后**毫秒级推送到整个集群 JVM**（要有都有、要删全删）；
- 数字：单 worker **16 万 key/s**、10 台 worker 每秒近 300 万次探测，已支撑京东 618。

**《单机 QPS 提升 17 倍实战》**【源：developer.jdcloud.com/article/2854】——性能调优实录：netty IO 线程与计算线程平衡（各半核）、弃 disruptor 改 LinkedBlockingQueue、换 protobuf 序列化 → 单机 QPS 从 **2 万 → 35 万**（16 核），热 key 稳定推送 10–12 万次/秒。方法论："**一切靠实践**，每个改动要线上真实流量 + 极端压测"。

## 3.2 大促备战方法论

**《如何应对大促流量洪峰？备战手册》**【源：京东技术公众号】
- **八步法**：识别保障范围（0/1 级系统）→ 业务量预估 → 预案整理（高可用/降级/弹性扩容）→ 监控报警梳理 → 压测演练 → 值班 → 复盘；
- 贯穿原则"**系统间不信任**"（B 永远不信任 A，自己做好兜底）；用"开门红"（6.1/11.1）做**真实演练**；云化后"备战逐渐淡化、系统随时可应对大促"。

**《架构师日记：大促备战的奥秘》**【源：developer.jdcloud.com/article/2987】
- 三视角：**应用**（单元化 + 异地多活、快速失败、限流降级）、**存储**（DB 主从/读写分离/分库分表、缓存一主多从/热点治理、ES 双集群）、**运营**（军演压测、**技术封版**、值班、预案）；
- **限流遵循木桶原理**：聚合业务系统用**单机限流**（扩容友好），底层基础服务用**全局集中式限流**（优先保存储层）；
- 数字：**70% 线上问题由改动发版导致**（因此封版）；单服务 99.9% × 100 节点组合后仅 99.5%。

**《618 稳定性之容量设计》**【源：developer.jdcloud.com/article/3867】——容量 = "风险最小化与成本最小化的平衡"：
- Redis 峰值 QPS 评估：`QPS = 在线连接数 × 应用 API × 单 API 访问 Redis 次数`；
- MQ 出队能力：`分片数×队列数×批量大小×(1000/tpAvg)×0.9`；
- 案例：**热点 SKU 1 个的流量峰值可等于 N 万个 SKU**；预估口径"往年峰值 1.3 倍"。

## 3.3 高保真压测 ForceBot

**《大促千万级流量来袭前，我们都在做什么？》**【源：京东技术公众号】
- **高保真压测**：环境=生产、数据真实（流量录制回放 + 业务配比模型）、方式多样（流量回放/模拟/**憋单压测**——利用异步节点蓄洪再放洪冲击下游）；
- 数字：军演流量需求百万级 → 千万级（10 倍）、高保真压测覆盖率 80%、覆盖 90% 研发团队、万台压力机。

## 3.4 多级缓存方案

**《服务端应用多级缓存架构方案》**【源：京东云技术团队】
- 20w~100w QPS 通用方案：请求先打**应用本地缓存**，未命中再打 r2m（Redis 集群）并回填；**热点 key 用"本地缓存 + 副本分散"**（加 Redis 集群数量对单 key 热点无效）；
- 一致性：Redis 发布订阅删本地 key；本地缓存 7 条注意事项（必须设有效期、加锁防并发击穿、深拷贝防 RPC 污染、重启后加载时机等）；
- 数字：**10w 流量打同一 key 会把单个 Redis 实例 CPU 打满**（加机器解决不了）——和"热点加机器没用"完全对应。

## 3.5 混部降本

**《混部技术如何每年为京东节省上亿元成本？》**【源：developer.jdcloud.com/article/2856】
- **混部** = 在线高优先级 + 离线低优先级同节点部署，利用负载"削峰填谷"提升利用率；
- 四技术：资源隔离（CPU Burst/内存回收/磁盘限速）、负载感知调度（阿基米德）、可观测、故障自愈；大促时**压制离线保在线**；
- 数字：混部节点 CPU 使用率常态 **80%**（提升 40%+），年省数亿元；**2022 春晚红包 20 多天不增加任何线上资源完成保障**；整机使用率 70% 时离线对在线 QPS/TP95 影响 ≤4%。

## 3.6 稳定性：故障演练 + 11.11 揭秘

**《亿级流量背后战场，京东11.11全方位技术揭秘》**【源：developer.jdcloud.com/article/1362】
- 五年演进：2015 容器化 → 2016 中间件 → **2017 引入全链路压测 + "捣乱的猴子"故障演练** → 2018 组件化 → 2019 中台化 → 2020 PaaS；
- 备战"纵横双向"：纵向按备战计划/预案/三轮压测推进并"捣乱演习"定位薄弱；横向对交易/前端/消息/用户交叉检查；限流降级用**令牌桶**、秒级监控（TP999/QPS/GMV）；
- 数字：2020 双11 成交额 2715 亿；全链路压测 TPS 50 万/秒、TP999 ≤10 秒；物流路由系统百亿级异步消息 + Fail-fast 熔断分片。

# 4　腾讯技术

## 4.1 海量服务之道：大系统小做

**《【大系统小做】理论篇 + 实战篇》**【源：腾讯大讲堂，cloud.tencent.com/developer/article/1041467、1041462】
- 理论：把复杂大系统**化大为小**，多个独立进程协作；"舞厅多色灯"论证——整体式故障 1→0，独立模块 1→0.99、故障点一目了然；
- 实战（QQ 相册百 P 级存储）：从**模型/层次/功能/设备/程序**五维度分解系统；层次 = 接入/逻辑/缓存/数据/外围，**接入层极轻量但承载量大，后端可无限扩展**。

**《后台服务架构高性能设计之道》**【源：腾讯技术工程官方号，article/1988700】——高性能方法论思维导图（可当 checklist）：
**无锁化 → 零拷贝（mmap/sendfile）→ 二进制序列化 → 池化（内存/线程/连接/对象）→ 并发化（请求+冗余请求）→ 异步化（Callback/Future/CPS）→ 缓存（多级 + Cache-Aside + 穿透/雪崩/热点治理）→ 分片（区间/随机/组合）→ 存储（读写分离/动静分离/冷热分离/数据异构）→ 队列（削峰/解耦/异步）**。
- 案例：企鹅电竞多级缓存 L1 命中率 **94%**；零拷贝比普通传输快约 3 倍；无锁链表比有锁快约 10%。

## 4.2 稳定性：混沌工程 + 高可用

**《微信支付混沌工程实践》**【源：腾讯云开发者，article/2398036】
- 微信支付作为国家关键基础设施，可用性要求**高于 5 个 9**；2021 年多分区改造（独立混沌分区）控制最小爆炸半径；
- 方法论：由"高可用原则拆解 + 历史故障分析"推导**故障原子**（RPC/队列/存储/缓存/认证/日志 × 生命线业务收付结退）；后期"单原子无差别注入 + 组合故障按相关性剪枝"找黑天鹅；自动设计/执行/分析；
- 数字：上线至今线上 0 故障、60+ 实验计划、500+ 实验任务、支持 30+ 故障原子。

**《工作十年，在腾讯沉淀的高可用系统架构设计经验》**【源：article/2239601】——六层面：研发规范（日志+链路追踪）、**容量规划（QPS 漏斗型预估：接入→详情→下单逐级衰减，先模块压测再全链路）**、应用服务（无状态+负载均衡+MQ 异步削峰+fail fast+限流熔断降级）、存储（1 主多从/冗余+失效转移）、产品兜底（柔性降级：默认页/停机页/兜底商品）、运维部署（灰度/监控/多机房/混沌演练）。结论：**可用性至少 4 个 9 才谈得上高可用**。

## 4.3 限流/熔断/降级

**《高并发场景下如何保证系统稳定性》（秒杀场景）**【源：腾讯云中间件团队，article/2171573】
- 秒杀四大特征（瞬时量大、热点、防超卖、不互相影响）+ 改造要点（秒杀子系统与主站**资源隔离**、网关限流、MQ 削峰、热点商品提前缓存）；
- 限流算法谱系：固定窗口→滑动窗口→漏桶（恒速削峰）→令牌桶（允许突发）；**单机 vs 分布式**（Redis/etcd 集中配额、batch 更新降开销、中间件不可用时**短路策略**）；
- 数字：TDMQ Pulsar 单集群 QPS>10 万、TDSQL Redis 千万级 QPS、秒杀前 HPC 定时扩容 + HPA 动态扩容双重保障。

**《熔断、隔离、重试、降级、超时、限流，流量治理核心策略》**【源：article/2374938】——以腾讯 O2 广告投放系统为例：
- 熔断：传统三态 vs **Google SRE 客户端自适应限流** `p=(requests−K×accepts)/(requests+1)`；
- **九种隔离**：动静/读写/核心/热点/用户/进程/线程/集群/机房；
- 重试：**指数退避 + 抖动防惊群**、重试风暴可达 3ⁿ 次、对冲策略；
- 降级：有损操作、自动+手动分级——"**降级牺牲功能、限流牺牲流量**"；
- 超时：固定 vs **EMA 动态超时**、超时传递；
- 案例：**微信后台用"平均排队时间"判断过载**——平均等待超 20ms 以降速因子过滤、低于 20ms 逐渐放行，"快速降低、缓慢提升"防大幅波动。

## 4.4 存储：Tendis 冷热混合

**《Redis vs Tendis：冷热混合存储版架构揭秘》**【源：腾讯技术工程，article/1815554】
- 解决 IEG 运营 Redis 四大痛点（内存成本高、fork 需预留一半内存、缓存一致性繁琐、可靠性差）；
- 冷热混合版 = **Proxy + 缓存层 Redis Cluster + 存储层 Tendis Cluster + 同步层 redis-sync**；冷数据自动降冷、热数据自动缓存；**Cuckoo Filter 表示全量 keys 防缓存穿透**；每 key 加 Version 实现增量 RDB/AOF 幂等；
- 数字：某业务 6620 万个 keys，缓存全量占 **18408MB**，Key 降冷后仅 **593MB**；Tendis 支持 PB 级、1000 节点。

## 4.5 大促/事件：微信红包与春晚

**《谈谈微信红包海量运营——发10亿个红包难在哪里？》**【源：腾讯大讲堂，article/1042200】——腾讯"海量之道 2.0"三策略：
- **有损服务**：选择性牺牲部分一致性，保证"摇-拆-分享"核心链路一气呵成；接入层置入摇红包逻辑把**每秒千万级降为万级**、后端异步分拆（合法验证后即返回成功，入账异步处理）；
- **柔性可用**：系统容灾（逻辑层 30% 切换）、资源隔离、快速拒绝、支付分组 set 化、流量预加载；
- **大系统小做**：高内聚低耦合模块化。
- 数字：2015 除夕摇一摇总次数 **110 亿次、峰值 1400 万次/秒**、红包收发 10.1 亿次；**400 倍挑战**（除夕一波红包 1.2 亿个，是上年峰值拆包量的 400 倍）。

**《微信红包技术篇：如何在服务有损时保证体验》**【源：article/1042250】——核心理念："**一定会挂，只是怎样更优雅**"：资源预下载平滑服务器压力、方案简单+异常简单（异常直接美化 404）、用户预期控制（红点/倒计时 Banner）、限流时长用"服务器传 level + 客户端查枚举"。

## 4.6 可观测性 + 弹性降本

- **《海量监控系统设计》**【源：article/2234905】：百万级服务器监控，采集 agent 按"一个程序只做一件事"拆三进程；告警做**屏蔽/去重/抑制/相关性收敛**，只发根因告警；单台 collector 支撑 10 万 agent、每天 100G+ 数据；
- **《云战疫：8天扩容100万核》**【源：article/1605436】：梳理"生死指标"（用户有损/收入有损/资源风险三类）、Grafana 作战大盘、**AIOps 无阈值监控 + 智能多维根因分析 + 告警相似性聚类**收敛告警风暴；
- **《百万级别容器云平台实践》**【源：article/2200815】：Pod 动态压缩（Request 双核 4G→单核 4G）、Node 动态超卖、HPAPlus 弹性 + VPAPlus 突发扩容；
- **《Caelus 全场景在离线混部》**【源：article/1759977】：k8s 零入侵混部，任务定级/批量调度（性能为原生 10 倍）/资源画像/干扰检测（perf CPI/eBPF）；**若 500 万核集群混部提高 10% 利用率可节约 50 万核**，在线集群 CPU 使用率可从 10% 提升到 60%+。

# 5　方法论提炼：共识 + 独门 + 对 MiniForum 的启发

## 5.1 可直接迁移到 MiniForum 的方法论（按成本从低到高）

| 方法论 | 大厂出处 | MiniForum 落地建议 |
|---|---|---|
| **容量 = 峰值流量 ÷ 单机容量** | 美团大促 | 先压测自己单实例能扛多少 QPS |
| **缓存选型框架 + 一键降级开关** | 美团《缓存那些事》 | 给热搜/热门列表加缓存，配降级开关 |
| **限流"木桶原理"：聚合单机限流 + 基础服务全局限流** | 京东架构师日记 | 推荐入口单机限流 + Redis 全局兜底 |
| **热点"加机器没用"→ 本地缓存 + 副本分散** | 京东多级缓存 | 热点帖上 Caffeine 本地缓存 |
| **压测标识透传 + 影子数据隔离** | 美团 Quake / 阿里双11 | 想压测先做"标识 + 影子"隔离 |
| **动态线程池（参数热改 + 监控）** | 美团 | 后续上线程池时把参数放配置中心 |
| **"降级牺牲功能、限流牺牲流量"** | 腾讯流量治理 | 推荐失败回热门兜底、打点失败不阻塞主链路 |
| **封网/封版（70% 问题由发版导致）** | 京东/阿里 | 大促前后不改代码 |

## 5.2 超大厂专属、MiniForum 现阶段不需要做

**单元化/异地多活**（阿里，RPO=0）、**混部降本**（京东/腾讯，万台级集群）、**神龙弹性/3 分钟 50 万核**（阿里）、**微信支付级混沌工程/5 个 9**（腾讯）、**JD-hotkey 百万级探测集群**（京东）——这些都是**量级到了才需要**。对 MiniForum：先把"单实例能扛、峰值有预案、多实例能扩展"这三件事做对，方法论已足够。

## 5.3 一句话总纲

> **大厂的高并发治理 = 压测摸清容量 → 缓存/预计算把算力压下来 → 限流/熔断/降级给峰值兜底 → 热点专项治理 → 弹性伸缩接住突发 → 混沌演练验证预案 → 大促封网保稳定**。
> 没有哪家靠"堆机器"硬扛——**堆机器是最后一道、也是成本最高的一道**，前六道才是日常功夫。
