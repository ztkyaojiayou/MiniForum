# 推荐系统微服务拆分方案（生产级架构参考）

> 创建：2026-08-25
> 主题：把 MiniForum 的推荐系统从"单体 + `@Profile` 生产适配"演进为**大厂生产级微服务形态**的架构参考。
> 配套：与《推荐系统深度调研报告-抖音版》《微博推荐调研》《推荐系统设计方案》《feed流架构调研与对比》并列。
> 说明：本文为**架构设计参考**，非代码变更计划；落地路径见 §9 分阶段迁移。当前项目仍是单体（一个可部署 jar），本方案描述的是"生产级应该长什么样"与"从现状怎么过去"。

---

## 0. 一句话核心洞察

**生产推荐系统 = 把"一个应用里的三层"拆成"多个可独立部署的服务"**，按两个正交维度切：

- **时效分层（三横）**：在线（毫秒）/ 近线（秒~分）/ 离线（小时~天）
- **功能域（多纵）**：召回 / 排序 / 特征 / 画像 / 数据管道 / 训练 / 管理

服务间靠 **Kafka / REST / gRPC** 通信；**数据所有权随服务走**（内存仓库不可跨服务共享，由中间件承载）；在线毫秒 SLA 与离线重计算彻底隔离。

---

## 1. 为什么要拆（目标）

| 诉求 | 单体痛点 | 拆服务收益 |
|---|---|---|
| 在线 SLA | ItemCF 重建 / 离线评估的大计算与在线接口同进程，互相拖累 | 在线毫秒级不被离线任务阻塞 |
| 独立扩缩容 | 只能整应用一起扩 | 在线按 QPS 扩、离线按数据量扩、Flink 按吞吐扩 |
| 故障隔离 | 近线模拟任务挂了影响在线 | Flink/离线任务挂不影响在线服务 |
| 独立发布 | 任何模块改动都要整体发版 | 各服务独立 CI/CD、灰度、回滚 |
| 独立演进 | 推荐算法改动受主应用耦合约束 | 可独立换模型/换语言（如 Python 训练 + Java serving） |

**反面约束**：拆分引入网络开销、分布式事务/一致性、运维复杂度。**小规模（演示/教学）不应拆**，本方案服务于"哪天真上生产推荐化"时的蓝图。

## 2. 大厂生产级总览：三横 × 功能域（天花板视角）

```
┌─ 在线层（毫秒、高 QPS）───────────────────────────────────────────┐
│  ① Rec-Server 在线推荐   召回→粗排→精排→重排→下发                  │
│     （大厂再拆：召回引擎 / 精排 GPU 推理 / 重排 / 网关）            │
│  ② 用户画像服务          长短期兴趣画像读写（在线特征来源之一）     │
│  ③ 物品/内容服务         物品元数据 + 内容理解（标签/向量）         │
│  ④ 图关系服务            关注/社交图谱（社交召回输入）              │
│  ⑤ 向量检索服务          ANN 向量库（Milvus / FAISS）              │
│  ⑥ 特征服务              在线特征拼装（防 training-serving skew）  │
├─ 近线层（秒~分）──────────────────────────────────────────────────┤
│  ⑦ Flink 流作业          实时统计 / 实时特征 / 增量画像 / 增量样本 / 索引增量 │
├─ 离线层（小时~天）─────────────────────────────────────────────────┤
│  ⑧ 日志 ETL → 数仓       行为日志清洗落仓                          │
│  ⑨ 特征平台              离线特征批量生产（训练集喂给模型）         │
│  ⑩ 训练平台              样本生成 → 模型训练 → 模型发布            │
│  ⑪ 离线构建任务          ItemCF / 向量 / 热度 / 相似度表 批量计算   │
│  ⑫ 评估 / AB 平台        离线评估 + 实验归因 + 推荐配置管理         │
└──────────────────────────────────────────────────────────────────┘
```

> 与抖音版调研 §2.7"实时性（三层架构）"一致：在线 Serving / 近线 Nearline / 离线 Offline。
> 说明：**不是所有项目都要 12 个服务**——12 个是"天花板"，拆到几层取决于规模（§5）。

## 3. 服务职责明细

| # | 服务 | 职责 | 关键技术 | 输入 → 输出 | 本项目对应模块（现状） |
|---|---|---|---|---|---|
| ① | **在线推荐 Rec-Server** | 漏斗编排：召回→融合→粗排→精排→重排→下发，带可解释理由；行为打点接收 | 规则 / 轻模型推理 / 多级缓存 | 请求(uid, ctx) → 推荐列表 | `recommend/service` `recall/` `rank/` `rerank/` `coldstart/` `RecommendController` |
| ② | **用户画像** | 长短期兴趣画像（话题/类目权重、时间衰减）、最近交互序列 | 读写分离（在线库 + 近线更新） | 行为 → 画像；查询 → 画像 | `recommend/feature`（UserProfileAggregator / FeatureService） |
| ③ | **物品/内容服务** | 帖子元数据、内容理解（分类/标签/话题/embedding） | 内容库 + NLP/向量化 | 帖子 → 特征化物品 | `PostService` + `PostRepository` |
| ④ | **图关系服务** | 关注/粉丝/二度关系，支撑社交召回与关注流 | 图存储（Redis/Neo4j） | 关系写 → 关系读 | `FollowRepository` + `feed/FollowFeedStore` |
| ⑤ | **向量检索** | ANN 近邻检索（双塔 embedding 召回） | Faiss / Milvus / HNSW | 向量 → TopK 候选 | 无（本项目 ItemCF 为主，无 embedding） |
| ⑥ | **特征服务** | 在线特征拼装，保证离线在线口径一致 | 特征存储（Redis/Feast） | 多源特征 → 打分特征 | `recommend/feature`（itemFeature / userProfile 组合） |
| ⑦ | **Flink 近线** | 行为流滑动窗口聚合实时特征、增量画像/样本/索引 | Flink（Kafka→窗口→Redis） | Kafka 行为流 → Redis 实时特征 | `FlinkRealtimeWindow`（src/prod）|
| ⑧ | **日志 ETL** | 行为日志清洗、落数仓、回溯 | Kafka → 数仓（Hive/StarRocks） | Kafka → 数仓表 | `recommend/behavior`（BehaviorLogRepository → behavior-log） |
| ⑨ | **特征平台** | 离线特征批量生产（训练特征、离线统计） | 批计算 | 数仓 → 特征表 | `recommend/feature`（离线侧） |
| ⑩ | **训练平台** | 样本生成、模型训练、模型/参数发布 | XGBoost / TF / PyTorch | 特征表 → 模型 | 无（弱训练侧：纯 Java 规则 + ItemCF） |
| ⑪ | **离线构建任务** | ItemCF 相似度表、热度分、冷启池批量计算 | 定时批任务 | 行为数据 → 模型表/索引 | `recommend/model`（ItemCfBuilder / ItemCfModelStore）+ `OfflineEvalScheduler` |
| ⑫ | **评估 / AB / 管理** | 离线评估指标、A/B 归因、推荐配置下发、运营报表 | 定时评估 + 实验平台 | 行为 → 指标；配置 → 服务 | `recommend/eval` `recommend/ab` `recommend/config` + 运营端 |

## 4. 数据流与服务间接口

### 4.1 主数据流（行为闭环跨服务）

```
用户行为 ──▶ ①在线推荐(打点) ──▶ Kafka("behavior-log")
                                    ├─▶ ⑦Flink近线 → Redis 实时特征 → ①在线排序 realtime 读
                                    ├─▶ ⑧日志ETL → 数仓 → ⑨特征平台 / ⑪离线构建
                                    └─▶ ②画像近线更新（用户实时兴趣）
发帖 ──▶ ③物品/内容 ──▶ Kafka("post-created") → ④图关系(feed fanout) + ①冷启池
①在线请求 ──▶ ②画像 + ④图关系 + ⑤向量 + ⑥特征 ──▶ 召回/排序/重排 ──▶ 下发
```

### 4.2 服务间通信方式

| 场景 | 通信方式 | 说明 |
|---|---|---|
| 在线请求串联（召回/精排/重排） | **进程内调用**（同服务）或 **RPC/gRPC**（已拆） | 在线链路延迟敏感，能进程内就不跨服务 |
| 服务解耦 / 削峰 / 必达 | **Kafka（异步事件）** | 行为、发帖事件、扇出 |
| 配置 / 画像 / 物品 读多写少 | **Redis + 直接读** | 低延迟查询 |
| 持久化 / 恢复 | **MySQL / 数仓** | 快照与历史 |
| 管理端→服务 | REST | 低频、内部 |

**原则**：在线链路尽量"进程内或就近"，跨服务只放"异步可容忍延迟"的路径（行为回流、扇出、离线同步）——避免为拆分而拆。

## 5. 按规模分档（拆到几层）

| 规模 | 拆法 | 例子 |
|---|---|---|
| 超大厂 | 12 服务全拆，在线再按召回/精排/重排独立部署 + 多级缓存 + 向量检索 | 抖音 / 微博 |
| 中型 | 在线推荐 1 + 近线 Flink + 离线任务 + 画像/物品各 1 | 中型内容平台 |
| **小规模（本项目）** | **4 服务即可**：在线 / 离线 / 近线 / 管理（§7） | MiniForum 生产化 |

## 6. 对标本项目现状（单体 + 生产适配）

现状架构（README"生产模式闭环审计"已描述）：**一个可部署 jar**，三层在应用内模拟或经 `@Profile("prod")` 切换中间件适配。

```
一个 jar（Monolith + @Profile 适配）
├─ 在线层   RecommendService（内存仓库 + Redis 适配读取）
├─ 近线层   内存 RealtimeFeatureWindow（演示） / FlinkRealtimeWindow（src/prod 独立作业）
├─ 离线层   ItemCfBuilder + OfflineEvalScheduler（应用内定时任务）
└─ 管理     配置(RecConfig) + AB + 运营端
```

| 现状 | 生产微服务目标 |
|---|---|
| 共享内存仓库（PostRepository / BehaviorLogRepository 直接注入） | 数据随服务走，跨服务走中间件 |
| 一个进程承担在线 + 离线 | 在线 / 离线 / 近线独立进程 |
| `@Profile("prod")` 切适配 | 每个服务独立部署，天然是"生产形态" |
| ItemCF 重建 / 离线评估 = 应用内定时任务 | 独立 offline-job 服务 |
| Flink 作业已在 src/prod（独立进程） ✅ | 已是正确形态，只需打独立部署单元 |

> 已具备的生产适配资产（可被拆分直接复用）：`KafkaBehaviorLogger/Consumer`、`KafkaPostCreatedProducer/Consumer`、`RedisRealtimeFeatureStore`、`RedisFollowRepository`、`RedisFollowFeedStore`、`NacosConfigService`、`FlinkRealtimeWindow`、`MySqlDataStore`。

## 7. 务实推荐拆法（4 服务）

```
admin ─────────────── 账号 / 运营 / 推荐配置 / AB 实验 / 评估报表
recommend-server ───── 在线推荐接口 + 行为打点 + 画像/物品特征（在线域）
offline-job ────────── ItemCF 构建 / 离线评估 / 冷启动池预热（定时任务）
flink-nearline ─────── FlinkRealtimeWindow 实时特征作业（独立进程）
```

### 7.1 各服务要点

| 服务 | 职责 | 进程/部署 | 数据 | 对外接口 |
|---|---|---|---|---|
| **admin** | 推荐配置下发、AB 分桶管理、离线评估报表、账号/运营 | 独立应用（低频内部） | 配置 + 评估结果 | REST（内部） |
| **recommend-server** | 在线推荐漏斗 + 行为打点 + 画像/物品特征读取 | 多实例（按 QPS 扩） | Redis（特征/画像/feed）+ 自持近线特征 | `/api/recommend/*`（对用户） |
| **offline-job** | ItemCF 相似度表构建、离线评估、流量池/冷启池预热、批量统计 | 独立应用或定时容器 | MySQL/数仓（行为快照） | 无对外（定时任务） |
| **flink-nearline** | Kafka 行为流 → 滑动窗口 → Redis 实时特征 | Flink 集群（独立） | Kafka + Redis | 无对外（流作业） |

### 7.2 关键数据归属

- **行为数据**：底座。写入口 = recommend-server 打点（或独立 gateway）→ Kafka；离线侧 = MySQL/数仓。
- **画像/实时特征**：Redis，由 flink-nearline 写、recommend-server 读。
- **关注关系 / feed inbox**：Redis，由 recommend-server（或独立图服务）维护。
- **配置**：Nacos，admin 写、recommend-server/offline-job 读（热更新）。
- **帖子/用户元数据**：MySQL，recommend-server 与 offline-job 只读回源。

### 7.3 用户三服务方案的说明

用户提议的 `admin / recommend / flink` 三服务切分**方向正确**（抓住了在线/近线/管理三个正交面）。唯一建议：**offline-job 的归属**要明确——

- 若并入 **recommend-server**：省一个服务，但 ItemCF 重建/离线评估的重计算会和在线接口同进程（回到单体痛点），需至少逻辑分模块、独立线程池/调度；
- 若并入 **admin**：管理端要扛离线计算，耦合运营与计算；
- **推荐独立 offline-job**：职责最干净，代价是多一个部署单元。

## 8. 关键设计原则与坑

1. **在线/离线隔离**：重计算（ItemCF、评估、特征批量）绝不放在线进程；在线进程禁止跑超过毫秒级的任务。
2. **数据所有权**：拆服务后**内存 `ConcurrentHashMap` 仓库不可跨服务共享**——这是从"单体适配"到"真微服务"的最大跳跃，必须落到 Redis/MySQL/Kafka。
3. **特征一致性（training-serving skew）**：离线训练用的特征口径必须与在线打分一致（同一个特征定义/版本），否则离线评估好看、线上翻车。
4. **幂等与至少一次**：Kafka 消费 / 行为回流允许重复投递，消费侧按 `(user_id, post_id, type)` 幂等；行为计数允许最终一致。
5. **冷启动池跨服务共享**：新帖流量池/赛马状态若放单服务内存，多实例会各算各的——生产放 Redis（TTL），offline-job 负责预热、recommend-server 负责读判晋级。
6. **AB 归因链路**：每次曝光/点击带 `expId`，从在线服务一路带到行为日志 → 离线评估按桶归因。
7. **不因拆分引入不必要的分布式事务**：推荐链路容忍最终一致，避免跨服务强事务。

## 9. 迁移路径（分阶段，每阶段可独立上线）

| 阶段 | 动作 | 收益 | 复杂度 |
|---|---|---|---|
| **0 现状** | 单体 + `@Profile("prod")` 适配（内存/中间件两态） | 演示可跑、生产适配齐备 | — |
| **1 逻辑分层** | 代码内把 在线(service/recall/rank/rerank) / 离线(model/eval) / 近线(stream) 边界显式化（包+配置开关），杜绝离线重计算阻塞在线线程 | 在线/离线物理上可分离的前提 | 低 |
| **2 近线独立** | 部署 `FlinkRealtimeWindow`（src/prod 已是独立作业），Kafka + Redis 真连 | 实时特征从"应用内模拟"变"独立近线" | 中 |
| **3 数据底座中间件化** | 行为→Kafka、画像/feed→Redis、持久化→MySQL 全真连（各适配类已就绪） | 消除共享内存依赖，可多实例 | 中高 |
| **4 admin 独立** | 管理/配置/AB/评估报表拆出独立应用，接 Nacos | 内部低频与对外隔离 | 中 |
| **5 recommend-server + offline-job 独立** | 在线推荐与离线构建拆成两个可部署单元 | 完成 4 服务形态，在线 SLA 独立保障 | 高 |

**当前状态**：处于**阶段 0**（单体 + 适配齐备），`src/prod` 的 Flink 作业 + MySQL 持久化已把阶段 2/3 的"适配代码"准备好，只差"真连中间件 + 部署编排"。
