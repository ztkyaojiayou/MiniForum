# 分布式系统四件套 · 网络抖动 / 超时 / 重试 / 幂等

## 0. 一句话全貌 + 因果链

> **网络抖动是前提，超时是止损，重试是自愈，幂等是保险。**

```mermaid

    A["网络不可靠（抖动）"] --> B["需要超时（止损线）"]
```

## 1. 网络抖动（Flaky Network / 部分失败）

### 1.1 是什么：分布式系统的"底层事实"

分布式系统里，跨进程/跨机器的调用，**网络不可靠**——延迟会波动（抖动）、可能丢包、可能中断、响应可能丢失。这不是异常，是**默认状态**。

**关键认知**：单体应用里一次调用是"确定的"（同一进程内，内存操作），所以你能保证结果；分布式里一次调用是"不确定的"，你**永远无法确定远端到底发生了什么**。

### 1.2 分布式系统的"8 大谬误"（为什么人们老是犯错）

Peter Deutsch 总结了分布式计算的 8 个常见错误假设（人们默认"以为"这些成立，其实全错）：

| # | 谬误 | 现实 |
|---|---|---|
| 1 | 网络是可靠的 | 会丢包、会断、会抖动 |
| 2 | 延迟为零 | 跨机器调用是毫秒~秒级 |
| 3 | 带宽是无限的 | 会拥塞 |
| 4 | 网络是安全的 | 会被攻击 |
| 5 | 拓扑不会变 | 节点/连接会增删 |
| 6 | 只有一个管理员 | 多团队、多机房 |
| 7 | 传输成本为零 | 有协议/序列化开销 |
| 8 | 环境是同质的 | 软硬件、配置各不相同 |

**最核心的一条就是 #1：网络不可靠。** 本项目的"零中间件"单体形态里你感觉不到它；一旦拆到多实例/多服务，它立刻成为常态。

### 1.3 抖动的来源

网络栈、负载、**GC 停顿**（Java 应用暂停几秒，调用方感知到的是"超时"）、带宽争用、防火墙、丢包重传、连接重建、热迁移……都让延迟从 1ms 波动到几百 ms，甚至超时。

### 1.4 部分失败（partial failure）：一切麻烦的根源

当你调用一个服务，响应丢了，你**无法确定**是哪种情况：

```
① 服务器没收到请求？
② 收到了，正在处理？
③ 处理完了，但响应在回传路上丢了？
④ 服务器处理到一半崩了？
⑤ 服务器收到了，但超慢，还没处理完？
```

> 你不知道"请求到底有没有被处理"——**这是分布式里所有麻烦（超时/重试/幂等）的起点**。

### 1.5 具体例子

下单服务 A 调用支付服务 B：

```
A 给 B 发"扣款 100 元"，等了 3 秒没响应。
A 能确定什么？什么都确定不了：
  - 可能 B 没收到 → 没扣款
  - 可能 B 扣了款但响应丢了 → 扣了
  - 可能 B 扣到一半挂了 → 状态未知
A 唯一的正确姿势：把这次调用当"不确定"，交给超时/重试/幂等去处理。
```

### 1.6 心智

> 不要把网络当可靠的。**超时 / 重试 / 幂等，全部是"对网络不可靠的防御"**——先接受"可能失败、可能重复"，再设计防御。

## 2. 超时（Timeout）

### 2.1 是什么：给每次外部调用设"最多等多久"的预算

**没有超时 = 线程可以无限阻塞。** 这是最常见的雪崩根因。

### 2.2 为什么必须（线程占用 / 雪崩）

```
下游 B 变慢（RT 5ms → 2s）
  → 没有超时：A 的每个请求线程阻塞在等 B（2s）
  → A 的 200 个线程全被占满
  → 新请求排队 → A 也挂 → 雪崩往上蔓延
```

**超时是给不可靠网络设的"止损线"**：到点就放弃，把线程释放出来。

### 2.3 三种超时 + 分级

| 超时 | 含义 | 例子 |
|---|---|---|
| 连接超时（connect timeout） | 建立连接最多等多久 | 500ms |
| 读/响应超时（read timeout） | 发出请求后等响应最多多久 | 1s |
| 总超时（total / call timeout） | 整次调用（含重试）的预算 | 3s |

**分级超时**：不同依赖设不同预算——快路径（本地缓存 miss 回源）100ms，慢路径（离线/批处理）10s。不能一刀切。

### 2.4 超时值怎么定：基于 P99，不是平均值

- 平均值会被长尾带偏（1 个 10s 的异常把 99 个 1ms 的平均拉到 100ms）；
- 正确做法：统计 **P99（99% 的调用在多少 ms 内完成）**，超时 = P99 × 安全系数（如 ×2）；
- **动态超时（EMA）**：按历史响应时间滚动调整（`EMA = α×上次RT + (1-α)×上次EMA`），如微信后台用"平均排队时间"判断过载——超 20ms 以降速因子过滤，低于 20ms 逐渐放行（"快速降低、缓慢提升"防震荡）。

### 2.5 超时传递（关键）

**下游超时必须比上游短**：

```
A（超时 2s）→ 调用 B（超时 1s）→ 调用 C（超时 500ms）
```

否则：A 等 2s 超时了，但 B 还在等 C（1s），B 还在处理——**上游先放弃了，下游还在浪费资源**。超时像水流一样从上游到下游递减。

### 2.6 具体例子：慢 SQL 无超时的后果

本项目 prod 用 MySQL（HikariCP 连接池）：

```
一个慢 SQL 跑 30s（缺索引/大表扫描）
  → 连接被占 30s
  → HikariCP 默认 maximum-pool-size=10，10 个连接全被占住
  → 第 11 个请求拿不到连接 → 排队 → 请求堆积
  → 没有 connectionTimeout → 无限等连接 → 线程全占住 → 雪崩
```

修复：设 `connectionTimeout`（拿到连接最多等多久）+ `socketTimeout`（SQL 执行最多多久）。

### 2.7 坑

- **不设超时** = 线程可无限阻塞（最常见根因）；
- **设太大** = 止损不及时，线程被长占；
- **设太小** = 正常慢请求被误杀（所以基于 P99 而非平均）；
- **忘了超时传递** = 上游放弃了下游还在跑。

## 3. 重试（Retry）

### 3.1 是什么 / 为什么需要

调用失败/超时后，再试一次或几次，期望这次成功。**网络抖动是暂时的**——一次抖动，重试就能自愈。重试是"给抖动一个机会"。

### 3.2 为什么危险：重试风暴（真实事故）

下游故障时，**所有调用方同时疯狂重试** → 流量指数放大 → 把原本能自愈的下游**彻底打挂** → 雪崩。

**GitHub 2026-08 宕机 8 小时**（官方复盘）：VS Code 客户端/边缘持续重试，Copilot 令牌流量被放大**约 10 倍**，叠加自动扩缩容盲区，形成级联故障。**重试是双刃剑：自愈或雪崩，取决于有没有节制。**

### 3.3 正确重试的四个要素

| 要素 | 怎么做 | 反例 |
|---|---|---|
| **只重试可重试的失败** | 连接失败/超时可重试；**业务错误（400/404/库存不足/余额不足）不可重试** | 重试扣款 → 重复扣款 |
| **只重试"可能没被处理"的** | 连接超时（服务器可能没收到）可重试；收到明确错误响应**不**重试 | 服务器返回 500 还重试 |
| **指数退避 + 抖动** | 1s → 2s → 4s + 随机抖动（防所有客户端同时重试的"惊群"） | 所有客户端固定 1s 同时重试 |
| **限制次数** | 最多 N 次（如 3 次），防无限放大 | 无限重试 → 重试风暴 |

### 3.4 退避算法（公式）

```
固定退避：delay = 固定值（1s）            ← 简单但容易惊群
线性退避：delay = base × n（1s, 2s, 3s）   ← 稍微错开
指数退避：delay = base × 2ⁿ（1s, 2s, 4s） ← 标准
指数 + 抖动：delay = min(base × 2ⁿ, max) + random(0, jitter)  ← 生产标准（防惊群）
```

**抖动（jitter）的意义**：没有抖动，N 个客户端都在第 1s/2s/4s 同时重试 → 每次重试都是一次"惊群"；加随机抖动让重试时间错开，下游才喘得过气。

### 3.5 具体例子：两个对比

**无节制重试（错）**：
```
10 万个客户端同时调用支付（支付卡顿）
  → 全部超时 → 全部固定 1s 后重试
  → 10 万 × 2 = 20 万请求同时砸向支付
  → 支付被彻底打挂 → 客户端又重试 → 指数放大 → 雪崩
```

**正确重试（对）**：
```
10 万个客户端调用支付（支付卡顿）
  → 超时 → 指数退避 + 抖动（1s + 随机、2s + 随机、4s + 随机）
  → 每次重试请求错开，支付只承受"能扛住的量"
  → 支付恢复后，重试陆续成功 → 自愈
```

### 3.6 坑

- 对**不可重试的失败**（业务错误）重试 → 重复扣款/重复发帖；
- 不加退避 → 惊群；
- 不限次数 → 重试风暴；
- 重试后**响应重复** → 必须配幂等（下一节）。

## 4. 幂等（Idempotency）

### 4.1 是什么 / 为什么需要

**同一个操作执行多次，效果和执行一次一样。** 为什么需要：网络不可靠 + 超时 + 重试 = **同一个请求可能被发送多次**（响应丢了客户端重试、或用户双击）。幂等让"重复"**无害**。

### 4.2 哪些操作天然幂等

| 方法 | 幂等？ | 说明 |
|---|---|---|
| GET | ✅ | 查询多次结果一样 |
| DELETE | ✅ | 删两次结果一样 |
| PUT | ✅ | 覆盖写，多次结果一样 |
| **POST** | ❌ | **默认不幂等**——重复 POST 会重复创建（发帖/下单/扣款）→ 必须靠幂等 key |

### 4.3 实现方式

| 方式 | 机制 | 例子 |
|---|---|---|
| **唯一约束**（DB） | `(user_id, post_id)` 唯一，重复 insert 被拒 | 本项目点赞：同一用户对同一帖只能一条 Like |
| **幂等 key / 请求 ID** | 客户端带 key，服务端记住"这个 key 处理过"，重复请求返回首次结果 | 本项目发帖的 `Idempotency-Key` |
| **Redis SETNX** | `SET key 1 NX EX` 原子占位，只成功一次 | 本项目 `RedisIdempotencyStore`（P0 已落地） |

### 4.4 幂等 key 的设计（工程细节）

```
客户端：每次"逻辑提交"生成一个 UUID 作为 Idempotency-Key，随请求头发送
服务端：
  1. getCompleted(key) → 命中 → 直接返回首次结果（防重放）
  2. acquire(key)  → SET key PROCESSING NX EX ttl   ← 原子占位，失败说明"正在处理中"
  3. 执行业务
  4. complete(key, resultId) → SETEX key ttl resultId  ← 记住结果
  5. 异常 → release(key)  → 下次可重试
```

**双保险**：Redis 幂等表（快）+ DB 唯一索引（最终防线）——Redis 可能丢，DB 唯一约束兜底（本项目发帖幂等 + Like 唯一约束就是这个组合）。

### 4.5 at-least-once 与幂等是一对

> **投递是"至少一次"（at-least-once），消费端必须幂等。**

消息队列/重试把同一个请求可能投递多次；消费端只有幂等才能让"重复投递"无害。这是"重复是常态，幂等是保险"的完整表述。

### 4.6 具体例子：发帖幂等（本项目的实现）

本项目 P0 已落地发帖幂等（`IdempotencyStore` + `Idempotency-Key`）：

```
用户点"发帖" → 网络抖动，请求超时 → 客户端重试（同一 Idempotency-Key）
  → 服务器收到两次发帖请求
  → 第一次：acquire(key) 占位成功 → 发帖 → complete(key, postId)
  → 第二次：getCompleted(key) 命中 → 直接返回第一次的 postId，不再发帖
  → 用户看到"发帖成功"一次，没有重复微博
```

**没有幂等**：一次抖动 + 一次重试 = **两条重复微博**。

### 4.7 坑

- 幂等 key **复用/冲突**（不同操作用了同一个 key → 误判重复）；
- **TTL 过短**（窗口内没处理完，key 过期 → 重试被当成新请求）；
- 幂等 key 和分布式锁**不是一回事**：锁是"并发互斥"，幂等是"重复去重"——虽然都用 SETNX，语义不同（本项目发帖幂等与 TrafficPool 原子入池是两种用途）。

## 5. 四件套的关系链 + 完整场景

### 5.1 因果链

```
网络不可靠（抖动）──→ 需要超时（止损线）
                       └─→ 超时触发 ──→ 需要重试（自愈）
                                          └─→ 重试导致重复 ──→ 需要幂等（让重复无害）
```

### 5.2 完整场景：发帖（一次抖动引发的连锁）

```
① 用户点"发帖" → 网络抖动，请求卡住
② 客户端超时（2s 到了）→ 放弃这次，但"不确定服务器收到没有"
③ 客户端重试（指数退避 + 抖动后，第二次发帖，带同一 Idempotency-Key）
④ 服务器实际收到了第一次请求，处理完了，只是响应在回传路上丢了
⑤ 第二次请求到达 → 幂等 key 命中 → 直接返回第一次的 postId
⑥ 用户看到"发帖成功"一次，没有重复微博
```

**缺任何一环**：没有超时 → 线程被占死；没有重试 → 一次抖动就失败；没有幂等 → 重试造成重复。**四件套缺一不可。**

### 5.3 更复杂：跨服务调用链（超时传递 + 幂等叠加）

```
A（发帖）→ 超时 3s → B（内容审核）→ 超时 2s → C（存储）
  A 调用 B：连接超时 → 重试（指数退避）
  B 调用 C：B 对 C 的超时(2s) < A 对 B 的超时(3s)   ← 超时传递
  A 的重试 + B 的重试 → C 可能收到同一内容的多次写入
  → C 必须幂等（以内容 hash 或 requestId 去重）
```

**每个 hop 都要超时（且递减）+ 重试（有节制）+ 幂等（去重）**——这就是为什么"四件套"是分布式调用的标配。

## 6. 没做过 vs 做过的人，对这四件事的认知

| 概念 | 没做过的人会想 | 做过的人会想 |
|---|---|---|
| 网络 | "网络是可靠的，一次调用必然成功" | "**网络不可靠，任何失败都当'可能发生过'**" |
| 超时 | "不设超时，慢就等" | "每个调用都有**超时预算**，基于 P99，且超时传递（下游短于上游）" |
| 重试 | "失败了就重试，直到成功" | "**有节制重试**：只重试可重试的、指数退避+抖动、限次数" |
| 幂等 | "操作天然只执行一次" | "**所有写操作都可能重复，默认要幂等**（at-least-once + 幂等 key + DB 唯一约束）" |

**一句话**：做过的人**默认所有写操作都可能重复、所有调用都可能超时**，然后按这四件事把系统加固；没做过的人把这些当"运气好就不会发生"。

## 7. 落到本项目（已有的 / 缺的）

| 四件套 | 本项目现状 |
|---|---|
| **幂等** | ✅ **已落地（P0）**：发帖 `Idempotency-Key` + `RedisIdempotencyStore`（SET NX EX）+ 点赞唯一约束（DB 双保险） |
| **超时** | ⚠️ 部分：`application-prod.yml` 已配 HikariCP `connectionTimeout`（P1-3）；但业务调用（下游 RPC/MySQL socket 超时）未系统化 |
| **重试** | ❌ 未落地：outbox relay 是 at-least-once 但无重试退避控制；消息消费无幂等去重（README 已知取舍"Kafka 自动提交 offset 可能重复计数"） |
| **网络抖动** | 认知前提（多实例后成为常态）；当前单体形态暂不明显 |

> **结论**：四件套里幂等已经做对了；**超时（系统化）+ 重试（有节制 + 幂等去重）是 P3 阶段要补的**——它们和限流/熔断/降级一样，是"多实例之后"的加固项。
