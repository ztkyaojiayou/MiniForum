## 二、P0：现在就能落，单实例立刻受益

### P0-1 画像预聚合/缓存【② 单机效率 · 工作量 M】

**现状**：`UserProfileAggregator.build(userId)` 每次推荐请求把该用户**全部行为**扫一遍做"权重×0.7^天数衰减"聚合；`RecommendService.recommend` 里 `recallService.recall`（各召回通道）和 `coldStartFallback` 都会触发 `userProfile`——**一次推荐可能现算多次画像**。这是单实例最大的隐性算力浪费（高并发铁律"能预计算的不实时算"被违反）。

**怎么做**：
1. 加一层**画像缓存**：`ConcurrentHashMap<Long, UserProfile>` + 短 TTL（如 60s）；
2. 行为回流时（`BehaviorEventQueue` 订阅者里）对相关 userId 的缓存**主动失效**，保证时效；
3. 生产可复用 `RedisUserProfileStore`（已是 read-through，按需现算后写 Redis），改成"行为回流时增量写 Redis"。

**收益**：消除单请求最大重复计算，时延/吞吐直接受益。
**参考**：三层模型② / 抖音"轻在线重离线"（下游 QPS 降 1/10）。

### P0-2 物品特征预聚合/缓存【② · M】

**现状**：`InMemoryFeatureService.itemFeature(postId)` 每次**现算聚合**点赞/评论/收藏/转发/浏览/时长（多次 countByPostId）；`RecommendService.topHotPosts()` 会对**全站每个帖子**调一次 `itemFeature`——排序层每个候选也各调一次。QPS 一上来全是重复 count 查询。

**怎么做**：热度分/计数改"**写时累加**"（like/comment/favorite/repost/view 时更新计数缓存，替代读时 countByPostId）或近线聚合写 `item:feature:{postId}` 缓存（TTL 几十秒），`itemFeature` 优先读缓存、miss 才回源。

**收益**：排序/热门路径从"N×count"变"一次缓存读"。
**参考**：三层模型② / 美团《缓存那些事》选型框架。

### P0-3 推荐失败热门兜底（降级）【③ 稳定性 · S】

**现状**：`RecommendService.recommend` 无任何 try-catch——召回/排序/重排任一步异常直接 500。现有 `coldStartFallback`/`topHotPosts()` 只服务"冷用户"，不是"异常兜底"。

**怎么做**：主链路包 `try-catch`，异常时返回 `topHotPosts()` 热门兜底 + 记 warn 日志 + 可加降级开关（`app.rec.degrade-hot-fallback`）。这是**最便宜收益最大的稳定性改动**。

**收益**：峰值/故障下推荐接口不 500，降级到热门榜。
**参考**：大厂方法论"降级牺牲功能、限流牺牲流量"。

### P0-4 六路召回并行化【② · S~M】

**现状**：`RecallService.recall` 串行 `for (RecallChannel channel : channels)` 依次跑 6 路，耗时是 6 路**求和**。

**怎么做**：6 路用 `CompletableFuture.supplyAsync(channel.recall(...)).allOf().join()` 并行（各通道互不依赖），配独立小线程池（避免占满 Tomcat 线程，参考美团动态线程池/腾讯"并发化"）。

**收益**：召回耗时从"6 路和"变"6 路 max"，整条漏斗 P95 明显下降。
**参考**：单pod问题 1.1（异步化/并发化）。

### P0-5 行为打点异步化【②③ · M】

**现状**：`InMemoryBehaviorLogger.log` **同步**落库（BehaviorLogRepository）+ **同步**广播（BehaviorEventQueue）——曝光/点击是最频繁的写操作，每次推荐逐条记 EXPOSE 都同步走完。

**怎么做**：打点改"先入内存队列 → 后台线程批量落库 + 发布"（行为允许最终一致，丢一点可接受）。`!prod` 先做；`prod` 本就该走 Kafka 异步。

**收益**：把最频繁的写从请求路径摘掉，降时延、防打点拖慢主链路。
**参考**：大厂"异步削峰填谷"。

## 三、P1：缓存与稳定性补全

### P1-1 热搜/热门/列表缓存【② · M】

**现状**：`topHotPosts()` 每次全站现算热度排序；热搜（`HeatAggregator`）内存现算。

**怎么做**：热门榜/热搜榜/未登录推荐**整页缓存**（短 TTL，如 30~60s）+ **降级开关**（对齐美团"一键关闭缓存降级"）。

**收益**：高频读路径命中缓存；降级开关可用于峰值自救。
**参考**：大厂方法论 5.1（缓存选型 + 降级开关）。

### P1-2 缓存三兄弟防护【② · S】

**现状**：加了缓存后暂无防护。

**怎么做**：空值短 TTL 缓存（防穿透）、互斥重建/单飞（防击穿）、TTL 加随机抖动（防雪崩）。推荐结果缓存尤其要防"不存在的 key 穿透"。

**收益**：缓存不会成为新的故障点。
**参考**：单pod问题 1.5。

### P1-3 连接池/线程池参数治理 + 慢 SQL【②（prod） · S~M】

**现状**：默认 HikariCP `maximumPoolSize=10` / Tomcat `maxThreads=200`；`itemFeature` 的 count 聚合 SQL 若缺索引会占连接。

**怎么做**：显式 `connectionTimeout`；池大小按 `(core×2)+disk` 参考公式调；给 `likes/comments/favorites` 的 `countByPostId` 建索引；需要时多池分离（长事务池/实时查询池）。

**收益**：prod 下避免"慢 SQL 占满连接→请求堆积→雪崩"。
**参考**：单pod问题 1.2（HikariCP 官方池大小论证）。

### P1-4 入口单机限流【③ · S】

**现状**：无任何限流。

**怎么做**：加一个单机限流 Filter（自研令牌桶或 Guava RateLimiter），对 `/api/recommend/**`、`/api/posts/**` 等入口限流；**按实例均分配额**（京东"木桶原理"：聚合业务系统用单机限流，扩容友好）。超限返回 `429` + 友好提示。

**收益**：第一道防线，防突发打满线程/连接。
**参考**：大厂方法论 5.1（限流木桶原理）。

### P1-5 请求 traceId + 结构化日志【③ · S】

**现状**：无 trace，跨层排查靠肉眼。

**怎么做**：入口 Filter 生成 `traceId` 入 MDC，日志带上；异步线程池注意透传 MDC。

**收益**：一次请求的日志可串起来，是压测/排障的前提。
**参考**：单pod→多pod 2.9。

## 四、P2：多实例资格（真扩展前必做）

> **✅ 已全部落地**（P0/P1/P2 全批次完成）：
> - `969e63b` P2-5 调度改造（XXL-Job 生产适配，演示保持 @Scheduled）
> - `f43c373` P2-4 Session 外置（Spring Session Redis，演示保持 Tomcat session）
> - `9679999` P2-2 冷启动池状态落 Redis（TrafficPool/NewItemPool store 接口 + InMemory/Redis 双实现）
> - `a3940cb` P2-1 行为读切换 + P2-3 ItemCF 离线发布（离线构建→Redis→在线读取闭环）
>
> 单实例阶段无感，但生产适配代码已就位；真上多实例时 `-Pprod` + prod profile + 配好中间件即可水平扩展。

### P2-1 行为事实源落 ClickHouse【① · M~L】

> ✅ **已落地（`a3940cb`）**：`ItemCfModelStore` 重建数据源 prod 切 ClickHouse 全量；离线评估/ItemCF 构建已读 ClickHouse。
> 注意：**在线画像/物品特征有意不切**（JDBC 延迟不可进请求路径，保持 Redis+内存，注释注明"在线快、离线切"）——比原方案更贴合"轻在线重离线"。

**现状**：prod 已有 `ClickHouseBehaviorStore`（Kafka Engine 摄入 ✅），但画像/ItemCF/评估仍读内存 `BehaviorLogRepository`。

**怎么做**：按 `数据存储矩阵`，prod 下画像/ItemCF/离线评估切 ClickHouse 读；或近线聚合写 Redis 供在线读。**演示（!prod）保持内存**。

**收益**：在线进程不再持有全量行为内存库，多实例才共享同一事实源。
**参考**：三层模型① / 数据存储矩阵 §3。

### P2-2 冷启动池 / TrafficPool 状态落 Redis【① · M】

> ✅ **已落地（`9679999`）**：`TrafficPoolStore`/`NewItemPoolStore` 接口 + InMemory（!prod）/Redis（prod）双实现；
> `notifyCreated` 判重改 `putIfAbsent`（SETNX 原子入池，多 pod 幂等）。多 pod 读改写非原子局限已文档化，升级路径（HINCRBY/Lua）写入注释。

**现状**：`TrafficPool.states` / `NewItemPool.alphaBeta` 是进程内 `ConcurrentHashMap`，多实例各算各的；`notifyCreated` 的 `containsKey` 判重是进程内的（多 pod 会重复入池）。

**怎么做**：prod 下状态落 Redis（`traffic:{postId}` = PostState、`coldstart:{postId}` = αβ，TTL 管理）；判重改 Redis 原子操作（`SETNX`）。

**收益**：赛马/冷启动跨实例一致。
**参考**：单pod→多pod 2.5（分布式幂等/去重）。

### P2-3 ItemCF 离线构建 → 发布【① · M~L】

> ✅ **已落地（`a3940cb`）**：`ItemCfModel` 加 `getSimMap/from`（Jackson 可序列化）→ `ItemCfModelRedisStore`（`itemcf:latest`）；
> offline-job `ItemCfModelPublisher` 从 ClickHouse 构建发布 + XXL-Job handler `itemcf-publish`；在线 `get()` 优先读 Redis 已发布模型
> （多实例共享 + **顺手修掉每请求 count()**），未发布才本地重建兜底并回写 Redis。

**现状**：`ItemCfModelStore` 在线进程内按行为数变化自动重建，不落盘不发布——每实例各算各的。

**怎么做**：离线构建模型序列化发布（写 Redis/文件），在线加载；或至少把"重建"收敛到单一职责（offline-job），在线只读。

**收益**：模型跨实例一致、不重复重算。
**参考**：三层模型① / 微服务拆分方案 §6。

### P2-4 Session 外置【① · M】

> ✅ **已落地（`f43c373`）**：Spring Session Redis，`SessionConfig`（demo-runner src/prod，@Profile("prod")）+ 依赖只在 prod profile，
> Controller 零改动（透明替换 HttpSession）；演示保持 Tomcat session。新增 `AuthControllerSessionTest` 守护 session 契约。

**现状**：全部控制器直接 `HttpSession`（Tomcat 内存）——多 pod 必踩坑（用户随机掉登录）。

**怎么做**：`Spring Session Redis`（把 Session 外置）或 JWT。**单实例阶段不用做**。

**收益**：多 pod 登录态不丢。
**参考**：单pod→多pod 2.2。

### P2-5 定时任务分布式锁【③ · S~M】

> ✅ **已落地（`969e63b`）**：采用 **XXL-Job 中心化调度**（非 ShedLock——生产标准、无空醒，但需调度中心）：
> `app.scheduling.mode` 开关（local/xxl）防双跑 + 5 个低频 @Scheduled 拆「守卫+doXxx」+ `XxlJobWebConfig`/`XxlJobOfflineConfig` 执行器。
> outbox relay（1s 轮询）例外：不适合 XXL-Job，保持自调度（重复投递 at-least-once + 幂等可接受）。

**现状**：6 处 `@Scheduled`（DataStore 30s、RealtimeFeatureWindow 5s、TrafficPool 1h、SimulatedActivityService 15min、PostService 3am、OfflineEvalScheduler 30min），多 pod 全部重复跑——最严重是 `SimulatedActivityService` 重复造帖造互动。

**怎么做**：ShedLock（Redis/DB 锁），同一任务集群内最多一个节点执行。

**收益**：多 pod 不重复执行。
**参考**：单pod→多pod 2.3。

## 六、明确"不做"清单（量级没到，别过度工程）

| 技术 | 为什么不做 |
|---|---|
| 分库分表 | 数据量远未到单库瓶颈；业界共识"能不分尽量不分"（会引入跨分片查询/分布式事务复杂度） |
| 单元化 / 异地多活 | 阿里 RPO=0 那套，需要独立机房 + 数据分片 + 强一致存储，量级差 6~7 个数量级 |
| 混部 / 神龙弹性 | 万台集群才划算 |
| 5 个 9 / 微信支付级混沌工程 | 保障级别不匹配 |
| JD-hotkey 探测集群 | 热点治理用"本地缓存 + 空值防护"足够，先做 P1-2/P3-3 |

## 七、落地建议与验收

1. **每项配单测**（沿用项目现有 JUnit 风格，如 `TrafficPoolOnPostCreatedTest`）：P0-1/P0-2 测缓存命中与失效、P0-3 测异常兜底、P0-4 测并行结果与串行一致、P0-5 测异步不阻塞。
2. **跑测试用 JDK 17**：`JAVA_HOME='D:\devSoftWare\jdk17\jdk-17.0.19+10' mvn -pl forum-recommend-server -am test`（或全量 `mvn test`）。
3. **建议顺序**：P0-3（S，兜底）→ P0-4（S~M，并行）→ P0-1/P0-2（M，预聚合）→ P0-5（M，异步）→ P1-4（S，限流）→ P1-1/P1-2（M，缓存）→ P1-3/P1-5 → P2 待定多实例再动。
4. **可观测性先于优化**：做 P0 之前建议顺手把 P1-5（traceId）加上，否则优化效果没有度量手段。
