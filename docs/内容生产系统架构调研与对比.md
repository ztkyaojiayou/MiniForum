# 内容生产系统架构调研与对比（发帖写路径 + 帖子全生命周期）

> 创建：2026-08-26
> 主题：内容生产（写路径）系统的可靠设计——从"用户输入"到"可被分发"，一条帖子的完整生命周期；并与 MiniForum 现状对比。
> 配套：与《内容分发系统架构调研与对比》对偶（分发管"读/展示"，生产管"写/产生"，两者经事件总线衔接）。
> **关键约束**：生产增强能力（幂等/Outbox/审核/异步管道）主要在 `-Pprod` 生产模式实现；演示版酌情落地，**必须不破坏演示**（内存等价闭环，零中间件可跑）。

---

## 0. 一句话核心洞察

**内容生产系统 = 一条帖子从"用户输入"到"可被分发"的可靠写路径**：
`校验/幂等 → 内容处理 → 状态机 → 落库 → 事件发布（Outbox 必达）→ 分发端消费 → 用户看到`。

生产模式承载全部能力；演示版保留**最小等价闭环**（发帖→落库→同步事件→展示），生产增强项按"不破坏演示"原则缺位或内存模拟。

---

## 1. 全生命周期总览（一条帖子的旅程）

```
用户输入（发帖表单）
  → ① 参数校验 + 内容规范化（标题/正文/分类/标签）
  → ② 幂等（Idempotency-Key，防重复提交）
  → ③ 内容处理（话题提取 / @提及识别 / 敏感词 / 审核 / embedding）
  → ④ 落库（主存储 + 全局唯一 ID）
  → ⑤ 事件发布（同事务写 outbox → Relayer → Kafka "post-created"）   ← 写读分界
  → ⑥ 分发端消费（关注流扇出 / 搜索索引 / 推荐冷启 / 统计 / 通知）
  → ⑦ 用户展示（最新流 / 关注流 / 推荐流 / 搜索 / 详情）
```

**写读分界在 ⑤**：⑤ 之前是"生产"，⑥ 之后是"分发"（读/展示，见配套文档）。生产系统保证"写进来且不丢"，分发系统保证"能看到且快"。

## 2. 生产侧（写路径）各环节深度

### 2.1 参数校验 + 内容规范化

| 项 | 设计 | 本项目现状 |
|---|---|---|
| 入参校验 | DTO + `@Valid`（标题长度/正文上限/标签数） | ✅ `PostCreateDTO` + JSR-303 |
| 内容规范化 | 去空白、分类兜底、标签去重/限长 | ✅ `normalizeTags` / `normalizeCategory` |
| 话题提取 | 内容 `#话题#` 正则提取、去重、限 5 | ✅ `extractTopics` |
| @提及识别 | `@用户名` 识别 → 通知 | ✅ `notifyMentions` |

### 2.2 幂等（防重复发帖）

**问题**：网络重试 / 用户双击 / 前端超时重发 → 同一内容发两遍。

**主流方案**：客户端生成 `Idempotency-Key`（UUID），随请求头发送；服务端 `key → postId` 缓存，同 key 重复请求直接返回首次结果。

- 存储：Redis（key → postId，TTL 数分钟）或 DB 唯一索引。
- 本项目现状：❌ **无幂等**（双击会发重）——生产增强项，演示可缺位。

### 2.3 内容处理（生产侧的"增值"）

| 处理 | 同步（快，可留请求内） | 异步（慢，走队列） |
|---|---|---|
| 话题/@提及 提取 | ✅ 本项目同步 | — |
| 敏感词/审核 | 量小可同步 | 生产走审核队列（先审后发/先发后审） |
| embedding/向量化 | — | 异步（推荐召回输入） |
| 标签补全/分类 | 同步 | 异步（内容理解模型） |

**原则**：快处理同步（不阻塞且毫秒级），慢处理异步（审核/embedding 进队列，发帖立即返回）。
本项目现状：话题/提及同步 ✅；审核/embedding ❌（演示无需）。

### 2.4 状态机

```
草稿(DRAFT) ──发布──▶ 已发布(PUBLISHED) ──编辑──▶ 已发布(改内容，重新提取/发事件?)
                         │
                         ▼ 删除（软删）
                      回收站(DELETED) ──恢复──▶ 已发布
                         │ 30 天
                         ▼ 彻底删除
                      物理删除（级联清评论/点赞/收藏/通知）
```

- 软删：立即可恢复，列表中不可见（`deleted=true` 过滤）。
- 定时清理：超过保留期彻底删除 + 级联清理。
- 本项目现状：✅ 完整实现（`createPost(草稿/发布)`、`updatePost`、`deletePost`、`restorePost`、`purgeExpiredPosts` 30 天清理、回收站查询）。

### 2.5 落库与 ID 生成

| 项 | 生产 | 演示 |
|---|---|---|
| 主存储 | MySQL（MySqlDataStore 快照） | 内存 + `data/*.json` |
| ID 生成 | Snowflake（全局单调带时间戳） | `Post.nextId()`（AtomicLong，单调） |

- Snowflake 价值：全局单调 + 时间戳可解析 → 天然游标（`max_id`/`since_id` 直接用 ID），跨实例不冲突。
- 本项目：AtomicLong 单调（单机够用），生产可换 Snowflake。

### 2.6 事件发布（衔接分发，保证必达）

```
发帖事务：INSERT posts + INSERT outbox(post_id, status=PENDING)   ← 同一事务，原子
  → Outbox Relayer（定时轮询 或 CDC/Debezium 监听 binlog）
  → 发 Kafka "post-created" → 成功更新 outbox status=DONE
  → 下游消费者（fanout / 搜索索引 / 推荐冷启 / 统计 / 通知）
```

- **必达**：事件先落 outbox 表，Relayer 兜底保证最终都发出去（进程崩溃不丢）。
- **幂等**：下游以 `(post_id, consumer)` 为幂等键。
- 本项目现状：`postCreatedNotifier.notify`（生产 `KafkaPostCreatedProducer` → Kafka；演示 `InMemoryPostCreatedNotifier` 同步 fanout）。**无 Outbox**——生产增强项。

## 3. 全生命周期：一条帖子从生产到最终展示（逐阶段追迹）

以"用户 A 发一条帖子，用户 B（A 的粉丝）最终在关注流看到"为例，逐阶段走一遍：

| 阶段 | 输入 → 处理 → 输出 | 生产模式（-Pprod） | 演示模式（默认） | 关键点 |
|---|---|---|---|---|
| **① 提交** | 表单 → 校验/规范化 → `PostCreateDTO` | 同 | 同 | DTO + @Valid |
| **② 幂等** | `Idempotency-Key` → 查重 → 放行/返回首次 | ✅ Redis key→postId | ⚠️ 缺位（演示双击可能发重） | 生产增强 |
| **③ 内容处理** | 提取话题/提及/审核/embedding → 元数据 | ✅ 话题/提及同步 + 审核/embedding 异步 | ✅ 话题/提及同步（无审核） | 演示保同步提取 |
| **④ 落库** | `PostRepository.save` → postId | ✅ MySQL 快照 | ✅ 内存 + JSON 落盘 | ID 单调 |
| **⑤ 事件发布** | `postCreatedNotifier.notify` → `PostCreatedEvent` | ✅ outbox→Kafka "post-created" | ✅ 进程内同步 notify | 写读分界；演示用同步模拟 Kafka |
| **⑥a 关注流扇出** | 消费事件 → `fanout` 写 B 的 inbox | ✅ KafkaPostCreatedConsumer | ✅ InMemoryPostCreatedNotifier | B 的 inbox 收到 postId |
| **⑥b 推荐冷启** | 消费事件 → `trafficPool.notifyCreated` | ✅ 事件驱动 | ⚠️ 懒加载（NewItemPool 扫描） | 行为等价，口径略异 |
| **⑥c 搜索索引** | 消费事件 → 倒排索引 | ❌ 未做（搜索实时全表扫） | ❌ 同 | 生产可后续 |
| **⑥d 统计/热搜/通知** | 消费事件 → 热度聚合 / @提及通知 | ⚠️ 通知同步（notifyMentions），热搜实时 | 同 | 量小不拆 |
| **⑦ 用户看到** | B 打开关注流 → 读 inbox → 回源 → 渲染 | ✅ | ✅ | B 看到 A 的帖子 |

**完整时序（生产模式）**：
```
B 发帖请求
  → ①③④⑤ 同一请求内：校验 → 提取 → save → notify
  → ⑤ 生产：Kafka "post-created"（异步）
  → ⑥a fanout 消费者：写 B 的 inbox（Redis ZSet）
  → ⑦ B 打开关注流：GET /api/follows/feed → 读 inbox → 回源 → 显示
```
演示模式把 ⑤ 的 Kafka 换成进程内同步 notify，⑥a 直接扇出内存 inbox——**闭环等价、零中间件**。

## 4. 生产版 vs 演示版 能力矩阵

| 环节 | 生产（-Pprod） | 演示（默认） | 演示是否受影响 |
|---|---|---|---|
| 发帖/草稿/编辑/软删/回收站 | ✅ | ✅ | 不（核心闭环） |
| 话题/@提及 提取 | ✅ | ✅ | 不 |
| 幂等 | ✅（计划） | ⚠️ 缺位 | 不影响（演示双击可发重，可接受） |
| 审核/embedding 异步管道 | ✅（计划） | ❌ 缺位 | 不影响（演示无审核需求） |
| 事件发布 | ✅ Kafka + Outbox（计划） | ✅ 进程内同步模拟 | 不（演示用内存事件，零中间件） |
| ID | Snowflake（计划） | ✅ AtomicLong | 不（AtomicLong 单机够用） |
| 持久化 | MySQL 快照 | ✅ JSON 落盘 | 不 |

> **原则**：生产增强能力全部"演示缺位也 OK"；演示保留最小等价闭环，任何增强不得引入中间件依赖或破坏单进程可跑。

## 6. 演进路径（prod 优先，演示可缺位）

| 阶段 | 动作 | 归属 | 演示影响 |
|---|---|---|---|
| 0 现状 | 发帖→事件→fanout（生产 Kafka / 演示同步） | 主干 | 无 |
| 1 幂等 | `Idempotency-Key` → Redis/内存 key→postId 去重 | 生产为主 | 演示可加内存版（低风险） |
| 2 Outbox | 发帖事务写 outbox → Relayer 轮询 → Kafka | **仅生产** | 无（演示仍用同步 notify） |
| 3 内容管道异步化 | 审核/embedding 进队列，下游消费写元数据 | **仅生产** | 无 |
| 4 ID 生产化 | Snowflake 替换 AtomicLong | **仅生产** | 无（演示 AtomicLong 保留） |
