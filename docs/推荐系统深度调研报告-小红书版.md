# 总览：一句话理解这类系统

**小红书的推荐系统是"内容理解 + 多场景分发 + 用户画像 + 冷启动 + 商业变现 + 社区治理"的一体化中枢**。它不是一个孤立的"首页推荐接口"，而是贯穿内容从发布、审核、分发、互动、到变现的整条链路的神经系统。

工业级推荐系统的核心心智模型是 **"层层漏斗"**：

```
全量物料(千万~亿)
   │
   ▼  ① 召回 Recall     （轻量、快、广覆盖，从全量池捞几千~上万候选）
候选集(几千~上万)
   │
   ▼  ② 粗排 Pre-Rank   （中等复杂度，截断到几百~一千）
候选集(几百~一千)
   │
   ▼  ③ 精排 Rank       （复杂模型、特征全量，精准打分，得到几十~几百）
候选集(几十~几百)
   │
   ▼  ④ 重排 Rerank     （多样性、打散、业务规则、广告混排）
最终下发 Top-K（几十条）
```

这是阿里、字节、Netflix、小红书等所有头部公司的统一范式。**任何规模的项目（包括学习项目）都不该跳过这个漏斗思维**——它是后续平滑升级的地基。

# 第一部分 · 业务功能体系（以小红书为参照）

## 1. 内容形态与内容数据结构

小红书以 UGC 图文/视频笔记为社区底座。核心内容形态与推荐的关系：

| 形态 | 是什么 | 对推荐系统的意义 |
|---|---|---|
| **图文笔记** | 起家形态，1-18 张图 + 标题 + 正文，可挂标签/话题/地点；3:4 竖图封面 | 推荐以"封面点击率"为第一入口信号；图文构成多模态特征 |
| **视频笔记** | 15s-15min 竖屏视频 | 引入"完播率/观看时长/重播"等时序信号，单列沉浸流 |
| **直播** | 挂载商品/券/预告 | 主要靠关注/搜索/笔记引流，非推荐流直插 |
| **短评/评论** | 评论区 UGC 密度最高，"求链接"等评论是电商转化信号 | 评论文本参与语义召回；种草意向信号 |
| **商品笔记** | 笔记挂商品卡/链接 | "内容消费"与"商品转化"信号打通 |
| **探店/本地笔记** | 带 POI 地点 | 催生"附近/本地"流与 LBS 特征 |

一篇笔记在系统中的数据结构（每项都可能成为推荐特征）：

```
标题 / 正文 / 图片·视频(多模态) / 标签(hashtag) / 话题 / 地点(POI)
发布时间(新鲜度特征) / 挂载组件(商品卡·直播间·课程·团购券) / 作者信息(账号权重·粉丝数·垂类归属)
```

这些字段经**多模态内容理解**（图片理解、OCR、ASR、文本分类、标签预测）加工成"内容向量 + 结构化标签"，供召回、排序、审核三处复用。

## 2. 用户互动体系与行为信号

**互动行为的相对价值**（行业流传口径，随版本调整，仅作理解框架）：

```
关注 > 评论/转发 > 收藏 > 点赞
```

| 行为 | 类型 | 对推荐的价值 |
|---|---|---|
| 点赞 | 显式正向 | 最基础兴趣信号，但"决策价值"最低，易受随手赞污染 |
| **收藏** | 显式正向、高意向 | **对推荐/电商最有价值**，代表"想后续使用/购买" |
| 评论 | 显式正向+文本 | 高成本互动；"求链接"评论是种草转化信号 |
| 转发/分享 | 显式强正向 | 代表内容"值得传播" |
| 关注 | 关系信号 | 最强正向，构建关系链 |
| 浏览时长/停留 | 隐式 | 双列=卡片停留/详情时长；单列=观看时长 |
| 完播率 | 隐式(视频) | 视频权重核心指标，秒划走是强负信号 |
| 点击率(封面→正文) | 隐式 | 双列瀑布流下最重要的第一层信号 |
| 不感兴趣/屏蔽/举报 | 显式负向 | 多级负反馈，直接压低曝光 |

> **行业流传的 CES 评分**（Community Engagement Score，非官方确认）：`CES ≈ 点赞×1 + 收藏×1 + 评论×4 + 转发×4 + 关注×8`，叠加完播率/时长/账号权重。核心思想是**深度、成本高的互动权重更大**，用于流量池晋级判定。

**对系统设计的意义**：互动信号是推荐模型的**训练目标与特征来源**。收藏/搜索/求链接是高转化意向信号，应作为排序目标之一；负反馈体系（不感兴趣 → 减少此类 → 屏蔽作者 → 举报）形成精细化的负向样本。

## 3. 信息流产品：多场景并存

- **底部 Tab**：发现(双列瀑布流)、购物、消息、我；（视频一度获得一级入口）
- **顶部频道**：关注 / 发现 / 视频 / 直播 / 本地，实现**多流并存**
- **四大流量入口**（行业口径）：**发现页(推荐) + 搜索页(搜索) + 关注页(订阅) + 本地页(附近)**，"发现页决定生死、搜索页是增长红利"
- **双列 vs 单列**：双列重"封面 CTR + 点击后行为"（双层漏斗），单列重"完播/时长"（时序信号）→ **排序目标需分形态设计**
- **刷新/加载**：下拉刷新、无限加载、预加载，直接影响"曝光样本"质量

**对系统设计的意义**：多流并存 = 多场景模型（同一内容在推荐/搜索/关注/附近需要不同召回与排序）；搜索词是最高置信度兴趣信号，可回填画像并反哺推荐冷启动。

## 4. 用户画像体系

- **基础属性**：年龄、性别、城市/地域、消费力等级、设备
- **兴趣标签/类目偏好**：按垂类（美妆、穿搭、美食、家居…）聚合的兴趣强度
- **作者偏好**：关注/常看作者集合（作者级协同）
- **位置**：POI 与 LBS（支撑本地流与本地广告定向）
- **活跃时段**：影响新鲜度分发与"黄金发布时间"
- **商业画像**：小红书商业化宣称拥有 **3200+ 行业决策因子**（"TA 是谁"升级到"TA 为什么买"）

**画像构建**：显式引导（新用户 OnBoarding 选兴趣标签）+ 隐式更新（每次曝光/点击实时回流）。自然流量与商业流量共用同一套用户理解。

## 5. 冷启动问题

### 5.1 新内容（新笔记）冷启动 —— 流量池/爬坡机制

```
发布 → 初始小流量池(200~500 曝光)
  → 观察早期指标：点击率 CTR / 互动率 / 收藏率 / 完播率 / 关注转化
  → 达标(与同类均值对比的相对值) → 进入更大流量池(5000→5万→50万...)
  → 不达标 → 留在原池/降权
```

- **为什么初始池必须小**：控制试错成本，避免低质内容污染信息流
- **晋级看相对值**：和同赛道/同时段内容均值比（如 CTR 超均值 1.5 倍），因品类基数差异大
- **置信度门槛**：设置最小曝光量后再判定晋级，防止小样本误杀优质内容
- **冷启动入口保证**：新内容要有独立"新内容召回通道"（按类目/标签倒排索引、新近召回、与同作者旧高赞内容关联）

### 5.2 新用户冷启动

- **引导页选兴趣** → 构造"弱交互画像"，后续召回/排序可被标签加权（注意：勾选兴趣≠真实兴趣，应给先验权重衰减，被真实行为逐步覆盖）
- **热门兜底**：无信号时用全局/地域热门保底
- **搜索行为**：新用户搜索词是最强意图信号
- **快速探索**：首屏"60% 有把握 + 30% 较稳妥 + 10% 试探"，并留负反馈出口

## 6. 商业化：广告、电商种草、直播带货

| 商业产品 | 是什么 | 与推荐的关系 |
|---|---|---|
| **薯条** | 笔记加热/内容推广 | 付费流量撬动自然流量，进同一推荐池竞争 |
| **聚光** | 效果广告投放平台 | 与自然内容混排在推荐流/搜索流，联合竞价+频控 |
| **蒲公英** | 达人合作撮合 | 达人创作种草笔记再投流放大 |
| **乘风** | 电商/直播投流工具 | 为店铺/直播间引入流量 |

**对推荐系统的意义**：
- 从"只看互动"升级为**多目标联合优化**（互动+点击+收藏+加购+下单+广告营收）
- **广告与自然内容统一排序（混排）**，做频控与体验约束（行业公开讨论"广告加载率 vs 用户体验"的博弈）
- 收藏、求链接评论、搜索词成为高转化意向标签，反哺电商排序与广告定向

## 7. 社区治理与推荐的关系

- **发布审核**：机审（AI 模型/敏感词/图片视频识别）+ 抽检人工，未过审不进推荐池。小红书官方论文 **Hi-Guard**（KDD 2026）做多模态审核，给可解释违规理由
- **账号治理**：小红书 2025 年首推"**真诚分**"体系，对黑灰产/虚假种草/刷量降权限流
- **去重/限流**：搬运/抄袭/低质同质化内容检测压制；"仅自己可见"等限流
- **负反馈闭环**：不感兴趣 → 减少此类 → 屏蔽作者 → 举报，多级负向样本
- **算法公示与合规**：披露推荐机制、热搜规则，支持用户自主关闭个性化推荐

**核心结论**：治理体系直接进入推荐链路——审核/真诚分/去重是"前筛"（决定内容能否进入召回池），限流/负反馈是"后惩"（在线压低权重）。推荐系统必须在**效果、商业化收入、内容安全、用户体验**四者间做**多目标约束优化**。

# 第二部分 · 技术架构（标准范式）

## 1. 整体分层：离线 / 近线 / 在线

三层架构模型最经典地来自 **Netflix 2013 公开架构**，也是业界统一范式：

| 层级 | 数据时效 | 响应要求 | 时延 | 核心职责 |
|---|---|---|---|---|
| **离线层 Offline** | 不依赖实时数据 | 不提供实时响应 | 小时~天 | 数仓、离线特征、模型批量训练、画像构建、索引构建 |
| **近线层 Nearline** | 使用实时数据 | 不保证实时响应 | 秒~分钟 | 实时特征更新、实时训练样本拼接、模型增量学习 |
| **在线层 Online** | 使用实时数据 | 保证实时响应 | 几十毫秒 | 召回+排序推理、在线特征拼接、AB 分流、业务干预 |

设计哲学：在线层时延天花板决定了它**只能用"预先算好的特征/索引/向量 + 轻量推理"**，重活全部前置到离线/近线。

```
客户端/App/Web（埋点：曝光/点击/时长/转化）
        │                                  ▲ 请求(uid, 场景, 上下文)
        ▼                                  │
   日志系统/Kafka                     在线层 Online
        │                              ├ 1. 特征获取(Redis/HBase)
        ▼                              ├ 2. 多路召回(热门/I2I/向量ANN/规则)
   近线层 Nearline                     ├ 3. 粗排截断
   Flink 实时特征/实时样本             ├ 4. 精排打分(CTR/CVR/时长)
   实时增量训练                        ├ 5. 重排(多样性/打散/广告)
        │                              └ 6. AB分流 + 下发
        ▼                                     ▲
   离线层 Offline                              │ 模型/特征/索引定期同步
   Spark/Hive 数仓│画像│离线特征│样本│模型训练 ─┘
```

## 2. 召回（Recall / Match）：多路召回

目标：从千万~亿级候选池选出**几千~上万**候选。为什么必须多路：

1. **单一路覆盖不足**：热度照顾全局、协同照顾相似兴趣、向量照顾语义深度，各有盲区
2. **鲁棒性兜底**：一路失败其他路兜底
3. **多样性分发**：精准/试探/时效按比例，且可解释

| 召回类型 | 核心思路 | 适用场景 |
|---|---|---|
| 热门召回 | 按全局消费热度 TopN | 冷启动用户、兜底、所有多路召回的"保底路" |
| 协同过滤 I2I/U2I | ItemCF：看了 A 的人还看 B；UserCF：相似用户喜欢什么 | 经典基础召回（Amazon 基石） |
| U2T2I/类目召回 | 用户→偏好类目/标签→该类目优质物料 | 意图明确、可解释 |
| 规则召回 | 地域 LBS、新品时效、复购、同卖家 | 强业务规则 |
| 向量召回 | 双塔把 user/item 映射到同一向量空间，线上 ANN 检索 | 语义深召回，**当前主流个性化召回** |
| 图召回 | Node2Vec/DeepWalk 学习图向量 | 挖掘多跳关系（淘宝 EGES） |
| 树/结构召回 | 学习可检索树结构 beam search | 字节 Deep Retrieval，数亿物料 |

**向量召回的关键工程点**（双塔 + ANN）：
- item embedding 与用户无关 → **离线全部算好建索引**，线上只算 user embedding 然后 ANN 检索
- ANN 算法：**Faiss**(PQ 向量量化)、**Annoy**(LSH)、**HNSW**(分层小世界图)
- **两个经典坑**：① 要归一化 embedding（点积不是度量空间、不满足三角不等式，HNSW 在点积下效果差；归一化后点积≈欧氏距离）；② 要温度系数（归一化后值域 [-1,1]，无温度系数难收敛）

## 3. 排序（Rank）：粗排 + 精排

### 3.1 粗排（Pre-Rank）
- 把上万候选截断到几百~一千，减轻精排压力
- 演进：全局统计截断 → LR/GBDT 轻量打分 → **双塔 DNN**（当前主流，用户侧/物品侧少量特征子集）
- 关键手法：**知识蒸馏**——用精排模型做 teacher，蒸馏出轻量 student 粗排模型，缩小粗排精排预估差异（**链路目标一致性**）

### 3.2 精排（Rank）
- 对几百~上千候选做最精准打分，技术含量最高、研究最密集
- 预估目标：CTR → CVR、时长、互动率等多目标
- **特征体系**：
  - 用户特征：画像、长期/短期行为序列、session 行为
  - 内容特征：item id、tag、类目、作者、多模态表征
  - 上下文特征：时间、地点、设备、网络、场景
  - 交叉特征：用户×内容、组合 id 特征
- **模型演进主线**：

```
LR(线性+人工交叉)
 → GBDT/LR+GBDT(Facebook 自动特征交叉)
 → FM/FFM(自动二阶交叉，稀疏友好)
 → Wide & Deep(记忆+泛化并行)
 → DeepFM/xDeepFM(端到端深度交叉)
 → DIN/DIEN/DSIN(行为序列注意力/兴趣演化)
 → MMoE/多任务多目标(CTR+CVR+时长)
 → Transformer 序列 → LLM 大模型(2025 淘宝 RecGPT 百亿参数)
```

- **多目标打分融合**：线性加权(人工)、随机搜索、CEM、贝叶斯优化、强化学习自动调权。示例：`RankScore = 10·P(click) + watch_time + P(praise)`

### 3.3 精排的落地形态
精排通常 **point-wise 并行打分**（逐 item 独立过模型），牺牲列表上下文感知——**这正是重排阶段存在的根本原因**。

## 4. 重排（Rerank）：多样性 + 业务规则 + 混排

为什么必须重排：
1. 精排 point-wise 看不到"周围其他 item"，而点击与前后内容强相关
2. 单点得分高易同质化、信息冗余
3. 承载业务规则：去重、打散、广告强插、流量扶持、合规过滤
4. 多业务线混排（广告/图文/视频/banner）

**规则类**（最常见、最可控）：
- 强制去重（同图/同作者/同视频）
- **打散**：类目打散、创作者打散、图文/视频间隔（小红书：最多连续 k=5 篇同形态；每 k=9 条最多 1 条广告）
- 提权/降权：大促类目提权、新品扶持、限流

**算法类**：
- **MMR（最大边际相关）**：贪心选"得分高 + 与已选集合差异最大"；工业界用滑动窗口改进（只与最近 N 个已选算相似）
- **DPP（行列式点过程）**：用行列式度量集合多样性，Hulu 给出 Cholesky 增量贪心求解，比 MMR 更能建模整体多样性
- RNN/模型类重排（阿里 globalrerank）

## 5. 特征平台与数据链路

### 5.1 实时特征 vs 离线特征

| 维度 | 离线特征 | 实时/近线特征 |
|---|---|---|
| 计算 | Spark/Hive 批处理(天/小时) | Flink 流计算(秒/分钟窗口) |
| 典型内容 | 长期画像、item 质量分、历史统计 | 最近 5 分钟点击、实时 CTR、session 行为 |
| 存储 | 离线数仓 | Redis/HBase 在线特征存储 |
| 问题 | 滞后、分布不一致 | 需与离线口径一致、防特征穿越 |

### 5.2 特征存储：Redis 是核心
- 在线推理需毫秒级取几十个预计算特征，Redis 提供 **<1ms P99、百万级 QPS**
- 关键能力：批+流并发写入同一实体，避免 **training-serving skew（训练-推理特征不一致）**；逐特征 TTL（HEXPIRE）；pipelined HMGET 一次取数百实体特征
- 大厂主流做法是**自研 Redis 特征服务**（Flink 算 → Redis 写 → 在线按 user+item+context 批量 MGET）

### 5.3 数据链路全貌

```
客户端埋点(曝光/点击/时长/转化/设备/session)
  → 日志收集 → Kafka
  → [离线] Kafka→Spark/Hive 数仓→画像/离线特征/天级~月级样本→离线训练→模型/索引推送在线
  → [近线] Kafka→Flink 流计算(实时特征/实时样本Join/实时索引/增量模型)→写 Redis/实时样本表
```

**关键概念**：
- **样本生成与 Label**：样本 = 曝光/行为日志 × 特征快照。正样本=曝光后点击/转化，负样本=曝光未点击。分阶段窗口：曝光-特征 5min、曝光-点击 10min、点击-转化 20min（超时视为负样本），可按品类配置
- **特征穿越(泄漏)防护**：用 Feature Dump——线上请求时对实际用到的特征做快照，训练用快照而非事后重算
- **在离线一致性**：统一同一套计算逻辑/SDK，保证口径一致

## 6. 在线服务

### 6.1 请求链路

```
用户请求(uid, 场景, 上下文, 请求量n)
 → 网关(限流/鉴权)
 → 特征获取(Redis 用户画像/实时离线特征/行为序列)
 → 多路召回(并行)→merge+去重→候选集
 → 粗排(双塔/轻量)→截断
 → 精排(Deep 多目标打分)→排序
 → 重排(多样性/打散/MMR/DPP/规则/广告混排)→Top-K
 → 组装下发(填充封面/标题/推荐理由)→返回
```

### 6.2 性能与容灾
- 端到端几十~百毫秒；腾讯云 Java 案例：峰值 **2.7 万 QPS、P99 72ms**
- **Java 侧关键优化**：
  - **异步全链路**：`CompletableFuture` 编排特征获取/模型调用/规则过滤（同步→异步后单节点吞吐 800→4200 QPS）；Java 21 虚拟线程
  - **gRPC 长连接 + 连接池**：与 TF Serving/PyTorch 通信，keepalive + RoundRobin
  - **攒批推理**：窗口内请求合并成 batch 一次推理（吞吐提升 3 倍）
  - **GC 调优**：对象池复用 + ZGC 稳定 P99
  - **模型预热**：启动时发哑请求预热，避免大模型加载超时
- **容灾**：多路召回路互为兜底；排序失败直接用召回结果；全链路失败返回热门兜底池；超时/熔断/降级/限流

### 6.3 AB 实验
- **分层正交**（Google KDD'10 论文）：同一用户可同时参与召回层/排序层/样式层实验而互不干扰；层内互斥、层间正交（不同 salt 哈希分桶），前提是各层效果近似可加
- **分流**：`bucket = hash(uid + salt) % 100`，用户粒度分桶，同一用户始终进同一组
- **数据打通**：每条曝光/行为日志带 `exp_id`，事后按实验归因
- **铁律**：离线指标只做初筛，"能不能上线"以 AB 在线指标为准

## 7. 评估体系

### 7.1 离线指标
| 指标 | 度量什么 | 使用位置 |
|---|---|---|
| AUC | 正样本得分>负样本的概率 | 精排主指标 |
| **GAUC**(Group AUC) | 按用户分组 AUC 加权平均 | **推荐排序更常用**（消除用户行为次数差异） |
| Recall@K / Precision@K | TopK 命中率/召回率 | 召回模型评估 |
| NDCG@K | 位置加权相关性 | 重排/精排 list 效果 |
| MRR / MAP | 首个相关位置/平均精度 | 搜索、单目标 |
| LogLoss/Calibration | 概率校准 | CTR 预估校准度 |
| **覆盖率** | 推荐出的物品占全量比例 | 长尾健康度（低=只推头部 1%） |
| **多样性** | 类目熵/ILS 列表内相似度 | 信息茧房对抗 |
| **新颖度/新鲜度** | -log2 p(item)；内容新旧占比 | 生态健康度 |

### 7.2 在线指标（业务指标族）
```
曝光层: 曝光量、曝光多样性
点击层: CTR
互动层: 点赞率/评论率/收藏率/转发率
消费层: 人均浏览数/时长、完播率
行为层: 关注转化、下单率、GMV
留存层: 次日/7日/30日留存、回访频次   ← 长期北极星
```

### 7.3 离线与在线 Gap（为什么"离线好≠线上好"）
1. **位置偏差**：排前面天然易被点击，离线高估
2. **曝光/幸存者偏差**：模型只在被曝光过的 item 上评估
3. **训练-推理不一致**：特征口径/采样策略不同
4. **目标不一致**：离线优化 AUC/NDCG，线上优化互动/时长/留存
5. **时间效应**：用户兴趣漂移
> 缓解：离线只做粗筛，模拟线上链路（同候选集/同位置/时序切分），一切以 AB 为准。可用 **Replay(重放历史日志)** 和 **Interleaving(交织结果给同一用户)** 加快迭代。

## 2. 关键澄清：算法在 Java 生态怎么落地

**不要在 Java 里从零写深度推荐模型。** Apache Mahout 已休眠(2019 停更)、DL4J 活跃度低、ML 训练生态完全围绕 Python。业界标准分工：

```
[Python 训练侧]                      [Java 在线侧]
样本/特征(Spark 产出)                Spring Boot 在线服务
 → PyTorch 训练双塔/DIN/DeepFM         → 召回: 向量库/ES/Redis(物品向量离线下发)
 → 导出 ①物品/用户向量 ②ONNX 模型       → 精排: Java 调 ONNX Runtime/DJL 本地推理
        ↓                              → 或 Java 调远程推理(Triton/TorchServe)
  特征/向量/模型下发在线存储
```

**Java 端推理选型**：ONNX Runtime(Java API，首推) / DJL(AWS 维护) / Triton·TorchServe(独立服务)。

**学习阶段建议**：
- 召回先不碰模型：用"标签/热度/协同过滤"实现；向量召回用预训练 embedding（Spring AI 的 ONNX bge 小模型，Java 本地跑，无 Python 依赖）
- 精排用 Spark ALS 推荐表 + 简单 LR/规则打分；进阶再走"Python 训练 ONNX → Java 推理"

## 3. 本地开发：哪些能省、哪些不能省

**能省**：向量库(本地用 Redis VSS 或 ES kNN，注意 Milvus Lite 是 Python 库 Java 用不了)、Flink 单机模式/定时任务模拟、Spark local[*]、Hive(MySQL/Parquet 替代)、监控链路。

**不能省**：
1. **"召回→排序"漏斗**（哪怕只有热门+协同两路召回、规则打分）
2. **用户行为日志闭环**（曝光/点击埋点→存储→回流，没有行为数据就是空壳）
3. **Redis**（画像/特征/缓存中枢）
4. **元数据模型**（用户/物品/行为三张核心表）
5. **配置中心思维**（召回权重/热榜开关抽成可配置项，为 AB 留口子）

## 4. 一条本地可跑的参考路径

```
Docker Compose 起: MySQL + Redis + (Kafka + Flink 单机 可选) + (Milvus standalone 或 ES 可选)
Spring Boot 单体:
  - 数据导入: 用 MovieLens/公开数据集灌 MySQL
  - 离线: Spark local ALS → 推荐表写 Redis；或预计算物品向量写 Redis VSS/ES
  - 在线: GET /api/v1/rec?userId= → 读画像/特征(Redis) → 多路召回(热榜/协同/向量)
          → 规则/轻模型排序 → 重排去重 → 返回
  - 行为回流: POST 曝光/点击 → 写 MySQL + (Kafka → Flink 写 Redis 计数, 可选)
```

## 5. 冷启动与评估的最小闭环（学习项目）

```
① 数据层    CSV/内存数据，每条带 timestamp
② 切分层    时间切分 train/test（含冷启动隔离）
③ 策略层    可插拔：热门兜底 / ItemCF / 双塔 / Thompson bandit(新内容)
④ 评估层    AUC / GAUC / Recall@K / NDCG@K / Coverage / Diversity / Freshness
⑤ 报告层    打印/写 CSV → 对比各策略指标矩阵
```

- **新内容冷启动公式**（可落地）：`quality_score = w1·text + w2·visual + w3·author + w4·engagement_prior + w5·freshness_bonus`，新鲜度用指数衰减 `f0·exp(-λ·age)`；配合冷启动池 + Thompson sampling（Beta 后验：`θ~Beta(α,β)`，点击 α+=1，无点击 β+=1，每次按采样分排序）
- **Bandit 三件套**：ε-greedy（极简）、UCB1（`x̄ + c·sqrt(ln t/n)`，确定性）、Thompson（贝叶斯、免调参，工业界默认）
- **AB 分桶**：`bucket = hash(userId + salt) % 100`，层间不同 salt 正交

**避坑清单**（离线评估）：
| 坑 | 后果 | 避坑 |
|---|---|---|
| 随机切分 | 时间泄漏、指标虚高 | 一律时间切分，带 timestamp |
| 负样本采样不当 | 指标失真 | 负样本在"该时刻之后"采样 |
| 只看 AUC | 忽略覆盖率/新鲜度 | 指标矩阵 7 项全看 |
| 混合新老用户评估 | 冷启动效果被稀释 | 新用户/新物品单独出指标 |
| 离线好就上线 | 线上翻车 | 离线只做粗筛，以实验为准 |
| 只看短期 CTR | 损留存 | 同时看留存/长尾/负反馈 |

## 6. 学习路线（按依赖顺序）

1. **阶段一（离线算法）**：MySQL 元数据 + Spark ALS 离线推荐表 → 理解协同过滤
2. **阶段二（在线服务）**：Spring Boot 读 Redis 推荐表 → 出一个能响应的推荐接口
3. **阶段三（漏斗）**：多路召回（热门 + 标签 + ALS）+ 简单排序 + 重排去重
4. **阶段四（数据链路）**：埋点 → Kafka → Flink 实时特征写 Redis → 在线拼特征 → 实时反馈闭环
5. **阶段五（向量化）**：Spring AI ONNX embedding → Redis VSS/ES kNN 向量召回；进阶用 PyTorch 训双塔导出 ONNX、Java 推理精排
6. **阶段六（工程增强）**：Nacos 配置灰度、Sentinel 降级、Milvus 替换本地向量库、AB 实验平台
