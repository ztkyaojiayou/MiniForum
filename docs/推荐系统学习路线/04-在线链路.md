# 第4步：在线链路（1~2周）

> **一句话核心认知**：**在线链路是"用成本换精度"的多级漏斗 + 延迟预算的艺术。** 每一级用更重的模型处理更少的候选，200ms 内从亿级候选挑出最终几十条。模型不是难点，**延迟预算、降级策略、多级配合**才是工程难点。

---

## 1. 核心概念与原理

### 1.1 为什么是多级漏斗

精排模型最强，但不能对亿级候选逐条精算（太慢太贵）。所以层层截流：

```
候选池（亿级）
   ↓ 召回：快筛，捞出可能感兴趣的        → 千条
   ↓ 粗排：轻量模型快速粗筛             → 数百条
   ↓ 精排：强模型精细打分               → 数十条
   ↓ 重排：业务约束与体验               → 最终 30~50 条
```

**每一级的成本递增、候选递减**，端到端控制在 200ms 内。

### 1.2 在线链路全景

```
客户端请求（user_id, scene, context）
   ↓
接入服务（鉴权、限流、路由）
   ↓
特征服务（第3步）：拉取 user/item/context 特征
   ↓ 并行
┌──────────┬──────────┬──────────┐
│ 召回A(向量)│ 召回B(协同)│ 召回C(热门)│  ← 多路并发召回
└────┬─────┴────┬─────┴────┬─────┘
     └──────────┼──────────┘
        合并去重（配额截断）→ 千条
   ↓
粗排（批量轻量打分）→ 数百条
   ↓
精排（逐条强模型打分）→ 数十条
   ↓
重排（多样性/业务约束）→ 30~50 条
   ↓
下发 → 客户端渲染 → 产生曝光日志（回到第1步闭环）
```

## 2. 关键技术细节

### 2.1 延迟预算分配（核心工程能力）

**端到端目标：P99 < 200ms**。预算分配示例：

| 环节 | 预算 | 优化手段 |
|------|------|---------|
| 接入/路由 | 10ms | 轻量、无 IO |
| 特征拉取 | 30ms | 批量取、Redis 缓存、并行 |
| 召回 | 50ms | 多路并行、ANN 检索 |
| 粗排 | 20ms | 批量打分 |
| 精排 | 50ms | GPU/批量推理、特征复用 |
| 重排 | 20ms | 轻量算法 |
| 下发/序列化 | 20ms | 精简 payload |

**关键手法**：
1. **并行化**：召回多路并行、特征与召回并行、粗排与精排衔接处管道化
2. **批量推理**：精排一次推理 batch 处理数百条，比逐条快一个数量级
3. **预计算**：能离线的全离线（item 向量、热门榜、统计特征）
4. **缓存**：热门请求直接命中缓存，跳过全链路

### 2.2 召回工程

#### 召回目标
从亿级候选快速捞出千条用户可能感兴趣的（宁滥勿缺）。

#### 多路召回（工业标配，绝不止一路）

```
┌─────────────────────────────────────────────┐
│  向量召回（双塔，主路）    → ANN 检索 top 800   │
│  协同过滤 I2I             → 看过的item找相似   │
│  社交召回                 → 关注的人/朋友喜欢   │
│  热门召回                 → 全局/垂类热门兜底   │
│  标签/关键词召回           → 显式兴趣匹配        │
│  新品/时效召回             → 冷启动+热点        │
│  语义召回（搜索联动）       → query/item 语义    │
└─────────────────────────────────────────────┘
              ↓ 合并 + 去重 + 配额截断（千条）
```

#### 双塔召回服务

```
User Tower（在线）: user特征 → embedding → L2归一化 → user向量
Item Tower（离线）: item特征 → embedding → L2归一化 → item向量 → 存向量库
在线：user向量 → Milvus/Faiss ANN 检索 → top-K item
```

**关键点**：
- Item 向量离线批量生成（重活离线做），在线只算 user 向量 + 检索
- ANN 参数：`nprobe`（IVF 搜几个聚类）/ `ef_search`（HNSW 搜索范围），越大召回率越高但越慢，要调参
- **向量 + 标量过滤**：检索同时过滤（如"只取 7 天内发布 + 排除已读"）

#### 多路融合（配额制）

```
向量路: 800 条
协同路: 200 条
热门路: 300 条
社交路: 100 条
   ↓ 合并去重（同一 item 保留最高优先级来源）
   ↓ 若总量不足千条，热门路补齐（兜底）
   → 送入粗排
```

**为什么用配额不用分数**：各路打分尺度不同（向量相似度 vs 热度分 vs 协同分），不能直接比大小。**让粗排统一排序，召回只负责"提供候选"**。

**配额动态调整**：新用户向量路效果差 → 加大热门/新品配额；大促期加大商业化召回配额。

### 2.3 粗排

**目标**：从千条快速筛到数百条，控制精排计算量。

| 方式 | 说明 |
|------|------|
| 双塔批量打分 | 复用双塔：user 向量 × item 向量批量内积，快 |
| 轻量 MLP | 少量特征 + 小模型，批量推理 |
| 规则粗筛 | 简单规则（如过滤低质、重复） |

**要点**：粗排要"少漏"（高召回率），不追求精确排序，宁可多留候选给精排。

### 2.4 精排

**目标**：对数百条精细打分，输出最可能让用户满意的几十条。

#### 模型选型（工程视角）

| 模型 | 特点 | 什么时候用 |
|------|------|-----------|
| **LR** | 线性、可解释、快 | 基线、简单场景 |
| **GBDT/XGBoost** | 强特征工程、非线性 | 特征以统计类为主的场景 |
| **DeepFM** | 低阶+高阶交叉自动学 | 主流选择，工程成熟 |
| **DIN** | 注意力建模用户兴趣多样性 | 行为序列丰富的内容/电商 |
| **MMoE** | 多目标（点击+时长+转化） | 多目标优化的标配 |

**工程要点**：
- 模型部署：TF Serving / ONNX Runtime / Paddle Serving，GPU 批量推理
- **批量推理**：一次 batch 喂数百条，用 GPU 并行，比逐条快 10 倍+
- 特征复用：精排需要的特征尽量从特征服务一次拉全，避免重复 RPC
- 多目标融合：点击分、时长分、转化分加权（权重由业务定 + AB 调）

#### DeepFM 一句话理解

```
DeepFM = FM（低阶交叉：二阶特征组合）+ Deep（高阶交叉：DNN 学复杂模式）
两者共享 embedding，同时学"记忆"（FM）和"泛化"（Deep）
```

#### DIN 一句话理解

```
DIN = 注意力机制：用户历史点击的每个 item 与当前候选 item 算相关度
      相关度高的历史行为贡献大 → 建模"兴趣多样性"
      （用户既喜欢科技又喜欢美食，看美食推荐时"美食历史"权重更大）
```

### 2.5 重排

**目标**：精排分数不是唯一标准，要处理体验和业务约束。

| 手段 | 解决什么 |
|------|---------|
| **多样性打散**（MMR/DPP） | 防止同一作者/同一题材霸屏 |
| **类目平衡** | 内容池不要全是同质内容 |
| **疲劳控制** | 刚看过的内容不再推、同 item 去重 |
| **商业化插帧** | 广告按比例插入自然流 |
| **人工干预** | 运营置顶、黑名单、品牌保护 |
| **频控** | 同一用户每天推送次数上限 |

#### MMR 一句话理解

```
MMR = 贪心选择：每选一条，既要"和用户相关"，又要"和已选的不重复"
      score = λ·相关性 − (1−λ)·与已选集合的相似度
```

#### DPP 一句话理解

```
DPP = 用行列式点过程建模"集合的整体质量"
      能一次性选出一个"相关且多样"的集合，比 MMR 更全局最优
      （矩阵行列式：对角线=相关性，非对角线=相似度惩罚）
```

### 2.6 缓存 / 降级 / 熔断 / 兜底（高 QPS 保命四件套）

| 手段 | 场景 | 做法 |
|------|------|------|
| **缓存** | 热门请求/热门用户 | 整页缓存（相同请求直接返回）、局部缓存（热门 item 特征/向量） |
| **降级** | 特征服务超时 | 特征用默认值；向量召回失败 → 只用热门召回 |
| **熔断** | 下游持续故障 | 快速失败（如 10 次失败熔断 30s），避免雪崩 |
| **兜底** | 全链路失败 | 返回热门榜/编辑精选（无论如何要有内容下发） |

**兜底是底线**：推荐接口可以"推荐得不准"，但**绝不能返回空**——空页面 = 事故。兜底策略（热门/编辑精选/默认流）必须随时可用。

## 3. 工程落地要点

1. **延迟预算表是开工前必须画的**：先定 200ms 怎么分配，再写代码，最后用压测验证
2. **多级之间解耦**：召回输出（item 列表）→ 粗排 → 精排 → 重排，每级接口明确、可独立替换
3. **召回和排序分开部署**：召回服务（向量检索）与排序服务（模型推理）独立扩容
4. **监控在线链路全环节**：每级耗时、每级输出量、每级失败率
5. **从简到繁迭代**：先"热门召回 + 规则重排"上线跑通，再逐步加向量召回、精排模型——**先让系统转起来，再变准**
6. **模型灰度上线**：新模型先小流量，AB 验证后再放量（第5步）

## 4. IoT 背景认知补全

### 你的底子能平移什么

| IoT 经验 | 平移到在线链路 |
|---------|--------------|
| 高并发服务（网关、限流、路由） | 直接复用 |
| 缓存/降级/熔断/兜底 | **老本行**，直接复用 |
| Milvus 向量检索 | 召回层基础设施现成 |
| 分布式服务拆分扩容 | 直接复用 |

### 你的认知缺口（重点补）

1. **多级漏斗是全新的**：IoT 没有"候选集→多层筛选"的流水线，告警分析是单层处理；C 端是"召回→粗排→精排→重排"层层过滤，**每一级都要想清楚成本和精度的权衡**。
2. **模型推理服务是新的**：IoT 模型多为离线分析/批量；C 端模型是**在线毫秒级推理**，要学 TF Serving/ONNX、批量推理、GPU 部署。
3. **延迟预算思维是新的**：IoT 对延迟容忍度高（秒级~分钟级），C 端 200ms 内要完成"特征+召回+排序+重排"，**每一毫秒都要精打细算**。
4. **重排的业务约束是新的**：IoT 没有"多样性""疲劳控制""广告插帧"这些体验概念，这是 C 端特有的业务层。

## 5. 常见坑与避坑

| # | 坑 | 后果 | 避坑 |
|---|-----|------|------|
| 1 | 召回只做一路（只做向量） | 冷启动/时效内容全漏 | 多路召回 + 配额融合 |
| 2 | 各路分数直接比较 | 尺度不一致，热门霸榜 | 配额制，让粗排统一排序 |
| 3 | 精排逐条推理 | P99 超时 | 批量推理 |
| 4 | 特征重复 RPC | 延迟爆炸 | 一次拉全、复用 |
| 5 | 没有兜底 | 下游故障返回空页 = 事故 | 兜底流永远可用 |
| 6 | 召回和排序耦合死 | 无法独立优化/扩容 | 接口解耦、独立部署 |
| 7 | 不监控每级耗时 | 延迟劣化无感知 | 全环节耗时/失败率监控 |
| 8 | 一上来就上 DeepFM | 链路没跑通先堆模型 | 先简单链路跑通，再逐步加 |
